# Architecture Decision Log

## ADR-001 — Bottom-up assembly order
**Date:** 2026-07-31
**Context:** The org chart must be derivable consistently from any business idea.
**Decision:** Assembly order is strict: tasks → sub-agents → teams → roles. Roles are assembled last to lead each team, never designed top-down.

## ADR-002 — Brains vs. Hands are separate key types
**Date:** 2026-07-31
**Context:** LLM provider access and service-API access have different scopes, risk profiles, and collection timing.
**Decision:** Brains (LLM providers, per-role) and Hands (service APIs, per-sub-agent, collected just-in-time) are separate key types with separate lifecycles in the vault.

## ADR-003 — Platform pays for onboarding only
**Date:** 2026-07-31
**Context:** Free-execution abuse and trial economics were the biggest v1 cost risk.
**Decision:** Platform pays AI inference ONLY for onboarding (capped cents/signup); everything after the Charter handoff is BYOK.

## ADR-004 — CEO agent is a recommender by architecture
**Date:** 2026-07-31
**Context:** Autonomous execution by a synthesizing agent is a safety and trust risk.
**Decision:** The CEO agent is a recommender by architecture — its only output pathway is the approval queue. It can never execute directly.

## ADR-005 — Trust core is CODEOWNERS-locked
**Date:** 2026-07-31
**Context:** The router, vault, cost gate, and approval queue are the security-critical trust core of the system.
**Decision:** Trust core (router, vault, cost gate, approval queue) is CODEOWNERS-locked; no AI-generated merges without human review.

## ADR-006 — Trust-core dependencies are pinned; the orchestration library is accessed only through our executor interface
**Date:** 2026-08-01
**Context:** `apps/router/` depends on the third-party `@open-multi-agent/core` package. A bare `open-multi-agent` name collision on npm (an unrelated project by a different author) already showed how easy it is to pull in the wrong thing; an unpinned version or a direct import scattered through business logic would make both a supply-chain compromise and a future swap-out far more dangerous and expensive.
**Decision:** Trust-core dependencies (starting with `@open-multi-agent/core`) are pinned to exact versions with a committed lockfile — no `^`/`~` ranges, no floating updates. Business logic never imports the orchestration library directly; it only ever goes through our own `AgentExecutor` interface (`apps/router/src/executor.ts`), so the library can be upgraded, patched, or replaced behind that interface without touching callers.

## ADR-007 — LocalKms is refused in production
**Date:** 2026-08-01
**Context:** `packages/vault`'s dev-only `LocalKms` stores the master key in a local file — no rotation, no HSM, no access audit on the master key itself. That's an acceptable dev convenience and an unacceptable production posture (T1: user API key theft) if it ever ships by accident (e.g. a missing env var in a deploy config).
**Decision:** Constructing `LocalKms` while `NODE_ENV=production` (or explicit `PRODUCTION=true`) throws `ProductionKmsGuardError` instead of silently working. Production must construct a real `Kms` implementation (`CloudKms` or equivalent) — there is no code path where a misconfigured production deploy quietly falls back to a file on disk.

## ADR-008 — Router refuses to construct in production without a CostGate and an ApprovalQueue
**Date:** 2026-08-01
**Context:** Both dependencies are optional constructor arguments on `Router` (dev/test convenience — the router's own tests don't need cost-gate or approval-queue machinery to verify tagging/dedup/ledger behavior). Nothing before this stopped a misconfigured production deploy from constructing a `Router` with one or both omitted, silently running every task with no spend limit (T4) and no human review before an effect runs (T10, security-architecture.md §5).
**Decision:** Same pattern as ADR-007: constructing `Router` while `NODE_ENV=production` (or `PRODUCTION=true`) throws `ProductionRouterGuardError` unless both a `CostGate` and an `ApprovalQueue` are provided. Dev/test code paths are unaffected — both remain optional outside production.

## ADR-009 — The shell/trust-core integration seam is an ESLint rule, not a convention
**Date:** 2026-08-01
**Context:** `apps/api` (and, later, `apps/web`) is the Emergent boundary side of the system — it's expected to iterate quickly, including with AI-generated changes, while trust-core (router, vault, cost gate, approval queue — ADR-005) stays CODEOWNERS-locked and slow-moving. If shell code ever reaches past a trust-core package's public `index.ts` into its internals (e.g. `@byok/vault/src/kms.js` instead of `@byok/vault`), the CODEOWNERS lock stops meaning much: internal APIs can change shape without the shell noticing at review time, and the shell can end up depending on implementation detail no one meant to expose. Relying on code review discipline alone to catch this doesn't scale, especially once AI-assisted changes are landing in the shell regularly.
**Decision:** `eslint.config.js` at the repo root applies a `no-restricted-imports` rule to `apps/api/**` and `apps/web/**` that blocks any import path matching `@byok/{router,vault,cost-gate,approval-queue}/*` — only the bare package import (which resolves to that package's `index.ts`) is allowed. This fails the build the same way a typecheck failure would; it isn't advisory. Trust-core packages themselves are not subject to this rule (they're allowed to reference each other's internals only through the same public interfaces, but that's enforced by their own existing design, not this rule). CI (see `.github/workflows/ci.yml`) runs `npm run lint` on every PR so a violation blocks merge before a human reviewer ever needs to notice it by hand.

## ADR-010 — Phase B is built by Claude Code under PR-per-issue discipline, not Emergent
**Date:** 2026-08-01
**Context:** The original plan (master-plan-v2.md §4, README) named Emergent as the Phase B builder, on the premise that a separate visual-design tool would generate the commodity UI surface fast and Claude Code would stay out of its way. In practice the scaffold Emergent was meant to generate already exists — Phase A's shell (`apps/api`, `packages/auth`, `packages/db`, `packages/jobs`) was built by Claude Code, is CODEOWNERS-reviewed, and Phase B needs to build directly on it rather than have a second tool re-derive or duplicate it. There's also no reason the containment fence built for Phase A (CODEOWNERS, the ADR-009 lint boundary, branch protection, required CI) should apply only to trust-core or only to one code generator — a UI bug or a boundary violation lands the same way regardless of which tool wrote the diff.
**Decision:** Phase B's commodity surface (`apps/web` and its supporting work) is built by Claude Code, one branch and one PR per step, each referencing a tracked issue, each requiring the same CODEOWNERS review, ADR-009 lint boundary, and required CI checks as everything else in this repo. This is a statement about which generator is producing shipped code, not a relaxation of the fence: the fence (CODEOWNERS, lint boundary, branch protection, CI) applies to every code generator equally, whether that's a human, Claude Code, or any other tool. External design tools (Figma, reference mockups, etc.) may inform the visual design, but they produce visual references only — no code from them enters the repo directly; it's implemented and reviewed the same as everything else.

## ADR-011 — The interview extracts the value chain, not founder preferences
**Date:** 2026-08-01
**Context:** Early onboarding-flow drafts mixed two different kinds of questions: ones that determine the actual STRUCTURE of the business (who pays, for what, how money and delivery move, which jurisdiction's rules apply) and ones that reflect the founder's PREFERENCES about how their company should run (which role to hire first, how much autonomy to grant agents). The first kind changes what org chart gets assembled — ADR-001's bottom-up task → sub-agent → team → role derivation depends on getting the value chain right. The second kind doesn't change the org chart at all; it changes settings on top of an org chart that's already correct. Conflating them made the interview longer than it needed to be and put configuration decisions (autonomy posture, especially) in a place — early onboarding, before the user has seen any real output — where they're hardest to make well.
**Decision:** The interview extracts the value chain only, walking inward from customer to CEO: what customers pay for → who the customer is → how money arrives → how delivery reaches them → jurisdiction. Founder-preference questions — first-hire priority, autonomy posture, and anything else that's a setting rather than a structural fact about the business — are configuration and live outside the interview, asked later at the point where they're actually actionable (e.g. autonomy posture during the BYOK/ceiling flow, once the user has a real role in front of them to grant autonomy to).

## ADR-012 — Trust-core review is a required CI attestation check, not an unsatisfiable approval requirement

**Date:** 2026-08-01
**Context:** Branch protection on `main` required an approving CODEOWNERS review before merge (issue #10's close-out). That's unsatisfiable as configured: every PR in this repo is authored by the `veltrixnextgen-arch` account (via the `gh` CLI), which is also the only entry in `.github/CODEOWNERS` — and GitHub does not allow an account to approve its own pull request. The first real attempt to merge a reviewed, CI-green PR (#29) hit this directly: `gh pr merge` refused with "the base branch policy prohibits the merge," not because anything was wrong with the PR, but because the required review could never exist. Removing the requirement outright would drop trust-core protection to "CI green" with no human-attention signal at all — acceptable for `apps/web` commodity-surface work, not for `packages/vault`, `packages/cost-gate`, `packages/approval-queue`, `apps/router`, `docs/architecture/security-architecture.md`, or the CI/lint-boundary/CODEOWNERS files themselves (ADR-009's rationale for locking those applies just as much here).
**Decision:** Branch protection on `main` no longer requires an approving review (`required_pull_request_reviews` removed; `required_status_checks` with `strict: true` and `enforce_admins: true` stay as-is). `.github/CODEOWNERS` stays in place, unchanged, as the source of truth for which paths are trust-core. In its place, a new required CI job (`trust-core-attestation` in `.github/workflows/ci.yml`) diffs the PR against its base branch: if any changed path matches a trust-core entry from CODEOWNERS, the job fails unless the PR description contains the literal line `TRUST-CORE REVIEWED: veltrixnextgen-arch`. That line must only be added after actually reading the trust-core diff — it is a required, auditable, machine-checked attestation, not a rubber stamp, and it's git history on the PR itself rather than a review that could be dismissed or lost. PRs that don't touch a trust-core path merge on green CI alone, same as any other repo. **This is a stand-in, not a replacement**: the moment a second maintainer exists, restore `required_pull_request_reviews` with `require_code_owner_reviews: true` and retire this job — a real second reviewer is strictly better than a self-attestation, and this mechanism only exists because a single-account repo has no other way to get trust-core changes reviewed by anyone but the person who wrote them.

**Amendment (2026-08-02):** The `TRUST-CORE REVIEWED` line must be added by the human maintainer only — Claude Code must never add it, including when explicitly asked to in-session, and must decline and explain why if asked. The line is a factual claim that a human read the trust-core diff; having the AI agent add it — even at the maintainer's explicit request, even with full context on the change — makes the claim false and defeats the entire point of the mechanism (ADR-012 exists specifically because self-certification isn't a real review). **Honest record:** this had already happened once before the amendment — Claude Code added the attestation line to PR #27 at the maintainer's explicit request, before this constraint was written down. That PR shipped durable storage (issue #6) and was reviewed in substance across the session that produced it, but the line itself was not maintainer-added, which is exactly the gap this amendment closes. No further exceptions from here forward.

## ADR-013 — One shared type contract for what extraction produces and the UI consumes

**Date:** 2026-08-02
**Context:** Before any interview/org-chart UI gets built in `apps/web`, extraction's output shapes (`packages/agents/extraction/src/types.ts`) and whatever the UI would need were on a collision course: nothing stopped a future screen from defining its own local `OrgChart`/`Agent`/`Task` shape that happened to look similar but drifted the moment either side changed independently — exactly the kind of duplicated business logic Phase B's build rules (docs/TRACKING.md) already forbid for screens, just one level up, at the data-shape level instead of the logic level. Building the actual role-card/org-chart UI (Stage 2, docs/product/userflow-v2.md) also surfaced gaps the existing extraction types never had to answer: userflow-v2.md names each agent ("Alex · CFO", "Priya · Invoicing") and gives each a Brain recommendation with a plain-language reason — neither a `name` nor a `brain` field existed anywhere before this ADR, and the temptation for whoever builds that screen next would be to invent placeholder values for both directly in the UI rather than waiting on the engine.
**Decision:** `packages/agents/contracts` (`@byok/contracts`) is the single source of truth for `OrgChart`, `Team`, `Agent`, `Task`, `Charter`, and `InterviewQuestion` (plus their supporting shapes — `TemplateSelection`, `ApiCallUsage`, `CustomizationLog`, `OnboardingBatch`, `SimulatedDayCard`, `InterviewAnswers`, `BrainRecommendation`). It has no runtime dependencies beyond `@byok/templates` (the primitive `Tier`/`TeamHint`/`Frequency`/etc. enums) — deliberately not a dependency of `packages/agents/extraction`'s `@anthropic-ai/sdk`/`commander`/`dotenv`, so `apps/web` can import types from it without pulling in an LLM SDK it will never call directly. `packages/agents/extraction` consumes and re-exports these types rather than redefining them; `apps/web` will do the same once it builds the interview/org-chart screens. A UI screen that needs a field the engine doesn't emit is a signal to add that field to the engine (`assembleOrgChart` or the onboarding-batch generation), not to invent it in `@byok/contracts` or in the UI itself — the contract only describes what extraction actually produces, never what a screen wishes it produced. Two fields are deliberately `null`/empty rather than fabricated to satisfy this ADR on paper: `Agent.brain` is always `null` (no per-role Brain-recommendation logic exists yet — which provider, and why, is a real product decision nobody has made), and the branch-question mechanism on `InterviewQuestion` (`appliesToTemplates`) has zero entries (no template has a real follow-up question designed yet). Both are complete, honest states, not stubs — the alternative (a fake recommendation or an invented question) would be worse than the gap it's covering. `Agent.name` is the one new field this ADR *does* populate for real: assembled deterministically from a curated name bank in `assemble.ts` (no LLM call — this is a synchronous assembly step, and every agent needs a name whether or not the budget-gated onboarding-batch call happens to run), and the onboarding-batch generation now sources its digest cards' names from that same canonical value instead of letting the model reinvent one, closing a latent inconsistency (userflow-v2.md: "Names flow through everything downstream").

**Amendment (2026-08-03):** The `appliesToTemplates`-filtered `InterviewQuestion` mechanism described above (a flat catalog in `@byok/contracts`, tagged with which templates a question applies to) is superseded by STEP 5's real branch-question content: each `BusinessTemplate` (`packages/templates`) now declares its own `branchQuestions: InterviewQuestion[]` directly, since the questions are genuinely template-specific data, not a shared catalog filtered after the fact. This required moving the primitive enum types (`Tier`, `TeamHint`, `Frequency`, `Stakes`, `AutonomyDefault`, `HandsScope`, `BusinessTemplateId`) out of `packages/templates` and into `@byok/contracts`, so `packages/templates` could depend on `@byok/contracts` (for `InterviewQuestion`) without creating a cycle — `@byok/contracts` no longer depends on `@byok/templates` at all as of this change. See ADR-015 for the rest of STEP 5's schema and persistence decisions.

## ADR-014 — The platform-key onboarding batch is gated by the cost gate directly, not routed through `Router.submitTask`

**Date:** 2026-08-03
**Context:** STEP 5 needed extraction (`packages/agents/extraction`) to "run through the router... cost cap enforced via the cost gate" — but `apps/router`'s `Router`/`AgentExecutor` model is built for one task in, one text result out (per `ExecutionOutcome = { result: string; costUsd?: number } | { error: string }`), while extraction is a self-contained pipeline of up to three sequential Claude tool-use calls (customize → category-validate → onboarding-batch), each needing structured (not plain-text) output, and already has its own working fail-closed cost guard (`packages/agents/extraction/src/costGuard.ts`'s `guardEstimatedCost`/`actualCostUsd`, checked before and after every individual call). Making each of those three calls flow through `Router` + `OpenMultiAgentExecutor` individually would require building a new tool-use-capable executor (the current one only returns plain text) and a `BrainKeyProvider` adapter resolving the flat platform `.env` key through the vault's per-role key interface — neither exists, and both are real, separate engineering, not a same-PR add-on to an already-large UI step.

A first design wrapped the whole batch as one `Router.submitTask()` call instead, avoiding the tool-use problem — but `Router.submitTask` unconditionally routes every successful result through the `ApprovalQueue` when one is attached (`apps/router/src/router.ts`), and ADR-008's production guard requires an `ApprovalQueue` to be attached at all. That coupling exists for real agent ACTIONS with a potential real-world `effect` a human might need to review before it happens — approve, reject, modify. Extraction has no effect: it produces a document (the org chart) the user reviews directly in the UI, with no approve/reject concept at all. Routing it through `submitTask` would have queued every signup's org chart for "human approval" in production, which is not what the approval queue is for, and isn't fixable by simply omitting an `effect` (a no-effect `ProposedAction` still queues by default, per the approval-queue's own tests — it just doesn't dispatch anything on approval).
**Decision:** `apps/api/src/extraction/runExtractionBatch.ts` gates and settles the batch directly against `CostGate.evaluateAndReserve`/`settle`/`release` — the same real pre-flight ceiling reservation (checked against company/role/task-type ceilings) and real settlement with the batch's actual total cost (`chart.meta.costUsd`) any router-routed task would get — without going through `Router.submitTask`'s approval-queue coupling. It appends directly to the same `TaskLedger` instance the Router wraps (now exposed on `TrustCoreDeps.ledger` for exactly this reason) at each state transition (pending → in_progress → completed/failed/queued/skipped), so the batch has the same visibility in the ledger a submitTask-routed task would have. Extraction's own per-call `guardEstimatedCost`/`actualCostUsd` keeps running unchanged *inside* the batch, as a second, finer-grained safety net the outer reservation doesn't replace. This satisfies "cost cap enforced via the cost gate" for the platform-key onboarding batch specifically, using the router's real infrastructure (its cost gate, its ledger) without forcing it through a state machine built for a different kind of task. It does not generalize to per-role ongoing agent work on a user's own BYOK key, where each action DOES have a real effect and genuinely needs `Router.submitTask`'s full gate → executor → approval-queue path with structured output — that's real, separate scope, tracked in issue #37 and required before MVP-1's "one role executing end-to-end on user keys" (issue #19) can be built.

## ADR-015 — The org chart is persisted against the signed-up user, not a tenant, until the Charter handoff

**Date:** 2026-08-03
**Context:** STEP 5's idea → interview → extraction → org-chart-reveal flow runs entirely before STEP 3's org-creation step (`/onboarding`, "name your company") — nothing in STEP 5's scope mentions company naming, and folding it in would rework an already-shipped flow for no requirement STEP 5 actually has. But the extraction batch is real, capped platform spend (ADR-003) that needs to be persisted for real CAC measurement "from signup one" — including users who see their org chart and never create an org at all, which a tenant-keyed record couldn't capture (there'd be no tenant yet to key it to). `packages/db`'s existing RLS isolation (`withTenantScope`, `app.tenant_id`) doesn't apply here for the same reason: there's no tenant.
**Decision:** A new `signup_extraction_batches` table is keyed to `user_id` (Better Auth's `user.id`, already synced into this project's own `users` table per STEP 3), not `tenant_id`. It gets its own `FORCE ROW LEVEL SECURITY` policy scoped on `current_setting('app.user_id')`, and a `withUserScope` helper (`packages/db`) that mirrors `withTenantScope`'s pattern exactly, set before any query against this table — the same defense-in-depth discipline the tenant-scoped tables already get, just keyed differently, rather than relying on application-code `WHERE user_id = ?` filtering alone. This intentionally leaves a gap: nothing currently moves a completed org chart from "belongs to a user" into a tenant's scope. That gap is deliberate, not unowned — issue #38 assigns it to the Charter handoff step (issue #16), the point userflow-v2.md itself calls "the second the company is live," which is the correct moment for an org chart to actually become a tenant's data.

## ADR-016 — apps/web's jsxDEV-in-production bug, and how it was actually fixed (STEP 6)

**Date:** 2026-08-03
**Context:** Live staging verification of STEP 5 caught a real production outage: `apps/web`'s pinned `nitro` (`3.0.260610-beta`, a date-versioned nightly channel, not a semver prerelease of any numbered release), paired with `vite@8.2.0` and `@vitejs/plugin-react@6.0.5`, produces an SSR (and client) bundle that calls `jsxDEV` — React's development-only JSX factory — in production, crashing every page that actually renders (not just an early-redirect route) with `TypeError: jsxDEV is not a function`. This wasn't caught by any earlier deploy because every prior Vercel build had been reusing a much older, never-fully-reconciled `node_modules` (via `npm install`'s incremental reuse of Vercel's build cache) that predated whatever pull introduced the bug — confirmed directly: a full, lockfile-accurate install (`--force` with no cache, then `npm ci`) reproduced the broken bundle byte-for-byte every time, while the stale cached install kept producing a correct one.

Two attempts to fix this by moving off the toolchain's beta channel were tried and reverted, both for good reason, not abandoned for convenience:
1. **`nitro@3.0.0`** (its only tagged non-prerelease 3.x release) requires `vite@^7`, so `vite` moved to `7.3.6` to match — the only mutually-compatible stable pair. `@tanstack/react-start`'s own peer dependency is `vite: ">=7.0.0"` (confirmed by inspection, not `>=8`), so this wasn't fighting the framework's own requirement. Locally this produced a clean build with zero `jsxDEV` references anywhere. But live on Vercel, the deployed site stopped crashing and instead went **silently non-interactive** — typing in the idea box never revealed the submit button, clicking "Sign in" did nothing, zero console errors. Confirmed the client bundle still called `e.jsxDEV(...)` directly even under this pairing — the toolchain swap hadn't actually eliminated the underlying symptom, just stopped it from crashing while breaking hydration instead. Worse than the bug it was meant to fix.
2. **`@vitejs/plugin-react@4.7.0`** (the last release before the plugin's move to an experimental oxc/Rolldown-based JSX transform — the one variable present, unchanged, across both the crash and the silent-hydration-break) doesn't even resolve: its peer range tops out at `vite@^7.0.0`, conflicting with `vite@8.2.0` (`ERESOLVE`, no install possible without `--legacy-peer-deps`, which was explicitly not authorized).

**Interim decision (STEP 5):** Revert to the original pins (`nitro@3.0.260610-beta`, `vite@8.2.0`, `@vitejs/plugin-react@6.0.5`) — the last combination confirmed to actually render and respond to input on staging. `.github/workflows/deploy-staging.yml`'s `vercel deploy` step does **not** pass `--force`: discarding Vercel's build cache forces the full, lockfile-accurate install that reliably reproduces the `jsxDEV` crash, so cache reuse was, at that point, load-bearing — an explicitly acknowledged fragility, not a hidden one. Tracked as issue #39.

**Actual fix (STEP 6):** Both prior attempts stayed within Nitro v3 (the package literally named `nitro`, imported as `nitro/vite`) and only varied its paired `vite`/`@vitejs/plugin-react` versions. The angle that actually worked was different: Nitro v3 is still on a date-versioned nightly channel with no numbered stable release past `3.0.0` (which itself doesn't support `vite@8`), and has multiple *independent* open upstream bugs against TanStack Start + Vercel unrelated to our specific symptom — [nitrojs/nitro#3905](https://github.com/nitrojs/nitro/issues/3905) (prerender failures), [nitrojs/nitro#3965](https://github.com/nitrojs/nitro/issues/3965) (wrong Node version), [vitejs/rolldown-vite#580](https://github.com/vitejs/rolldown-vite/issues/580) (unresponsive server on `vite@8` beta + Nitro v3 alpha — the same Vite-8-plus-Nitro-v3 pairing we were pinned to). TanStack Start still officially supports `@tanstack/nitro-v2-vite-plugin`, which wraps `nitropack@2.x` — the mature, long-stable Nitro line Nuxt and SolidStart have shipped on for years — as its pre-v3-migration path, not something deprecated away.

Swapped `nitro()` for `nitroV2Plugin({ preset: "vercel" })` (explicit preset — the v2 plugin doesn't advertise the v3 rewrite's Vercel-build-env auto-detection). `vite@8.2.0` and `@vitejs/plugin-react@6.0.5` stayed exactly as pinned (`nitro-v2-vite-plugin`'s peer is `vite: ">=7.0.0"`, no upper bound — installed clean, no `ERESOLVE`). Verified two independent ways: locally, zero `jsxDEV` calls anywhere in the compiled SSR entry (the one `jsxDEV` string match is React's own bundled `react-jsx-runtime.development.js` sitting in the function's `node_modules` — nitropack v2 treats `react` as an external dependency rather than inlining it, and Node's own `require()` resolves away from that file via `NODE_ENV` at runtime, same as any correctly-configured Node production deploy); live on staging, a real signed-up account was driven all the way through idea input → interview → real extraction → task list → org chart, with zero console errors and the compliance-locked banner rendering correctly. `--force` was **not** restored to the `vercel deploy` step even after this fix — a clean install is no longer known to break the build, but there's no reason to spend the cache-reuse safety margin now that the actual bug is gone; revisit only if a future, unrelated change needs cache-bypassing for its own sake.

One caveat carried forward, not fully resolved: `@tanstack/nitro-v2-vite-plugin` is documented as TanStack's pre-migration path, not the new-project default — it's the pragmatic, verified-stable choice today, not a claim that it's the long-term direction. Revisit if TanStack deprecates it outright, or once Nitro v3 ships a real stable release with confirmed Vercel + `vite@8` support.

## ADR-017 — The product is named Runwisely; BYOK is a concept, not the product name

**Date:** 2026-08-04
**Context:** The product shipped its first 20-tester pilot under the working title "BYOK Business Autopilot" — accurate as a description (bring-your-own-key, the whole point of the spend-wall architecture) but never actually the brand. Every user-visible surface (page title, hero copy, README, the product docs) still said "BYOK Business Autopilot" going into the pilot. Left alone, the acronym would keep drifting into places a real brand name belongs — new docs, new screens, new copy — just because it was the first thing typed into this repo, not because anyone decided it should be the name.
**Decision:** The product is named **Runwisely**. Renamed throughout every user-visible and prose surface: README title, all `docs/` prose (current and archived — `docs/archive/master-plan-v1.md`'s title changed too; an archive preserves the *strategy*, not a stale product name), ADR titles/headers where the literal product name appeared, the root `package.json` `"name"` field, the app's page `<title>` (`apps/web/src/routes/__root.tsx`) and hero copy (`apps/web/src/routes/index.tsx`), and the extraction CLI's `--help` description.

**What stays "BYOK," deliberately:**
- The **feature/mechanic** — bring-your-own-key, the three-spend-wall model, "BYOK Graduation" as a named onboarding stage — is still correctly called BYOK throughout the product docs (`userflow-v2.md`, `roles-and-api-key-guide.md`, `master-plan-v2.md`, `DECISIONS.md`). This is the concept the acronym actually describes; renaming it away would make those docs *less* accurate, not more on-brand.
- **BrainKey** / **HandsKey** (`packages/vault`) — the vault's own key-type names, unrelated to the product name.
- The internal `@byok/*` npm workspace package scope (`@byok/web`, `@byok/api`, `@byok/vault`, `@byok/contracts`, …) — **left unchanged, on purpose**. Renaming it means touching every import statement in every package across the monorepo (hundreds of call sites) for a label no user, tester, or anyone outside this codebase ever sees — it's private workspace-internal namespacing, never published, never rendered. The risk (this repo has already spent one full session recovering from a toolchain regression — see ADR-016) isn't worth it for a purely internal identifier. Revisit only if the scope is ever actually published or becomes externally visible.
- The GitHub repo name (`byok-business-autopilot`) — unchanged for the same reason renaming a repo breaks: existing clones, CI secrets scoped to the repo, issue/PR links, and the deploy pipeline's own references to it. The README now says so explicitly, pointing here.

**Why this won't drift back:** the distinction is now written down in exactly one place (here) instead of living only in whoever happened to remember it — "Runwisely" is the name on anything a user, tester, or investor reads; "BYOK" is the accurate technical description of one mechanic inside it, plus two internal-only legacy labels (the npm scope, the repo name) that are deliberately not part of the rename's scope.

## ADR-019 — The Dependency-audit gate suppresses specific, expiring, reasoned findings — it never lowers the severity floor or gets disabled

**Date:** 2026-08-08
**Context:** `.github/workflows/ci.yml`'s `dependency-audit` job ran a bare `npm audit --audit-level=high`, which fails the whole PR the moment any high-or-critical advisory exists anywhere in the dependency tree — including ones with no real fix available and no real exposure in this deployment. Investigating one such red check (docs/TRACKING.md's "two npm audit findings with no working fix" entry) found `@tanstack/react-start-plugin` is already on its newest published version (nothing to upgrade to — the advisory's own suggested fix is a downgrade that fixes nothing) and `esbuild`'s vulnerable copy is reachable only through a dev-only CLI tool that never starts the affected dev server. Both are real findings, correctly reported, and currently unfixable without a regression. Left as a bare `--audit-level=high` gate, PRs touching completely unrelated code (a docs-only PR, in this case) inherit a permanently red required check — which trains whoever's watching to stop reading it, so it catches nothing the day a real, fixable high-severity finding actually lands.
**Decision:** `.github/scripts/check-audit-allowlist.mjs` replaces the bare `npm audit` command in CI. It keeps `--audit-level=high` as the floor — moderate findings never fail this gate, same as before — but a high/critical finding only passes if its advisory (matched by GHSA id, extracted from `npm audit --json`'s `via` entries) is a reasoned, unexpired entry in the committed `.github/audit-allowlist.json`. Two independent failure conditions, enforced every run:
1. A high/critical finding whose advisory isn't in the allowlist (or is, but the entry is expired) — the build fails, full stop.
2. An allowlist entry itself past its own `expiresAt` — the build fails even if that advisory doesn't currently manifest as high/critical, forcing a periodic re-review rather than a suppression that quietly lives forever. Seeded at a 90-day expiry.

Suppressing a specific advisory ID with a reason and an expiry, by editing a committed JSON file that shows up in the PR diff, is the **only** sanctioned way to quiet this gate. Two things this is explicitly not a replacement for, and must never become one:
- **Never lower `--audit-level`.** Moderate-and-below findings staying non-blocking is an existing, separate decision (informational, reported, not gated) — the allowlist only governs the high/critical floor this ADR is about.
- **Never disable or skip the job.** An allowlist entry is a recorded, reasoned, time-boxed acceptance of one specific advisory; disabling the job accepts everything, forever, with no record of why.

Seeded with the two findings from docs/TRACKING.md's entry (`GHSA-9m65-766c-r333`, `GHSA-67mh-4wv8-2f99`), same reasons, `expiresAt: 2026-11-05`.

## ADR-020 — OAuth Hands credentials: structured storage, single-flight refresh, fail-closed to draft on any refresh failure

**Date:** 2026-08-12
**Context:** `HandsKeyRecord`'s `material` decrypted to an opaque secret handed straight to a Hands tool's `invoke()` — correct for a pasted static API key (Stripe, Square, ...), but Google Calendar/Meta connect (the two services picked from `docs/design/tool-registry.md` §2g's ranking) issue short-lived OAuth access tokens with a refresh token behind them. Building this generically, ahead of either provider integration, was a deliberate choice: sizing it against one concrete integration (Google Calendar, PR 2B) rather than two simultaneously, per the decision to sequence Calendar before Meta.

**Verifying before building surfaced a real, pre-existing gap, not just an OAuth-specific one.** `OpenMultiAgentExecutor`'s `missingHands` — the list `router.ts` uses to force `effect: undefined` (issue #22's draft-mode guarantee) — was populated **only** by the pre-flight `resolveHandsKeyId` filter, before the LLM's run even starts. A Hands tool connected at pre-flight (a key exists) but failing when the LLM actually calls it — a plain decrypt error, a key revoked mid-run, or now an OAuth refresh failure — reached `handsTool.ts`'s existing catch block (a clean `isError` tool result, so the run never crashed) but never reached `missingHands`. The router could therefore still submit the caller's original requested effect even though the Hands call never actually succeeded — the fail-closed-to-draft property held for "never connected" but not for "connected, then failed mid-run." This was always reachable (a mid-run revoke already exercised the same code path per `handsTool.ts`'s original comment), but OAuth token expiry turns it from a rare edge case into a routine, expected occurrence. **Fixed as a required change, not folded silently into the OAuth work**: `createHandsTool` (`apps/router/src/handsTool.ts`) takes an optional `onLiveFailure` callback, called on both existing failure branches (`!keyId` and a `decryptHandsKey` throw); `OpenMultiAgentExecutor` wires it to push into the same `missingHands` array the pre-flight filter already populates. `router.ts` itself needed zero changes — its existing `effect: task.missingHands ? undefined : input.effect` already treats both sources identically once they land in the same array.

**Decision:**
1. `HandsKeyRecord` gains `credentialKind: "opaque" | "oauth"`, set once at `storeHandsKey` time. `"opaque"` (the default, issue #22's existing pasted-key behavior) is completely unchanged. `"oauth"` means `material` decrypts to a JSON-serialized `OAuthCredential` (`{accessToken, refreshToken?, expiresAt?, scope?}`) — never a bare token string.
2. `decryptHandsKey` checks `expiresAt` (60s safety margin) for an `"oauth"` record. Not expired: returns a `SecretHandle` wrapping only `accessToken` — the decrypted JSON blob (which carries `refreshToken`) is `zeroBuffer`'d immediately after parsing, so a Hands tool's `invoke()` never sees anything but the access token, same shape as an opaque key today.
3. Expired: refreshed via a provider-registered `HandsCredentialRefresher` (one per Hands `service`, e.g. `"google-calendar"`) — the vault owns everything provider-independent; a refresher owns exactly one HTTP call to its provider's token endpoint. Re-encrypts and stores the new credential **in place** (same key id, same AAD scope-binding) — no caller holding that id needs to know a refresh happened.
4. **Fail-closed is structural, not just tested.** Every path through `performRefresh`/`getOrRefreshCredential` either returns a genuinely fresh credential or throws — there is no branch that returns a stale/expired `accessToken`. No expired credential ever silently reaches a Hands tool call.
   - No `refreshToken` on an expired credential → `HandsRefreshFailedError` immediately, refresher never called.
   - Refresh network/provider error → `HandsRefreshFailedError` (transient: the key stays connected, a later call may succeed).
   - Provider signals the refresh token itself is dead (`HandsRefreshTokenRevokedError`) → the stored key is revoked for real, through the same `revokeHandsKey` path (purge, audit, `key.revoked` event) a manual revoke uses — issue #22/#37's revoke-cancels-queued listener fires identically, rather than leaving a "connected" key that fails the same way forever.
   - A refresher call is bounded by `refreshTimeoutMs` (`withTimeout`, default 10s) — a hanging provider call rejects on schedule instead of hanging the caller.
   - A single attempt, no internal retry loop — a transient failure surfaces immediately rather than this method hammering the provider's token endpoint.
5. **Single-flight refresh per key id**, via an `inFlightRefreshes: Map<keyId, Promise<OAuthCredential>>` — a second `decryptHandsKey` call for the same expiring key while a refresh is already running awaits the SAME promise rather than starting a second one.

**On whether the concurrency guard is defensive or fixes an observed bug — checked, not assumed:** it was scoped as insurance against a *future* orchestration-library change. Reading `@open-multi-agent/core`'s installed source (`node_modules/@open-multi-agent/core/dist/tool/executor.js`, `ToolExecutor.executeBatch`) took a few minutes and turned that into a **verified fact, not a hedge**: a turn's tool calls already run through `Promise.all` gated by a 4-way `Semaphore` (`options.maxConcurrency ?? 4`) — real, present, reachable concurrent tool execution, not a hypothetical. An LLM double-calling the same Hands tool within one turn (which does happen) can reach `decryptHandsKey` for the same key id twice before either finishes, today, with the library exactly as currently installed. The guard is still not a fix for an *observed* race in this system specifically — no bug report prompted it — but it is not speculative about the library's mechanics. (Separately, `ToolExecutor.runTool` calls each tool exactly once per dispatch with no internal retry of a failed call — the "retry loop" risk named in the build brief is about *our* refresh code needing to stay single-attempt, which it does, not about the library retrying failed tool calls itself.)

Test coverage: `packages/vault/src/vault.test.ts` — non-expired credential never triggers a refresh; expired credential refreshes and re-encrypts in place; all four fail-closed scenarios (no refresh token, generic refresh failure, network error, revoked refresh token) each end in a thrown error and no handle, with the revoked case additionally asserting the key becomes actually unreachable and the `key.revoked` event fires; a hanging refresher rejects on the bounded timeout; concurrent decrypts single-flight to exactly one refresher call; a failed single-flight attempt rejects every concurrent caller and still allows a later retry; the refreshed access token is still never `JSON.stringify`/`String()`-serializable. `apps/router/src/openMultiAgentExecutor.test.ts` — the `missingHands` gap itself, regression-tested directly: a Hands tool connected at pre-flight but failing on the actual call still lands in `missingHands`.

## ADR-021 — Google Calendar OAuth connect: HMAC state (not server-side storage), platform client secret in env config, code-complete pending only a real domain

**Date:** 2026-08-12
**Context:** ADR-020 built the generic OAuth-credential refresh infrastructure without wiring a real provider. PR 2B wires the first one — Google Calendar, §2g's top-ranked build target — end to end: `apps/api`'s `/hands-oauth/:service/start` and `/hands-oauth/:service/callback` routes, `packages/templates`'s `handsAuth.ts` giving Calendar's badge a real connect affordance instead of the honest-pending message, and a `HandsCredentialRefresher` registered into Vault. Google's own app verification (`docs/design/google-oauth-verification-checklist.md`) requires a real public homepage and a same-domain privacy policy this product doesn't have yet — the code had to be complete and correct without either existing.

**Decision:**

1. **CSRF state is a self-contained, HMAC-signed token — no server-side storage.** `apps/api/src/oauth/state.ts` signs `{tenantId, subAgentId, capabilityScope, service, nonce, issuedAt}` with `BETTER_AUTH_SECRET` (domain-separated via a distinct HMAC context string, `"hands-oauth-state:v1"`, so a token valid for one purpose is never mistakable for the other) and verifies signature + a 10-minute expiry on the way back. Rejected a server-side nonce table: the callback route deliberately doesn't hold a Postgres connection open (next point), so there's no natural transactional place to store one, and a signed token survives a multi-replica deployment for free. Reuses the existing required secret rather than adding a new required env var — one more thing that doesn't need to exist before this is otherwise ready.
2. **The callback route is NOT behind `tenantMiddleware`.** Every other `/me/*` route wraps its full request in `withTenantScope` — a live Postgres connection held for the request's duration. The callback's own body is a server-side HTTP round-trip to Google's token endpoint; holding a pooled DB connection open across an external network call for the whole exchange is exactly the kind of thing to avoid, and `storeHandsKey` doesn't touch the SQL pool at all in this deployment (Vault is KMS/in-memory, see `devTrustCore.ts`). Session is still checked directly (`auth.api.getSession`, the same call `tenantMiddleware` makes internally) and cross-checked against the state's embedded `tenantId` — defense in depth: the signed state alone proves the request traces back to a `/start` call this server issued, but the live-session cross-check means a leaked or replayed state link can't be completed from a different signed-in tenant either.
3. **Platform client ID/secret live in `readServerConfigFromEnv`'s env config, never the vault** (ADR-003's pattern — the onboarding Anthropic key — extended to a second platform credential). Unlike every other field there, `google` is **optional**: `GOOGLE_OAUTH_CLIENT_ID`/`GOOGLE_OAUTH_CLIENT_SECRET` unset resolves to `google: null`, and the server boots fine either way — `/hands-oauth/google-calendar/start` just 404s with "isn't connectable yet" instead of the whole process refusing to start. This is deliberate, not a shortcut: these two values genuinely don't exist yet (Google's app isn't registered, verification hasn't started), and a `readServerConfigFromEnv`-style hard requirement would mean staging can't boot at all until they do.
4. **Fail-closed, no partial connect, matching ADR-020's property exactly**: every failure path (provider declines consent, invalid/expired/mismatched state, failed code exchange, a vault store failure) redirects with `?handsOAuth=error&reason=...` and stores nothing — `storeHandsKey` either writes one complete `credentialKind: "oauth"` record or the callback never calls it at all. There is no code path that writes a placeholder or half-populated credential.
5. **The only remaining step once real credentials exist is two `railway variable set` lines in `deploy-staging.yml`** — deliberately not added in this PR. `.github/workflows/` is CODEOWNERS-locked (trust-core-adjacent per its own header comment), and there's nothing real to set yet (no domain, no verified app, no client secret) — adding placeholder/empty values now would just be a second edit to make later for no benefit today. This is the literal answer to "build it so the only thing standing between it and working is the domain, not more code": the code merges as-is; the domain unlocks Google's verification; verification produces the two secret values; those two `railway variable set` lines (one PR, needing attestation because of the file they touch, not because of what they do) are the entire remaining task.

**Scope note, recorded rather than silently absorbed:** `handsAuth.ts`'s `Calendar` label covers both Google Calendar and Outlook Calendar per `tool-registry.md` §2b — this PR wires Google specifically (§2g's ranked recommendation), so a business on Microsoft 365 sees the same "Connect" button and completes a Google OAuth flow regardless of which calendar they actually use. Same category of imprecision as the existing `Shopify/Etsy` and `Resend/ConvertKit` combined-label entries — flagged in `handsAuth.ts`'s own comment, not solved here; the label would need to split by underlying service for a real fix.

## ADR-022 — Migrations run on every boot, not just on a tagged staging deploy; a second, independent schema-currency check backs it up

**Date:** 2026-08-12
**Context:** Staging's extraction pipeline returned a raw 500 (`column "tenant_id" does not exist`) for every real signup. Root cause, confirmed by reading the failing code path directly (`SignupExtractionBatchStore.start()`'s `RETURNING` clause references `tenant_id`, added by migration `0006`) and by querying staging's live schema (`signup_extraction_batches` had no `tenant_id`, `tenants` had no `monthly_ceiling_usd` — migration `0007`): **migrations hadn't run against staging since `v0.6.13-staging` (2026-08-08)**, confirmed via `git tag`. Everything since — eleven merged PRs, including both migrations this broke on — deployed fine, because Railway's own GitHub integration auto-redeploys `@byok/api`'s *code* on every push to `main` regardless (`railway.json`'s `startCommand` is just `npm run start`, no migration step), while the *schema* only advances inside `deploy-staging.yml`'s migration step, which only runs on a manually-pushed `v*.*.*-staging` tag. Nobody had pushed one in four days. The two deploy paths had quietly decoupled, and nothing surfaced that until a real request hit the gap.

**Decision: both (a) and (b), not either alone.**

1. **(a) — migrations run on every boot.** `apps/api/src/start.ts` and `dev.ts` now call `runMigrations(pool)` before `startServer(...)`, unconditionally, every process start — staging, and local dev. This removes the drift at the source: code and schema can no longer ship on different schedules, because they now ship on the same boot.
2. **(b) — a second, independent schema-currency check.** `verifySchemaCurrent(pool)` runs immediately after, as its own call, not folded into `runMigrations`. Deliberately redundant with (a): the point is to still catch drift if some future change to `start.ts` accidentally drops the `runMigrations` line but leaves this one, or if a not-yet-imagined deploy path never calls either. It checks a small, hand-maintained canary list (`SCHEMA_CANARIES` in `migrate.ts`) — one `{table, column, addedBy}` entry per migration that adds a column via `ALTER TABLE ... ADD COLUMN` — against `information_schema.columns`, and throws `SchemaDriftError` naming exactly what's missing and which migration adds it. Canaries are scoped to *column-adding* migrations specifically, not every migration: a `CREATE TABLE IF NOT EXISTS` migration against a database that's never seen it either creates the whole table or is a complete no-op — there's no way to end up silently half-missing a table the way a skipped `ADD COLUMN` silently leaves a column absent from an already-existing table. That asymmetry is exactly what let this incident happen invisibly for four days.

Both failures now happen the way ADR-007/008's guards already work in this codebase: the process refuses to start and crashes loudly on boot, rather than starting cleanly and serving a raw Postgres error to the first real user who hits the gap.

**On whether (a) is risky here — checked, not assumed, per the explicit ask:**
- **Long migrations blocking boot** — not a real risk *today*: all seven migration files are pure DDL (574 lines total, no data backfills — confirmed by reading every file), sub-second to apply. It's a real risk for the *pattern* going forward, though: once migrations run at boot, a future migration that does a heavy backfill on a large table would block every subsequent boot until it finishes, which could exceed Railway's ~2-minute healthcheck window and look like a failed deploy. Noted as a convention to carry forward, not fixed here since nothing today triggers it: a future slow migration should ship as an additive, backward-compatible step (add a nullable column, backfill via a separate background job, tighten the constraint in a later migration) rather than one blocking `ALTER`.
- **Concurrent replicas racing the same migration** — genuinely low today (every environment runs `replicas: { configured: 1 }`, confirmed via `railway service list --json`), but not zero risk in the code *pattern* if that ever changes without anyone revisiting this file. Most of this repo's migration statements tolerate a race fine — Postgres's own `CREATE TABLE IF NOT EXISTS` is race-safe. The one pattern that isn't: `DROP POLICY IF EXISTS` immediately followed by `CREATE POLICY`, used throughout for RLS (Ring 1 tenant isolation). Two replicas interleaving those two statements could leave a real, if narrow, window where a tenant-isolation policy is dropped but not yet recreated. Rather than accept that as a someday-problem, `runMigrations` now wraps the whole run in a Postgres advisory lock (`pg_advisory_lock`/`pg_advisory_unlock`, session-scoped, auto-released if the holding connection dies) — cheap insurance now, and it means scaling replicas later never requires remembering to come back and add this.

**Test coverage:** `packages/db/src/migrate.test.ts` — the advisory lock brackets every migration call and releases even when a migration throws (never left held on a crashed run); `verifySchemaCurrent` resolves cleanly when canaries are present, throws `SchemaDriftError` naming the exact missing column and its source migration when they're not, and reports every missing canary at once rather than just the first.

**Verified against the real incident, not just unit tests:** pushed `v0.6.14-staging`, watched `deploy-staging.yml`'s migration step succeed, then independently re-queried staging's live schema directly (not just trusted the green checkmark) — `tenant_id` and `monthly_ceiling_usd` both present. Drove a full real signup through interview → extraction → org chart → feedback on staging afterward; extraction completed with a real, idea-specific org chart and no error.

## ADR-023 — Template selection: structured interview answers are the primary signal, idea-text keywords are secondary

**Date:** 2026-08-13

**Context:** A real end-to-end run of "a subscription-based meal prep company in Vancouver" got routed to the `saas` template — a Build Agent proposing code via GitHub, a QA/smoke-test agent, a Deploy Coordinator — because `"subscription"` was a `saas` keyword in `templateSelect.ts`, despite the founder's payment model already being captured correctly by the structured `howMoneyArrives` field. `customization.added` came back empty: the customize pass had nothing structurally wrong to fix, since nothing in the *scaffold itself* pointed at food/kitchen/delivery at all — it just relabelled software-product task text with food-adjacent phrasing. A controlled comparison (a real barbershop run, the existing `saas-scheduler` fixture, `mortgage-brokerage` naming real regulators — BCFSA, FINTRAC — by name) confirmed the customize pass itself was not the problem: when template selection is right, it already does genuine, specific, structural work. The bug was entirely upstream, in a keyword table that let one generic word decide a business's entire vertical.

**A full keyword audit** (all six templates, every keyword, checked against "does this describe a business TYPE or a business MODEL/maturity/payment-structure") found this wasn't an isolated word: `saas`'s `"startup"` (maturity, not a vertical), `physical-space`'s `"membership"`/`"rental"`/`"booking"` (payment/access model, not a space type), `ecommerce`'s `"marketplace"` (ambiguous between "sells via a marketplace" and "is a marketplace platform"), and a separate but related flaw — `service`'s own `"service"`/`"services"` keywords are so generic ("meal-prep *service*," "subscription *service*") they function as noise, not signal. Also found: a `stage === "nothing-yet"` bonus wired to `saas` specifically — the exact same category of bug applied to a non-keyword signal (a brand-new *anything* nudged toward "software").

**Decision:**
1. **Structured answers are now the primary signal, weighted above keywords, not the other way around.** `howDeliveryReaches`/`howMoneyArrives`/`whoTheCustomerIs` each carry a per-template bonus (weight 3) that a single stray keyword hit (weight 1) can no longer outweigh. `howMoneyArrives` deliberately contributes **no** template-specific bonus at all — payment model doesn't predict business type, so encoding it as a signal for any one vertical would just be relocating the same bug, not fixing it.
2. **Every business-model/maturity keyword found in the audit was removed** from the keyword tables (`startup`, `membership`/`memberships`, `rental`/`rentals`/`equipment rental`, `booking`/`bookings`, `marketplace`, `platform`, `tool`, `build`, `service`/`services`). Verified via a regression check against all 8 real fixtures (the original 6 plus new barbershop and meal-prep ones — see below): zero change in outcome for any already-correctly-routed idea.
3. **A confidence signal**, surfaced on every `TemplateSelection` (`confidence: "high" | "low"`) and logged unconditionally when low — the top-two-scores-close case (the pre-existing makerspace/wedding-photographer "known limitation" and the meal-prep incident are the same shape: a genuinely ambiguous idea, silently resolved by an arbitrary tiebreak instead of being flagged). Two regressions were introduced and caught by this same process while wiring the structured-signal bonuses (a blanket `howDeliveryReaches: "shipped"` bonus that outweighed food-hospitality's own keywords and re-broke the meal-prep case a different way; a blanket `"in-person"` bonus that tied a wedding photographer against a food-specific category with zero food-keyword backing on either side) — both fixed before merge, both now covered by `templateSelect.test.ts`.
4. **When confidence is low, the founder is asked directly** instead of the system guessing silently: `interviewQuestions.ts`'s `buildDisambiguationQuestion` injects a real interview question (top two candidate templates, by name/description) in place of branch questions until it's answered. Requires no new UI — it's rendered by the same generic single-select question path every other interview question already uses, and the answer flows through the same `branchAnswers` bucketing `InterviewScreen.tsx` already does for any non-spine/non-context question id. `selectTemplate` treats an explicit `branchAnswers.templateDisambiguation` as an unconditional override, ahead of any score.
5. **A seventh template, `food-hospitality`**, was added — same depth as the other six (20 tasks, 3 branch questions, a real food-safety compliance task with `requiresProfessionalVerification: true`) — rather than leaving food/meal businesses to blend awkwardly across `local` and `service` (which, even once correctly routed there, pulled in `service`'s B2B sales-pipeline tasks — lead qualifier, outreach drafter — a poor fit for a consumer subscription business).
6. **`meal-prep-subscription.json` and `barbershop.json` are now permanent fixtures** in `test/fixtures/` (run automatically by `test/run-differentiation.ts`, no code change needed to include them going forward) — this exact regression class cannot silently return unnoticed.

**Verified against a real re-run, not just the regression check:** meal-prep now resolves to `food-hospitality` alone, confidently (score 3 vs. the next-best's 2, no blend) — the real customize pass added a BC food-safety/labelling compliance task, delivery-zone routing, cold-chain packaging inventory, subscription pause/churn handling, and a subscriber onboarding sequence; removed B2B invoicing as a poor fit for a pure consumer subscription. Zero software-product agents, zero B2B sales-pipeline agents — the two failure modes this ADR exists to close.

## ADR-024 — R2: the Charter becomes a versioned entity, and its prompt cascade is generated deterministically, never by an LLM

**Date:** 2026-08-13

**Context:** `docs/architecture/automation-runtime-plan.md` §2 describes R2 — the Charter compiler, editor, handoff ceremony, and three-tier prompt cascade (CEO / role-lead / sub-agent) — as the layer that turns an assembled org chart into something that actually runs. Before this ADR: a Charter *draft* already existed (`packages/agents/contracts/src/charter.ts`'s `Charter` interface, generated by the extraction pipeline's onboarding-batch call, issue #4) but was purely illustrative — never versioned, never tenant-owned, embedded only as JSON inside `signup_extraction_batches.org_chart`, with no state machine and no path to becoming the thing a prompt cascade could install from. Nothing composed a system prompt for any agent at all: `apps/router`'s `RouterTask`/`RouterTaskInput` had no prompt field, and `OpenMultiAgentExecutor` never populated `runAgent`'s (already-supported, just-unused) `systemPrompt` option.

**A citation error in the plan doc, caught before writing any code:** §2 attributed the "immutable role prompts... composed by the router per dispatch" rule to "ADR-011." ADR-011 (above) is about interview-question design (value-chain vs. founder-preference questions) and has nothing to do with prompts — full-text search of this file confirms zero occurrences of "prompt" or "immutable" outside this ADR. The actual rule lives in `docs/architecture/security-architecture.md` §4 (Ring 2: "Own system prompt (immutable per dispatch)") and §5.1 ("the agent's system prompt is composed by the router per dispatch from the versioned Charter + role definition; nothing an agent reads can modify it"). Similarly, "T10" (the CEO-recommender-only rule) is named directly in `security-architecture.md`'s threat table, not as a DECISIONS.md ADR label — the ADR that actually establishes it is **ADR-004** ("CEO agent is a recommender by architecture"), which the approval-queue package already enforces structurally: `RecommendationItem` has no `effect` field at all (not even `undefined`), and `submitRecommendation` throws if one is smuggled in via `as any`. The plan doc's citation is corrected in place (§2) to point at the real sources instead of silently leaving a wrong pointer for the next person who goes looking.

**What already existed vs. what R2 actually needed to add** — checked before designing, not assumed:
- The draft `Charter` shape covered `sharpenedIdea`, `mvpDefinition`, a bare `roleTasks: {roleTitle, tasks}[]` list, `monthOneGoals`, and a `budgetCeilingPlaceholder` — explicitly documented as a placeholder string ("you'll set a real ceiling when you connect your keys") because the interview never collects a budget figure.
- Missing: **role mandates** (an authority/scope statement per role, not just its task list), a **real numeric budget ceiling**, a **state machine** (draft → active → superseded, versioned, tenant-owned), and the **entire prompt cascade** — none of which existed anywhere.

**Decision:**

1. **Charter compiler — the mandate/ceiling split.** `roleTasks` is renamed `roleMandates`, gaining a `mandate: string` field per role, generated by the SAME haiku `generate_onboarding_batch` tool call the draft already used — a wider JSON schema on an existing call, not a new one. `budgetCeilingUsd` is no longer LLM-generated at all: the interview doesn't collect a budget figure, so asking the model to invent a dollar amount would produce a number disconnected from what actually gets enforced. It's resolved deterministically in code, post-call, to the exact same default the cost gate itself uses (`apps/api/src/routes/ceiling.ts`'s `DEFAULT_MONTHLY_CEILING_USD = 50`, duplicated as `packages/agents/extraction/src/onboardingBatch.ts`'s `DEFAULT_CHARTER_BUDGET_CEILING_USD` — extraction can't import from `apps/api`, ADR-015's ordering — kept in sync by comment cross-reference, not a shared import). **Measured cost delta: effectively zero.** Re-running the real 8-fixture differentiation suite before/after (see `test/results/differentiation-report.md`'s existing baseline, `$0.0348–0.0411/signup`) showed the mandate field adds a few dozen output tokens per role to an already-running haiku call — the ceiling computation costs nothing (pure code, no model call). No new LLM call was added anywhere in the batch.

2. **The versioned, tenant-owned Charter — a new entity, not a repurposed one.** `CompanyCharter` (new type, `packages/agents/contracts/src/charter.ts`) wraps `Charter` content with `id`, `tenantId`, `version`, `status: "draft" | "active" | "superseded"`, `cascade`, `createdAt`, `installedAt`. Persisted in a new `company_charters` table (migration `0008`, standard tenant-RLS pattern), created at **Charter acceptance** — not draft time — matching `master-plan-v2.md` Stage 4's actual ceremony and ADR-015's assignment of the org-chart-to-tenant handoff to exactly this moment. A partial unique index (`WHERE status = 'active'`) enforces at most one active version per tenant; accepting a new version supersedes the old one in the same transaction. The pre-acceptance draft (`OnboardingBatch.charterDraft`) is untouched and still the seed for the first `CompanyCharterStore.createDraft` call — two different lifecycle stages of the same content shape, not two competing sources of truth.

3. **The prompt cascade is generated deterministically — explicitly NOT an LLM call.** `packages/agents/extraction/src/cascade.ts`'s `generateCascade(charter, chart, previous?)` builds the CEO/role-lead/sub-agent prompt text from the Charter's own content and the org chart's own data (team mandates, task text, tool scopes, autonomy status) — same input always produces the same output, zero cost, zero latency, and nothing for a prompt-injection attempt to influence (the cascade never reads anything an agent or a user's connected tool produced). Stored as one JSONB blob on the `company_charters` row (`cascade`), regenerated wholesale on Charter edit — never a separate per-prompt table, matching the org chart's own existing "one JSONB blob" persistence pattern (`signup_extraction_batches.org_chart`) rather than introducing the first first-class per-agent DB rows in this codebase for what's still a fully derived artifact.

4. **Override preservation, enforced in the generator itself, not by convention.** Every generated prompt (`CeoPrompt`/`RoleLeadPrompt`/`SubAgentPrompt`) carries `overridden: boolean`. `generateCascade`'s regeneration path checks each `previous` entry first — an `overridden: true` entry is returned verbatim, never regenerated, until a human explicitly resets it. Covered directly in `cascade.test.ts`: an overridden CEO prompt survives a Charter content edit that changes every other prompt.

5. **T10 enforced structurally in the router, in front of the approval queue — not merely by routing to a different queue method.** `RouterTaskInput`/`RouterTask` gain `promptTier: "ceo" | "role-lead" | "sub-agent"` (default `"sub-agent"`, so every pre-R2 caller is unaffected) and an optional `systemPrompt`, threaded into `OpenMultiAgentExecutor`'s `runAgent()` call — the first real consumer of the library's already-existing, previously-unused `systemPrompt` option. In `router.ts`: a `promptTier === "ceo"` task's effect is forced to `undefined` **before** the approval-queue branch is ever reached (independent of, and in addition to, `RecommendationItem`'s type-level inability to hold one) and is submitted via `approvalQueue.submitRecommendation(...)`, never `submitProposedAction`. Two independent layers refusing the same thing is deliberate — "no matter what its prompt becomes" (T10's own wording) means the guarantee can't depend on a caller remembering not to pass `effect` for a CEO-tier task. Covered in `router.approvalQueue.test.ts`: a CEO-tier task never reaches `submitProposedAction`, and an effect requested on a CEO-tier task never dispatches, even with a real effect executor wired up. The durable `router_tasks` table gains matching `prompt_tier`/`system_prompt` columns (migration `0009`, with a `SCHEMA_CANARIES` entry — this is an `ALTER TABLE ADD COLUMN`, exactly the class of migration ADR-022 exists to catch if it's ever skipped) so a durably-replayed idempotent task reconstructs the same `promptTier` its caller originally set, not a silently-wrong default.

6. **The handoff ceremony reuses the existing claim endpoint's design intent exactly as it was written.** `apps/api/src/routes/me.ts`'s `POST /claim-org-chart` comment already said, back when it was built: "structured as its own idempotent operation so the Charter-acceptance screen (#16) can call the exact same endpoint later without this route or its logic changing at all, just the caller." That held — `/claim-org-chart` is untouched. The new `POST /me/charter/draft/:id/accept` (`apps/api/src/routes/charter.ts`) calls `generateCascade` against the tenant's already-claimed org chart and installs the result. `apps/web`'s `OnboardingScreen.tsx` now navigates to the new `/charter` screen instead of straight to `/dashboard` once org creation + claim succeed — the Charter review/edit/accept screen (`CharterScreen.tsx`) is what now owns the final `/dashboard` navigation, once the ceremony completes.

7. **Known, deliberate scope gap — not fabricated as done.** The plan's cascade-regeneration triggers are "Charter edit, agent rename, or autonomy change." Only the first is wired end-to-end in R2: `generateCascade` is called (and correctly preserves overrides) whenever a Charter is accepted, including a re-accepted "reopened" edit. Post-claim agent rename and autonomy-change endpoints **do not exist yet** — `packages/db`'s PR #94 explicitly scoped org-chart editing (`reassemble`/`rename-agent`) to pre-claim only ("a post-claim revisit to `/org-chart` can view but not edit"), and no autonomy-grant endpoint exists in `apps/api` at all yet. `CompanyCharterStore.updateActiveCascade` exists and is ready to be called once those mutations exist — but nothing calls it yet, and this ADR says so plainly rather than wiring a call to a codepath that doesn't exist or silently claiming the trigger is complete. This is the same honesty standard ADR-013 set for `Agent.brain: null`: a documented, complete gap, not a stub dressed up as done.

**Verified:** full-monorepo typecheck; `templates:test`/`extraction:test`/`router:test`/`api:test`/`web:test` all green, including new coverage — `cascade.test.ts` (generation, per-tier correctness, override preservation, content-edit regeneration), `charter.test.ts` (draft creation/idempotency/reopen-seeding/edit/accept, all 404/409 paths), `router.approvalQueue.test.ts`'s three new T10 tests, `openMultiAgentExecutor.test.ts`'s two new systemPrompt-threading tests. No trust-core test was deleted or weakened to make this land.

## ADR-025 — R3: the scheduler ships cadence triggers only, reuses Router.submitTask entirely for dispatch, and the tier-floor naming is reconciled to what's actually shipped

**Date:** 2026-08-13

**Context:** `docs/architecture/automation-runtime-plan.md` §3(a)/§7/§8 describe R3 as the smallest useful subset of the scheduler: BullMQ repeatable jobs driven by R1's cadence metadata, per-tenant scheduling, a pre-flight cost-gate check on every scheduled dispatch, pause-on-exhaustion with a resumable record, cadence floors per tier baked into the data model from day one, and the §7 instrumentation meter built alongside the scheduler rather than retrofitted later.

**A real prerequisite gap, found before writing scheduler code, not assumed away.** R1 (ADR entry 2026-08-13, "R1: cadence metadata on every sub-agent template task") added `cadence`/`batchable`/`triggerType` to `TemplateTask` (`packages/templates`) — but never to the assembled `Task` the extraction pipeline actually persists and the API serves (`packages/agents/contracts/src/orgChart.ts`). Checked directly: `pipeline.ts`'s `templateTaskToTask` (`{...t, origin: "template"}`) happened to carry the data through at the JS-object level via spread, but `Task`'s TypeScript shape never declared the fields, so nothing could read them in a type-checked way — and the customize-added-task path (`addedTasks`, built from the customize LLM's own `CustomizeAddition` output) never had the data at all, since a customize-added task has no template to inherit from. A scheduler built on top of this would have had no real cadence data to schedule from. Fixed as part of this PR, not deferred:
1. `Task` (contracts) gains `cadence`/`batchable`/`triggerType`, matching `TemplateTask` exactly.
2. `packages/agents/extraction/src/scheduleMetadata.ts`'s `deriveScheduleMetadata(frequency, agentType)` derives the same three fields **deterministically** for customize-added tasks — no second LLM call — calibrated against R1's own keyword-based heuristics (triage/escalation → event; expense-shaped → nightly-batched; cashflow/forecast-shaped → weekly; tax-shaped → monthly; inventory/reorder-shaped → threshold; `adhoc` frequency → event; otherwise cadence maps 1:1 to frequency), matched on agentType *keywords* rather than exact template ids, since a customize-added task's agentType is idea-specific and won't literally match a template's.
3. Every existing `Task`-literal construction site across the repo (test fixtures, the reassemble edit-op's zod schema in `apps/api/src/routes/extraction.ts`, `apps/web`'s client-side "add a custom task" feature) updated to carry the new required fields — found exhaustively via `npm run typecheck`, not by guessing which call sites existed.

**The tier-floor naming had to be reconciled, not invented fresh.** Plan §7 names its cadence-floor tiers "Founder $29 / Operator $79 / Agency $199." Checked against the actual shipped product before building anything: `apps/web/src/lib/pricingConstants.ts`'s `PRICING_TIERS` — the single source of truth for the real `/pricing` page — names them **Solo / Company / Scale**, with `priceLabel: "—"` (no monthly price has been set by product yet, an explicit, honest placeholder already in that file). "Founder/Operator/Agency" appears nowhere else in this codebase's real pricing surface; `docs/product/roles-and-api-key-guide.md`'s one "FOUNDER/CEO" hit is the org-chart role, not a subscription tier. No `tenants.tier` column existed at all, and no tier-selection UI exists anywhere in the signup/onboarding flow.

**Decision on naming:** the plan's real INTENT — three tiers, cadence floor tightening from daily → hourly → 15min as the tier goes up — is preserved exactly; only the LABELS change, to the tiers this product actually ships (`solo`/`company`/`scale`). `tenants.tier` (migration `0010`) defaults to `'solo'` — the most conservative (slowest) floor, fail-closed, since nothing selects a tier yet and no pricing is finalized. `packages/jobs/src/cadenceFloors.ts`'s `CADENCE_FLOOR_BY_TIER` and its UI-facing clamp-reason string (`"Runs daily on Solo — hourly available on Company."`) both use the real names, so a future pricing-tier UI never has to translate between two competing naming schemes.

**Decision — scope and design, point by point:**

1. **Cadence floors, clamped at schedule time, not run time (plan §7 rule 1).** `clampCadenceToTierFloor(declared, tier)` is a pure function: a task's declared cadence faster than its tenant's tier floor is rewritten to the floor's cadence, with a visible reason, computed once when the schedule is synced — never silently re-evaluated or dropped per-firing. Soft run-caps (§7's 50/300/1000 runs/day) are **not** enforced in R3 — only measured, via the instrumentation meter below; the plan's own §7 instrumentation section frames the caps as *"modelled, not measured, and should be treated as a starting hypothesis"* that the meter exists to correct, which only makes sense if enforcement is a later, data-informed step, not this one. Not fabricated as done.

2. **The real BullMQ API turned out to be better than what the plan doc's own phrasing ("repeatable jobs") implied — corrected mid-build, not shipped wrong.** The installed `bullmq@6.0.5` exposes `upsertJobScheduler`/`getJobSchedulers`/`removeJobScheduler` (BullMQ's newer "Job Scheduler" API), not the older `add({repeat})`/`getRepeatableJobs`/`removeRepeatableByKey` API this file's first draft assumed by name-pattern-matching the plan's prose. Caught for real by `npm run typecheck` failing against the actual installed type definitions (`Queue` didn't structurally satisfy the first-draft `RepeatableQueueLike` interface) — not discovered by reading docs first, but the mismatch was root-caused against `node_modules/bullmq`'s real `.d.ts` before redesigning, not patched around. `upsertJobScheduler` does an atomic create-or-update in one call keyed by a caller-chosen id, which is a strictly better fit than the old API's separate add/list/remove-by-derived-key dance — `packages/jobs/src/tenantScheduler.ts`'s `syncTenantSchedule` is simpler than its first draft because of this, not more complex.

3. **`packages/jobs` stays generic; the trust-core-touching orchestration lives in `apps/api`.** Same split `apps/api/src/extraction/runExtractionBatch.ts` already established for extraction (ADR-014): the reusable primitive (cadence-floor math, BullMQ sync logic) has no dependency on `@byok/router`/`@byok/cost-gate`/`@byok/db` and is fully unit-testable without Redis or Postgres; `apps/api/src/scheduler/computeDesiredSchedule.ts` (pure — Charter + org chart + tier → desired jobs) and `scheduledDispatchProcessor.ts` (the actual worker body) are where the real dependencies get wired.

4. **The scheduled-dispatch worker's whole job is composing the right input for `Router.submitTask` — R2 already does everything else.** T10 enforcement, the cost gate, the approval queue: all of it is already correct in `Router.submitTask` (ADR-024). `scheduledDispatchProcessor.ts` looks up the tenant's active Charter cascade, resolves `promptTier` from the dispatching agent's team (`"founder"` → `"ceo"`, everything else → `"sub-agent"`), resolves the model via the exact same `TierModelMap` every other `Router.submitTask` caller uses (now threaded onto `TrustCoreDeps` — it was constructed inline in `devTrustCore.ts` before and never exposed), and calls `submitTask`. No new cost-gate call, no new approval-queue logic, no second T10 check — one path, already proven in R2.

5. **Pause-on-exhaustion reuses the pre-existing, previously-unwired `DurableBatchStore`/`paused_batches` mechanism (`packages/cost-gate`) — this PR is its first real caller.** Checked before building a second mechanism: `BatchExhaustionManager`/`PostgresDurableBatchStore` already existed, fully built and tested, for exactly this "pause, preserve what's needed to resume, resume later" shape — nothing in `apps/api` had ever constructed or called it. `Router.submitTask` returning `"queued"`/`"skipped"` is, today, unambiguous evidence of a cost-gate ceiling verdict (the only code path that produces those two statuses) — the worker treats either as exhaustion, pauses the tenant via a new `tenant_schedule_state` row (migration `0010`) pointing at a real `paused_batches` record, and every subsequent job firing for that tenant becomes a cheap no-op (checked before any Charter/org-chart lookup) until `POST /me/scheduler/resume` clears it. The underlying BullMQ Job Schedulers are never removed while paused — only the worker's own pause check short-circuits them — so resuming needs no re-sync to pick back up.

6. **The §7 instrumentation meter is built now, with the scheduler, exactly as instructed — including the two columns nothing calls yet.** `scheduler_instrumentation_daily` (migration `0010`) has `scheduled_runs_executed`/`worker_seconds_consumed`/`ledger_rows_written` (incremented for real by `scheduledDispatchProcessor.ts` on every firing) and `event_triggers_received`/`chain_steps_completed` (columns exist, `SchedulerInstrumentationStore.recordEventTrigger`/`recordChainStep` exist — R5/task chains and R6/event triggers are what will actually call them). `ledger_rows_written` mirrors `router.ts`'s own `ledger.append` call count for each code path exactly (2 for QUEUE/SKIP — pending + terminal, no in_progress; 3 for everything else) rather than a guessed constant. Zero rows with nonzero values in the two not-yet-wired columns is the honest current state.

7. **The worker runs in-process with the HTTP server, not as a separate deployable — a direct lesson from this repo's own incident record.** `docs/TRACKING.md`'s "Railway auto-detects workspace packages as deployable services" entry: an accidentally-auto-provisioned second Railway service crash-looped for days because it inherited the wrong start command. A dedicated worker process is a legitimate future scaling change; reaching for it now, in a repo that has already been burned once by an extra deployable appearing where only one was intended, isn't free just because it's the more conventionally "correct" shape. `REDIS_URL` — already wired through CI and `deploy-staging.yml`, already documented in `.env.example`, never previously consumed by any code — required, same discipline as `DATABASE_URL`.

8. **`packages/jobs/` added to CODEOWNERS**, same reasoning already on record for `packages/db/`: it went from a generic, unused BullMQ wrapper to the thing that decides when an unattended, spend-triggering dispatch fires and enforces the cadence-floor cost-safety limits — load-bearing for trust-core now, same review bar.

**Verified:** full-monorepo typecheck (including the real installed BullMQ types, not assumed ones); `templates:test`/`extraction:test`/`router:test`/`db:test`/`jobs:test`/`api:test` all green — new coverage includes `scheduleMetadata.test.ts` (every heuristic + the fixed-frequency fallback), `cadenceFloors.test.ts` (every tier boundary, including that Scale is never clamped), `tenantScheduler.test.ts` (add/remove/unchanged/cadence-change-triggers-re-upsert, and strict per-tenant isolation on a shared queue), `computeDesiredSchedule.test.ts`, `scheduledDispatchProcessor.test.ts` (cascade-prompt composition for both CEO and sub-agent tiers, the paused-tenant no-op, both ledger-row-count branches, both QUEUE/SKIP-triggers-pause branches, and both "no active Charter" / "stale agent or task id" failure modes), and `scheduler.test.ts` (the sync/status/resume routes, including the clamp-reason surfaced end to end).

## ADR-026 — Staging boots on durable CostGate/ApprovalQueue storage, not dev wiring; Router's ledger/dedup stay in-memory, tracked separately

**Date:** 2026-08-14

**Context:** Driving the real staging verification R3's own review demanded — a scheduled dispatch firing unattended, hitting the cost gate, landing in the approval queue, recording in `scheduler_instrumentation_daily` — surfaced that `apps/api/src/start.ts` (the staging entrypoint) had booted on `createDevTrustCore()` since before R3 existed. That wiring's own comment said so plainly and, at the time, correctly: staging's original job was proving auth → tenant → RLS-scoped API resolves end to end, "which never touches trust-core's `/tasks` route." R3 is the first thing that actually calls `Router.submitTask` unattended in that environment, and the claim stopped being true the moment it shipped — nobody revisited the wiring decision when the thing it was scoped around changed.

Concretely, under `createDevTrustCore`: `CostGate` was built on `InMemoryDurableReservationStore` — real per-tenant ceiling enforcement for the life of one process, reset on every restart. `ApprovalQueue` had **no durable storage at all** — `pending`/`pendingRecommendations` were plain in-memory `Map`s inside `packages/approval-queue/src/queue.ts` itself; `PostgresDurableApprovalStore` existed, fully built and exported, but nothing in the codebase ever constructed it. A scheduled dispatch landing in the approval queue was real within that process's lifetime but invisible to any query, any route, or the next redeploy — there was no way to durably prove "the task landed in the approval queue" no matter how long staging ran.

**Decision — what became durable:**

1. **CostGate's reservation store** — a clean swap, `InMemoryDurableReservationStore` → `PostgresReservationStore` (`packages/cost-gate/src/durable/reservationStore.ts`), same `DurableReservationStore` interface, already covered by a real-Postgres `.itest.ts` suite. No other change to `CostGate`'s construction.

2. **ApprovalQueue's pending-item storage** — not a swap, a real build: `ApprovalQueue` (`packages/approval-queue/src/queue.ts`) had no constructor slot for `DurableApprovalStore` at all before this. It gained a 4th constructor parameter, `store: DurableApprovalStore = new InMemoryDurableApprovalStore()`, and `submitProposedAction`/`resolve`/`submitRecommendation`/`resolveRecommendation`/`pendingActions`/`pendingRecommendationItems` now read and write through it instead of the local Maps, which are gone. This is a breaking API change — `resolve`, `resolveRecommendation`, `pendingActions`, and `pendingRecommendationItems` now take a leading `tenantId` (matching `DurableApprovalStore`'s own tenant-scoped, RLS-friendly shape, and every other durable store in this codebase), and `submitRecommendation`/`resolveRecommendation` are now async. Checked before making the change, not after: grepping every real (non-test) call site in the monorepo found exactly one, `Router`'s `submitRecommendation(item)` call (now `await`ed) — everything else touching these methods was test code, updated to match. `PostgresDurableApprovalStore` writes through the same `withTenantScope`/`audit_log` mechanism `PostgresReservationStore` already used, via a shared `PostgresDurableAuditLog` instance passed to both — meaning a scheduled dispatch's approval-queue submission now shows up in `GET /dashboard`'s `recentActivity` (`audit_log`-backed) for real, which it structurally could not before.

3. **A construction guard, ADR-007/008-style, allowlist not denylist.** `packages/vault/src/env.ts` gained `isDevOrTestEnvironment()` — true only when `NODE_ENV` is unset, `"development"`, or `"test"`. `InMemoryDurableReservationStore` and `InMemoryDurableApprovalStore` both throw (`DevOnlyReservationStoreGuardError` / `DevOnlyApprovalStoreGuardError`) if constructed outside that allowlist. This is deliberately an allowlist rather than `isProductionEnvironment()`'s denylist: a new deploy target added later (staging today; whatever comes after) defaults to **refused**, not silently accepted, which is the direction this exact class of bug — dev wiring reaching a deployed environment unnoticed for months — needs to fail in. `apps/api/src/durableTrustCore.ts` is the new staging-appropriate construction (`start.ts` now calls it instead of `createDevTrustCore`); `apps/api/src/dev/devTrustCore.ts` (`dev.ts`, local dev) is untouched and still uses the in-memory stores, which is correct — `NODE_ENV` is unset there, so the guard passes.

**Decision — what deliberately did NOT become durable, and why:** Router's `TaskLedger` (`apps/router/src/ledger.ts`) and `DedupStore` (`apps/router/src/dedup.ts`) stay in-memory. Durable counterparts exist (`PostgresDurableTaskLedger`, `PostgresDurableDedupStore`, `apps/router/src/durable/`) but implement different, **async** interfaces (`DurableTaskLedger`, `DurableDedupStore`) than what `Router`'s constructor requires (the synchronous `TaskLedger`/`DedupStore`) — not a drop-in swap the way `CostGate`'s reservation store was. Making them durable means converting roughly ten synchronous ledger/dedup calls inside `Router.submitTask` to async, plus making the public `ledgerFor()` method async — a real, separate change, scoped out of this ADR deliberately rather than rushed into the same PR as the approval-queue work. Tracked in issue #120 (filed alongside this ADR): it becomes **required**, not optional, before any multi-replica deployment or real production traffic — an in-memory dedup store that only one replica can see means the same task can dispatch, and be paid for, twice under concurrent replicas. Single-replica staging today is not exposed to that risk; it will be the moment a second replica exists.

**What "staging now uses durable trust-core wiring" means, precisely, after this change:** the approval queue and the cost-gate reservation ledger survive a restart. The task ledger and the dedup store do not. Anyone extending this later should not assume the second half without checking — this ADR exists specifically so that assumption doesn't have to be reverse-engineered from the code.

**Verified:** full-monorepo typecheck; `approval-queue:test`/`router:test`/`cost-gate:test`/`vault:test`/`api:test` all green, including `queue.test.ts` and `router.approvalQueue.test.ts` updated for the new tenant-scoped async signatures, and `env.test.ts` (new) covering the allowlist guard's boundary. No staging deploy has yet been run against this wiring at the time of writing — that is the next step, not assumed complete here.
