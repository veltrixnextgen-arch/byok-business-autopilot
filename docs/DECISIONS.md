## ADR-001 — Bottom-up assembly order
**Date:** 2026-07-31
**Context:** The org chart must be derivable consistently from any business idea.
**Decision:** Assembly order is strict: tasks → sub-agents → teams → roles. Roles are assembled last to lead each team, never designed top-down.

## ADR-002 — Brains vs. Hands are separate key types
**Date:** 2026-07-31
**Context:** LLM provider access and service-API access have different scopes, risk profiles, and collection timing.
**Decision:** Brains (LLM providers, per-role) and Hands (service APIs, per-sub-agent, collected just-in-time) are separate key types with separate lifecycles in the vault.

## ADR-003 — Platform pays for onboarding only
**Date:** 2026-07-31
**Context:** Free-execution abuse and trial economics were the biggest v1 cost risk.
**Decision:** Platform pays AI inference ONLY for onboarding (capped cents/signup); everything after the Charter handoff is BYOK.

## ADR-004 — CEO agent is a recommender by architecture
**Date:** 2026-07-31
**Context:** Autonomous execution by a synthesizing agent is a safety and trust risk.
**Decision:** The CEO agent is a recommender by architecture — its only output pathway is the approval queue. It can never execute directly.

## ADR-005 — Trust core is CODEOWNERS-locked
**Date:** 2026-07-31
**Context:** The router, vault, cost gate, and approval queue are the security-critical trust core of the system.
**Decision:** Trust core (router, vault, cost gate, approval queue) is CODEOWNERS-locked; no AI-generated merges without human review.

## ADR-006 — Trust-core dependencies are pinned; the orchestration library is accessed only through our executor interface
**Date:** 2026-08-01
**Context:** `apps/router/` depends on the third-party `@open-multi-agent/core` package. A bare `open-multi-agent` name collision on npm (an unrelated project by a different author) already showed how easy it is to pull in the wrong thing; an unpinned version or a direct import scattered through business logic would make both a supply-chain compromise and a future swap-out far more dangerous and expensive.
**Decision:** Trust-core dependencies (starting with `@open-multi-agent/core`) are pinned to exact versions with a committed lockfile — no `^`/`~` ranges, no floating updates. Business logic never imports the orchestration library directly; it only ever goes through our own `AgentExecutor` interface (`apps/router/src/executor.ts`), so the library can be upgraded, patched, or replaced behind that interface without touching callers.

## ADR-007 — LocalKms is refused in production
**Date:** 2026-08-01
**Context:** `packages/vault`'s dev-only `LocalKms` stores the master key in a local file — no rotation, no HSM, no access audit on the master key itself. That's an acceptable dev convenience and an unacceptable production posture (T1: user API key theft) if it ever ships by accident (e.g. a missing env var in a deploy config).
**Decision:** Constructing `LocalKms` while `NODE_ENV=production` (or explicit `PRODUCTION=true`) throws `ProductionKmsGuardError` instead of silently working. Production must construct a real `Kms` implementation (`CloudKms` or equivalent) — there is no code path where a misconfigured production deploy quietly falls back to a file on disk.

## ADR-008 — Router refuses to construct in production without a CostGate and an ApprovalQueue
**Date:** 2026-08-01
**Context:** Both dependencies are optional constructor arguments on `Router` (dev/test convenience — the router's own tests don't need cost-gate or approval-queue machinery to verify tagging/dedup/ledger behavior). Nothing before this stopped a misconfigured production deploy from constructing a `Router` with one or both omitted, silently running every task with no spend limit (T4) and no human review before an effect runs (T10, security-architecture.md §5).
**Decision:** Same pattern as ADR-007: constructing `Router` while `NODE_ENV=production` (or `PRODUCTION=true`) throws `ProductionRouterGuardError` unless both a `CostGate` and an `ApprovalQueue` are provided. Dev/test code paths are unaffected — both remain optional outside production.

## ADR-009 — The shell/trust-core integration seam is an ESLint rule, not a convention
**Date:** 2026-08-01
**Context:** `apps/api` (and, later, `apps/web`) is the Emergent boundary side of the system — it's expected to iterate quickly, including with AI-generated changes, while trust-core (router, vault, cost gate, approval queue — ADR-005) stays CODEOWNERS-locked and slow-moving. If shell code ever reaches past a trust-core package's public `index.ts` into its internals (e.g. `@byok/vault/src/kms.js` instead of `@byok/vault`), the CODEOWNERS lock stops meaning much: internal APIs can change shape without the shell noticing at review time, and the shell can end up depending on implementation detail no one meant to expose. Relying on code review discipline alone to catch this doesn't scale, especially once AI-assisted changes are landing in the shell regularly.
**Decision:** `eslint.config.js` at the repo root applies a `no-restricted-imports` rule to `apps/api/**` and `apps/web/**` that blocks any import path matching `@byok/{router,vault,cost-gate,approval-queue}/*` — only the bare package import (which resolves to that package's `index.ts`) is allowed. This fails the build the same way a typecheck failure would; it isn't advisory. Trust-core packages themselves are not subject to this rule (they're allowed to reference each other's internals only through the same public interfaces, but that's enforced by their own existing design, not this rule). CI (see `.github/workflows/ci.yml`) runs `npm run lint` on every PR so a violation blocks merge before a human reviewer ever needs to notice it by hand.

## ADR-010 — Phase B is built by Claude Code under PR-per-issue discipline, not Emergent
**Date:** 2026-08-01
**Context:** The original plan (master-plan-v2.md §4, README) named Emergent as the Phase B builder, on the premise that a separate visual-design tool would generate the commodity UI surface fast and Claude Code would stay out of its way. In practice the scaffold Emergent was meant to generate already exists — Phase A's shell (`apps/api`, `packages/auth`, `packages/db`, `packages/jobs`) was built by Claude Code, is CODEOWNERS-reviewed, and Phase B needs to build directly on it rather than have a second tool re-derive or duplicate it. There's also no reason the containment fence built for Phase A (CODEOWNERS, the ADR-009 lint boundary, branch protection, required CI) should apply only to trust-core or only to one code generator — a UI bug or a boundary violation lands the same way regardless of which tool wrote the diff.
**Decision:** Phase B's commodity surface (`apps/web` and its supporting work) is built by Claude Code, one branch and one PR per step, each referencing a tracked issue, each requiring the same CODEOWNERS review, ADR-009 lint boundary, and required CI checks as everything else in this repo. This is a statement about which generator is producing shipped code, not a relaxation of the fence: the fence (CODEOWNERS, lint boundary, branch protection, CI) applies to every code generator equally, whether that's a human, Claude Code, or any other tool. External design tools (Figma, reference mockups, etc.) may inform the visual design, but they produce visual references only — no code from them enters the repo directly; it's implemented and reviewed the same as everything else.

## ADR-011 — The interview extracts the value chain, not founder preferences
**Date:** 2026-08-01
**Context:** Early onboarding-flow drafts mixed two different kinds of questions: ones that determine the actual STRUCTURE of the business (who pays, for what, how money and delivery move, which jurisdiction's rules apply) and ones that reflect the founder's PREFERENCES about how their company should run (which role to hire first, how much autonomy to grant agents). The first kind changes what org chart gets assembled — ADR-001's bottom-up task → sub-agent → team → role derivation depends on getting the value chain right. The second kind doesn't change the org chart at all; it changes settings on top of an org chart that's already correct. Conflating them made the interview longer than it needed to be and put configuration decisions (autonomy posture, especially) in a place — early onboarding, before the user has seen any real output — where they're hardest to make well.
**Decision:** The interview extracts the value chain only, walking inward from customer to CEO: what customers pay for → who the customer is → how money arrives → how delivery reaches them → jurisdiction. Founder-preference questions — first-hire priority, autonomy posture, and anything else that's a setting rather than a structural fact about the business — are configuration and live outside the interview, asked later at the point where they're actually actionable (e.g. autonomy posture during the BYOK/ceiling flow, once the user has a real role in front of them to grant autonomy to).

## ADR-012 — Trust-core review is a required CI attestation check, not an unsatisfiable approval requirement

**Date:** 2026-08-01
**Context:** Branch protection on `main` required an approving CODEOWNERS review before merge (issue #10's close-out). That's unsatisfiable as configured: every PR in this repo is authored by the `veltrixnextgen-arch` account (via the `gh` CLI), which is also the only entry in `.github/CODEOWNERS` — and GitHub does not allow an account to approve its own pull request. The first real attempt to merge a reviewed, CI-green PR (#29) hit this directly: `gh pr merge` refused with "the base branch policy prohibits the merge," not because anything was wrong with the PR, but because the required review could never exist. Removing the requirement outright would drop trust-core protection to "CI green" with no human-attention signal at all — acceptable for `apps/web` commodity-surface work, not for `packages/vault`, `packages/cost-gate`, `packages/approval-queue`, `apps/router`, `docs/architecture/security-architecture.md`, or the CI/lint-boundary/CODEOWNERS files themselves (ADR-009's rationale for locking those applies just as much here).
**Decision:** Branch protection on `main` no longer requires an approving review (`required_pull_request_reviews` removed; `required_status_checks` with `strict: true` and `enforce_admins: true` stay as-is). `.github/CODEOWNERS` stays in place, unchanged, as the source of truth for which paths are trust-core. In its place, a new required CI job (`trust-core-attestation` in `.github/workflows/ci.yml`) diffs the PR against its base branch: if any changed path matches a trust-core entry from CODEOWNERS, the job fails unless the PR description contains the literal line `TRUST-CORE REVIEWED: veltrixnextgen-arch`. That line must only be added after actually reading the trust-core diff — it is a required, auditable, machine-checked attestation, not a rubber stamp, and it's git history on the PR itself rather than a review that could be dismissed or lost. PRs that don't touch a trust-core path merge on green CI alone, same as any other repo. **This is a stand-in, not a replacement**: the moment a second maintainer exists, restore `required_pull_request_reviews` with `require_code_owner_reviews: true` and retire this job — a real second reviewer is strictly better than a self-attestation, and this mechanism only exists because a single-account repo has no other way to get trust-core changes reviewed by anyone but the person who wrote them.

**Amendment (2026-08-02):** The `TRUST-CORE REVIEWED` line must be added by the human maintainer only — Claude Code must never add it, including when explicitly asked to in-session, and must decline and explain why if asked. The line is a factual claim that a human read the trust-core diff; having the AI agent add it — even at the maintainer's explicit request, even with full context on the change — makes the claim false and defeats the entire point of the mechanism (ADR-012 exists specifically because self-certification isn't a real review). **Honest record:** this had already happened once before the amendment — Claude Code added the attestation line to PR #27 at the maintainer's explicit request, before this constraint was written down. That PR shipped durable storage (issue #6) and was reviewed in substance across the session that produced it, but the line itself was not maintainer-added, which is exactly the gap this amendment closes. No further exceptions from here forward.

## ADR-013 — One shared type contract for what extraction produces and the UI consumes

**Date:** 2026-08-02
**Context:** Before any interview/org-chart UI gets built in `apps/web`, extraction's output shapes (`packages/agents/extraction/src/types.ts`) and whatever the UI would need were on a collision course: nothing stopped a future screen from defining its own local `OrgChart`/`Agent`/`Task` shape that happened to look similar but drifted the moment either side changed independently — exactly the kind of duplicated business logic Phase B's build rules (docs/TRACKING.md) already forbid for screens, just one level up, at the data-shape level instead of the logic level. Building the actual role-card/org-chart UI (Stage 2, docs/product/userflow-v2.md) also surfaced gaps the existing extraction types never had to answer: userflow-v2.md names each agent ("Alex · CFO", "Priya · Invoicing") and gives each a Brain recommendation with a plain-language reason — neither a `name` nor a `brain` field existed anywhere before this ADR, and the temptation for whoever builds that screen next would be to invent placeholder values for both directly in the UI rather than waiting on the engine.
**Decision:** `packages/agents/contracts` (`@byok/contracts`) is the single source of truth for `OrgChart`, `Team`, `Agent`, `Task`, `Charter`, and `InterviewQuestion` (plus their supporting shapes — `TemplateSelection`, `ApiCallUsage`, `CustomizationLog`, `OnboardingBatch`, `SimulatedDayCard`, `InterviewAnswers`, `BrainRecommendation`). It has no runtime dependencies beyond `@byok/templates` (the primitive `Tier`/`TeamHint`/`Frequency`/etc. enums) — deliberately not a dependency of `packages/agents/extraction`'s `@anthropic-ai/sdk`/`commander`/`dotenv`, so `apps/web` can import types from it without pulling in an LLM SDK it will never call directly. `packages/agents/extraction` consumes and re-exports these types rather than redefining them; `apps/web` will do the same once it builds the interview/org-chart screens. A UI screen that needs a field the engine doesn't emit is a signal to add that field to the engine (`assembleOrgChart` or the onboarding-batch generation), not to invent it in `@byok/contracts` or in the UI itself — the contract only describes what extraction actually produces, never what a screen wishes it produced. Two fields are deliberately `null`/empty rather than fabricated to satisfy this ADR on paper: `Agent.brain` is always `null` (no per-role Brain-recommendation logic exists yet — which provider, and why, is a real product decision nobody has made), and the branch-question mechanism on `InterviewQuestion` (`appliesToTemplates`) has zero entries (no template has a real follow-up question designed yet). Both are complete, honest states, not stubs — the alternative (a fake recommendation or an invented question) would be worse than the gap it's covering. `Agent.name` is the one new field this ADR *does* populate for real: assembled deterministically from a curated name bank in `assemble.ts` (no LLM call — this is a synchronous assembly step, and every agent needs a name whether or not the budget-gated onboarding-batch call happens to run), and the onboarding-batch generation now sources its digest cards' names from that same canonical value instead of letting the model reinvent one, closing a latent inconsistency (userflow-v2.md: "Names flow through everything downstream").

**Amendment (2026-08-03):** The `appliesToTemplates`-filtered `InterviewQuestion` mechanism described above (a flat catalog in `@byok/contracts`, tagged with which templates a question applies to) is superseded by STEP 5's real branch-question content: each `BusinessTemplate` (`packages/templates`) now declares its own `branchQuestions: InterviewQuestion[]` directly, since the questions are genuinely template-specific data, not a shared catalog filtered after the fact. This required moving the primitive enum types (`Tier`, `TeamHint`, `Frequency`, `Stakes`, `AutonomyDefault`, `HandsScope`, `BusinessTemplateId`) out of `packages/templates` and into `@byok/contracts`, so `packages/templates` could depend on `@byok/contracts` (for `InterviewQuestion`) without creating a cycle — `@byok/contracts` no longer depends on `@byok/templates` at all as of this change. See ADR-015 for the rest of STEP 5's schema and persistence decisions.

## ADR-014 — The platform-key onboarding batch is gated by the cost gate directly, not routed through `Router.submitTask`

**Date:** 2026-08-03
**Context:** STEP 5 needed extraction (`packages/agents/extraction`) to "run through the router... cost cap enforced via the cost gate" — but `apps/router`'s `Router`/`AgentExecutor` model is built for one task in, one text result out (per `ExecutionOutcome = { result: string; costUsd?: number } | { error: string }`), while extraction is a self-contained pipeline of up to three sequential Claude tool-use calls (customize → category-validate → onboarding-batch), each needing structured (not plain-text) output, and already has its own working fail-closed cost guard (`packages/agents/extraction/src/costGuard.ts`'s `guardEstimatedCost`/`actualCostUsd`, checked before and after every individual call). Making each of those three calls flow through `Router` + `OpenMultiAgentExecutor` individually would require building a new tool-use-capable executor (the current one only returns plain text) and a `BrainKeyProvider` adapter resolving the flat platform `.env` key through the vault's per-role key interface — neither exists, and both are real, separate engineering, not a same-PR add-on to an already-large UI step.

A first design wrapped the whole batch as one `Router.submitTask()` call instead, avoiding the tool-use problem — but `Router.submitTask` unconditionally routes every successful result through the `ApprovalQueue` when one is attached (`apps/router/src/router.ts`), and ADR-008's production guard requires an `ApprovalQueue` to be attached at all. That coupling exists for real agent ACTIONS with a potential real-world `effect` a human might need to review before it happens — approve, reject, modify. Extraction has no effect: it produces a document (the org chart) the user reviews directly in the UI, with no approve/reject concept at all. Routing it through `submitTask` would have queued every signup's org chart for "human approval" in production, which is not what the approval queue is for, and isn't fixable by simply omitting an `effect` (a no-effect `ProposedAction` still queues by default, per the approval-queue's own tests — it just doesn't dispatch anything on approval).
**Decision:** `apps/api/src/extraction/runExtractionBatch.ts` gates and settles the batch directly against `CostGate.evaluateAndReserve`/`settle`/`release` — the same real pre-flight ceiling reservation (checked against company/role/task-type ceilings) and real settlement with the batch's actual total cost (`chart.meta.costUsd`) any router-routed task would get — without going through `Router.submitTask`'s approval-queue coupling. It appends directly to the same `TaskLedger` instance the Router wraps (now exposed on `TrustCoreDeps.ledger` for exactly this reason) at each state transition (pending → in_progress → completed/failed/queued/skipped), so the batch has the same visibility in the ledger a submitTask-routed task would have. Extraction's own per-call `guardEstimatedCost`/`actualCostUsd` keeps running unchanged *inside* the batch, as a second, finer-grained safety net the outer reservation doesn't replace. This satisfies "cost cap enforced via the cost gate" for the platform-key onboarding batch specifically, using the router's real infrastructure (its cost gate, its ledger) without forcing it through a state machine built for a different kind of task. It does not generalize to per-role ongoing agent work on a user's own BYOK key, where each action DOES have a real effect and genuinely needs `Router.submitTask`'s full gate → executor → approval-queue path with structured output — that's real, separate scope, tracked in issue #37 and required before MVP-1's "one role executing end-to-end on user keys" (issue #19) can be built.

## ADR-015 — The org chart is persisted against the signed-up user, not a tenant, until the Charter handoff

**Date:** 2026-08-03
**Context:** STEP 5's idea → interview → extraction → org-chart-reveal flow runs entirely before STEP 3's org-creation step (`/onboarding`, "name your company") — nothing in STEP 5's scope mentions company naming, and folding it in would rework an already-shipped flow for no requirement STEP 5 actually has. But the extraction batch is real, capped platform spend (ADR-003) that needs to be persisted for real CAC measurement "from signup one" — including users who see their org chart and never create an org at all, which a tenant-keyed record couldn't capture (there'd be no tenant yet to key it to). `packages/db`'s existing RLS isolation (`withTenantScope`, `app.tenant_id`) doesn't apply here for the same reason: there's no tenant.
**Decision:** A new `signup_extraction_batches` table is keyed to `user_id` (Better Auth's `user.id`, already synced into this project's own `users` table per STEP 3), not `tenant_id`. It gets its own `FORCE ROW LEVEL SECURITY` policy scoped on `current_setting('app.user_id')`, and a `withUserScope` helper (`packages/db`) that mirrors `withTenantScope`'s pattern exactly, set before any query against this table — the same defense-in-depth discipline the tenant-scoped tables already get, just keyed differently, rather than relying on application-code `WHERE user_id = ?` filtering alone. This intentionally leaves a gap: nothing currently moves a completed org chart from "belongs to a user" into a tenant's scope. That gap is deliberate, not unowned — issue #38 assigns it to the Charter handoff step (issue #16), the point userflow-v2.md itself calls "the second the company is live," which is the correct moment for an org chart to actually become a tenant's data.

## ADR-016 — apps/web's jsxDEV-in-production bug, and how it was actually fixed (STEP 6)

**Date:** 2026-08-03
**Context:** Live staging verification of STEP 5 caught a real production outage: `apps/web`'s pinned `nitro` (`3.0.260610-beta`, a date-versioned nightly channel, not a semver prerelease of any numbered release), paired with `vite@8.2.0` and `@vitejs/plugin-react@6.0.5`, produces an SSR (and client) bundle that calls `jsxDEV` — React's development-only JSX factory — in production, crashing every page that actually renders (not just an early-redirect route) with `TypeError: jsxDEV is not a function`. This wasn't caught by any earlier deploy because every prior Vercel build had been reusing a much older, never-fully-reconciled `node_modules` (via `npm install`'s incremental reuse of Vercel's build cache) that predated whatever pull introduced the bug — confirmed directly: a full, lockfile-accurate install (`--force` with no cache, then `npm ci`) reproduced the broken bundle byte-for-byte every time, while the stale cached install kept producing a correct one.

Two attempts to fix this by moving off the toolchain's beta channel were tried and reverted, both for good reason, not abandoned for convenience:
1. **`nitro@3.0.0`** (its only tagged non-prerelease 3.x release) requires `vite@^7`, so `vite` moved to `7.3.6` to match — the only mutually-compatible stable pair. `@tanstack/react-start`'s own peer dependency is `vite: ">=7.0.0"` (confirmed by inspection, not `>=8`), so this wasn't fighting the framework's own requirement. Locally this produced a clean build with zero `jsxDEV` references anywhere. But live on Vercel, the deployed site stopped crashing and instead went **silently non-interactive** — typing in the idea box never revealed the submit button, clicking "Sign in" did nothing, zero console errors. Confirmed the client bundle still called `e.jsxDEV(...)` directly even under this pairing — the toolchain swap hadn't actually eliminated the underlying symptom, just stopped it from crashing while breaking hydration instead. Worse than the bug it was meant to fix.
2. **`@vitejs/plugin-react@4.7.0`** (the last release before the plugin's move to an experimental oxc/Rolldown-based JSX transform — the one variable present, unchanged, across both the crash and the silent-hydration-break) doesn't even resolve: its peer range tops out at `vite@^7.0.0`, conflicting with `vite@8.2.0` (`ERESOLVE`, no install possible without `--legacy-peer-deps`, which was explicitly not authorized).

**Interim decision (STEP 5):** Revert to the original pins (`nitro@3.0.260610-beta`, `vite@8.2.0`, `@vitejs/plugin-react@6.0.5`) — the last combination confirmed to actually render and respond to input on staging. `.github/workflows/deploy-staging.yml`'s `vercel deploy` step does **not** pass `--force`: discarding Vercel's build cache forces the full, lockfile-accurate install that reliably reproduces the `jsxDEV` crash, so cache reuse was, at that point, load-bearing — an explicitly acknowledged fragility, not a hidden one. Tracked as issue #39.

**Actual fix (STEP 6):** Both prior attempts stayed within Nitro v3 (the package literally named `nitro`, imported as `nitro/vite`) and only varied its paired `vite`/`@vitejs/plugin-react` versions. The angle that actually worked was different: Nitro v3 is still on a date-versioned nightly channel with no numbered stable release past `3.0.0` (which itself doesn't support `vite@8`), and has multiple *independent* open upstream bugs against TanStack Start + Vercel unrelated to our specific symptom — [nitrojs/nitro#3905](https://github.com/nitrojs/nitro/issues/3905) (prerender failures), [nitrojs/nitro#3965](https://github.com/nitrojs/nitro/issues/3965) (wrong Node version), [vitejs/rolldown-vite#580](https://github.com/vitejs/rolldown-vite/issues/580) (unresponsive server on `vite@8` beta + Nitro v3 alpha — the same Vite-8-plus-Nitro-v3 pairing we were pinned to). TanStack Start still officially supports `@tanstack/nitro-v2-vite-plugin`, which wraps `nitropack@2.x` — the mature, long-stable Nitro line Nuxt and SolidStart have shipped on for years — as its pre-v3-migration path, not something deprecated away.

Swapped `nitro()` for `nitroV2Plugin({ preset: "vercel" })` (explicit preset — the v2 plugin doesn't advertise the v3 rewrite's Vercel-build-env auto-detection). `vite@8.2.0` and `@vitejs/plugin-react@6.0.5` stayed exactly as pinned (`nitro-v2-vite-plugin`'s peer is `vite: ">=7.0.0"`, no upper bound — installed clean, no `ERESOLVE`). Verified two independent ways: locally, zero `jsxDEV` calls anywhere in the compiled SSR entry (the one `jsxDEV` string match is React's own bundled `react-jsx-runtime.development.js` sitting in the function's `node_modules` — nitropack v2 treats `react` as an external dependency rather than inlining it, and Node's own `require()` resolves away from that file via `NODE_ENV` at runtime, same as any correctly-configured Node production deploy); live on staging, a real signed-up account was driven all the way through idea input → interview → real extraction → task list → org chart, with zero console errors and the compliance-locked banner rendering correctly. `--force` was **not** restored to the `vercel deploy` step even after this fix — a clean install is no longer known to break the build, but there's no reason to spend the cache-reuse safety margin now that the actual bug is gone; revisit only if a future, unrelated change needs cache-bypassing for its own sake.

One caveat carried forward, not fully resolved: `@tanstack/nitro-v2-vite-plugin` is documented as TanStack's pre-migration path, not the new-project default — it's the pragmatic, verified-stable choice today, not a claim that it's the long-term direction. Revisit if TanStack deprecates it outright, or once Nitro v3 ships a real stable release with confirmed Vercel + `vite@8` support.

## ADR-017 — The product is named Runwisely; BYOK is a concept, not the product name

**Date:** 2026-08-04
**Context:** The product shipped its first 20-tester pilot under the working title "BYOK Business Autopilot" — accurate as a description (bring-your-own-key, the whole point of the spend-wall architecture) but never actually the brand. Every user-visible surface (page title, hero copy, README, the product docs) still said "BYOK Business Autopilot" going into the pilot. Left alone, the acronym would keep drifting into places a real brand name belongs — new docs, new screens, new copy — just because it was the first thing typed into this repo, not because anyone decided it should be the name.
**Decision:** The product is named **Runwisely**. Renamed throughout every user-visible and prose surface: README title, all `docs/` prose (current and archived — `docs/archive/master-plan-v1.md`'s title changed too; an archive preserves the *strategy*, not a stale product name), ADR titles/headers where the literal product name appeared, the root `package.json` `"name"` field, the app's page `<title>` (`apps/web/src/routes/__root.tsx`) and hero copy (`apps/web/src/routes/index.tsx`), and the extraction CLI's `--help` description.

**What stays "BYOK," deliberately:**
- The **feature/mechanic** — bring-your-own-key, the three-spend-wall model, "BYOK Graduation" as a named onboarding stage — is still correctly called BYOK throughout the product docs (`userflow-v2.md`, `roles-and-api-key-guide.md`, `master-plan-v2.md`, `DECISIONS.md`). This is the concept the acronym actually describes; renaming it away would make those docs *less* accurate, not more on-brand.
- **BrainKey** / **HandsKey** (`packages/vault`) — the vault's own key-type names, unrelated to the product name.
- The internal `@byok/*` npm workspace package scope (`@byok/web`, `@byok/api`, `@byok/vault`, `@byok/contracts`, …) — **left unchanged, on purpose**. Renaming it means touching every import statement in every package across the monorepo (hundreds of call sites) for a label no user, tester, or anyone outside this codebase ever sees — it's private workspace-internal namespacing, never published, never rendered. The risk (this repo has already spent one full session recovering from a toolchain regression — see ADR-016) isn't worth it for a purely internal identifier. Revisit only if the scope is ever actually published or becomes externally visible.
- The GitHub repo name (`byok-business-autopilot`) — unchanged for the same reason renaming a repo breaks: existing clones, CI secrets scoped to the repo, issue/PR links, and the deploy pipeline's own references to it. The README now says so explicitly, pointing here.

**Why this won't drift back:** the distinction is now written down in exactly one place (here) instead of living only in whoever happened to remember it — "Runwisely" is the name on anything a user, tester, or investor reads; "BYOK" is the accurate technical description of one mechanic inside it, plus two internal-only legacy labels (the npm scope, the repo name) that are deliberately not part of the rename's scope.

## ADR-019 — The Dependency-audit gate suppresses specific, expiring, reasoned findings — it never lowers the severity floor or gets disabled

**Date:** 2026-08-08
**Context:** `.github/workflows/ci.yml`'s `dependency-audit` job ran a bare `npm audit --audit-level=high`, which fails the whole PR the moment any high-or-critical advisory exists anywhere in the dependency tree — including ones with no real fix available and no real exposure in this deployment. Investigating one such red check (docs/TRACKING.md's "two npm audit findings with no working fix" entry) found `@tanstack/react-start-plugin` is already on its newest published version (nothing to upgrade to — the advisory's own suggested fix is a downgrade that fixes nothing) and `esbuild`'s vulnerable copy is reachable only through a dev-only CLI tool that never starts the affected dev server. Both are real findings, correctly reported, and currently unfixable without a regression. Left as a bare `--audit-level=high` gate, PRs touching completely unrelated code (a docs-only PR, in this case) inherit a permanently red required check — which trains whoever's watching to stop reading it, so it catches nothing the day a real, fixable high-severity finding actually lands.
**Decision:** `.github/scripts/check-audit-allowlist.mjs` replaces the bare `npm audit` command in CI. It keeps `--audit-level=high` as the floor — moderate findings never fail this gate, same as before — but a high/critical finding only passes if its advisory (matched by GHSA id, extracted from `npm audit --json`'s `via` entries) is a reasoned, unexpired entry in the committed `.github/audit-allowlist.json`. Two independent failure conditions, enforced every run:
1. A high/critical finding whose advisory isn't in the allowlist (or is, but the entry is expired) — the build fails, full stop.
2. An allowlist entry itself past its own `expiresAt` — the build fails even if that advisory doesn't currently manifest as high/critical, forcing a periodic re-review rather than a suppression that quietly lives forever. Seeded at a 90-day expiry.

Suppressing a specific advisory ID with a reason and an expiry, by editing a committed JSON file that shows up in the PR diff, is the **only** sanctioned way to quiet this gate. Two things this is explicitly not a replacement for, and must never become one:
- **Never lower `--audit-level`.** Moderate-and-below findings staying non-blocking is an existing, separate decision (informational, reported, not gated) — the allowlist only governs the high/critical floor this ADR is about.
- **Never disable or skip the job.** An allowlist entry is a recorded, reasoned, time-boxed acceptance of one specific advisory; disabling the job accepts everything, forever, with no record of why.

Seeded with the two findings from docs/TRACKING.md's entry (`GHSA-9m65-766c-r333`, `GHSA-67mh-4wv8-2f99`), same reasons, `expiresAt: 2026-11-05`.

## ADR-020 — OAuth Hands credentials: structured storage, single-flight refresh, fail-closed to draft on any refresh failure

**Date:** 2026-08-12
**Context:** `HandsKeyRecord`'s `material` decrypted to an opaque secret handed straight to a Hands tool's `invoke()` — correct for a pasted static API key (Stripe, Square, ...), but Google Calendar/Meta connect (the two services picked from `docs/design/tool-registry.md` §2g's ranking) issue short-lived OAuth access tokens with a refresh token behind them. Building this generically, ahead of either provider integration, was a deliberate choice: sizing it against one concrete integration (Google Calendar, PR 2B) rather than two simultaneously, per the decision to sequence Calendar before Meta.

**Verifying before building surfaced a real, pre-existing gap, not just an OAuth-specific one.** `OpenMultiAgentExecutor`'s `missingHands` — the list `router.ts` uses to force `effect: undefined` (issue #22's draft-mode guarantee) — was populated **only** by the pre-flight `resolveHandsKeyId` filter, before the LLM's run even starts. A Hands tool connected at pre-flight (a key exists) but failing when the LLM actually calls it — a plain decrypt error, a key revoked mid-run, or now an OAuth refresh failure — reached `handsTool.ts`'s existing catch block (a clean `isError` tool result, so the run never crashed) but never reached `missingHands`. The router could therefore still submit the caller's original requested effect even though the Hands call never actually succeeded — the fail-closed-to-draft property held for "never connected" but not for "connected, then failed mid-run." This was always reachable (a mid-run revoke already exercised the same code path per `handsTool.ts`'s original comment), but OAuth token expiry turns it from a rare edge case into a routine, expected occurrence. **Fixed as a required change, not folded silently into the OAuth work**: `createHandsTool` (`apps/router/src/handsTool.ts`) takes an optional `onLiveFailure` callback, called on both existing failure branches (`!keyId` and a `decryptHandsKey` throw); `OpenMultiAgentExecutor` wires it to push into the same `missingHands` array the pre-flight filter already populates. `router.ts` itself needed zero changes — its existing `effect: task.missingHands ? undefined : input.effect` already treats both sources identically once they land in the same array.

**Decision:**
1. `HandsKeyRecord` gains `credentialKind: "opaque" | "oauth"`, set once at `storeHandsKey` time. `"opaque"` (the default, issue #22's existing pasted-key behavior) is completely unchanged. `"oauth"` means `material` decrypts to a JSON-serialized `OAuthCredential` (`{accessToken, refreshToken?, expiresAt?, scope?}`) — never a bare token string.
2. `decryptHandsKey` checks `expiresAt` (60s safety margin) for an `"oauth"` record. Not expired: returns a `SecretHandle` wrapping only `accessToken` — the decrypted JSON blob (which carries `refreshToken`) is `zeroBuffer`'d immediately after parsing, so a Hands tool's `invoke()` never sees anything but the access token, same shape as an opaque key today.
3. Expired: refreshed via a provider-registered `HandsCredentialRefresher` (one per Hands `service`, e.g. `"google-calendar"`) — the vault owns everything provider-independent; a refresher owns exactly one HTTP call to its provider's token endpoint. Re-encrypts and stores the new credential **in place** (same key id, same AAD scope-binding) — no caller holding that id needs to know a refresh happened.
4. **Fail-closed is structural, not just tested.** Every path through `performRefresh`/`getOrRefreshCredential` either returns a genuinely fresh credential or throws — there is no branch that returns a stale/expired `accessToken`. No expired credential ever silently reaches a Hands tool call.
   - No `refreshToken` on an expired credential → `HandsRefreshFailedError` immediately, refresher never called.
   - Refresh network/provider error → `HandsRefreshFailedError` (transient: the key stays connected, a later call may succeed).
   - Provider signals the refresh token itself is dead (`HandsRefreshTokenRevokedError`) → the stored key is revoked for real, through the same `revokeHandsKey` path (purge, audit, `key.revoked` event) a manual revoke uses — issue #22/#37's revoke-cancels-queued listener fires identically, rather than leaving a "connected" key that fails the same way forever.
   - A refresher call is bounded by `refreshTimeoutMs` (`withTimeout`, default 10s) — a hanging provider call rejects on schedule instead of hanging the caller.
   - A single attempt, no internal retry loop — a transient failure surfaces immediately rather than this method hammering the provider's token endpoint.
5. **Single-flight refresh per key id**, via an `inFlightRefreshes: Map<keyId, Promise<OAuthCredential>>` — a second `decryptHandsKey` call for the same expiring key while a refresh is already running awaits the SAME promise rather than starting a second one.

**On whether the concurrency guard is defensive or fixes an observed bug — checked, not assumed:** it was scoped as insurance against a *future* orchestration-library change. Reading `@open-multi-agent/core`'s installed source (`node_modules/@open-multi-agent/core/dist/tool/executor.js`, `ToolExecutor.executeBatch`) took a few minutes and turned that into a **verified fact, not a hedge**: a turn's tool calls already run through `Promise.all` gated by a 4-way `Semaphore` (`options.maxConcurrency ?? 4`) — real, present, reachable concurrent tool execution, not a hypothetical. An LLM double-calling the same Hands tool within one turn (which does happen) can reach `decryptHandsKey` for the same key id twice before either finishes, today, with the library exactly as currently installed. The guard is still not a fix for an *observed* race in this system specifically — no bug report prompted it — but it is not speculative about the library's mechanics. (Separately, `ToolExecutor.runTool` calls each tool exactly once per dispatch with no internal retry of a failed call — the "retry loop" risk named in the build brief is about *our* refresh code needing to stay single-attempt, which it does, not about the library retrying failed tool calls itself.)

Test coverage: `packages/vault/src/vault.test.ts` — non-expired credential never triggers a refresh; expired credential refreshes and re-encrypts in place; all four fail-closed scenarios (no refresh token, generic refresh failure, network error, revoked refresh token) each end in a thrown error and no handle, with the revoked case additionally asserting the key becomes actually unreachable and the `key.revoked` event fires; a hanging refresher rejects on the bounded timeout; concurrent decrypts single-flight to exactly one refresher call; a failed single-flight attempt rejects every concurrent caller and still allows a later retry; the refreshed access token is still never `JSON.stringify`/`String()`-serializable. `apps/router/src/openMultiAgentExecutor.test.ts` — the `missingHands` gap itself, regression-tested directly: a Hands tool connected at pre-flight but failing on the actual call still lands in `missingHands`.

## ADR-021 — Google Calendar OAuth connect: HMAC state (not server-side storage), platform client secret in env config, code-complete pending only a real domain

**Date:** 2026-08-12
**Context:** ADR-020 built the generic OAuth-credential refresh infrastructure without wiring a real provider. PR 2B wires the first one — Google Calendar, §2g's top-ranked build target — end to end: `apps/api`'s `/hands-oauth/:service/start` and `/hands-oauth/:service/callback` routes, `packages/templates`'s `handsAuth.ts` giving Calendar's badge a real connect affordance instead of the honest-pending message, and a `HandsCredentialRefresher` registered into Vault. Google's own app verification (`docs/design/google-oauth-verification-checklist.md`) requires a real public homepage and a same-domain privacy policy this product doesn't have yet — the code had to be complete and correct without either existing.

**Decision:**

1. **CSRF state is a self-contained, HMAC-signed token — no server-side storage.** `apps/api/src/oauth/state.ts` signs `{tenantId, subAgentId, capabilityScope, service, nonce, issuedAt}` with `BETTER_AUTH_SECRET` (domain-separated via a distinct HMAC context string, `"hands-oauth-state:v1"`, so a token valid for one purpose is never mistakable for the other) and verifies signature + a 10-minute expiry on the way back. Rejected a server-side nonce table: the callback route deliberately doesn't hold a Postgres connection open (next point), so there's no natural transactional place to store one, and a signed token survives a multi-replica deployment for free. Reuses the existing required secret rather than adding a new required env var — one more thing that doesn't need to exist before this is otherwise ready.
2. **The callback route is NOT behind `tenantMiddleware`.** Every other `/me/*` route wraps its full request in `withTenantScope` — a live Postgres connection held for the request's duration. The callback's own body is a server-side HTTP round-trip to Google's token endpoint; holding a pooled DB connection open across an external network call for the whole exchange is exactly the kind of thing to avoid, and `storeHandsKey` doesn't touch the SQL pool at all in this deployment (Vault is KMS/in-memory, see `devTrustCore.ts`). Session is still checked directly (`auth.api.getSession`, the same call `tenantMiddleware` makes internally) and cross-checked against the state's embedded `tenantId` — defense in depth: the signed state alone proves the request traces back to a `/start` call this server issued, but the live-session cross-check means a leaked or replayed state link can't be completed from a different signed-in tenant either.
3. **Platform client ID/secret live in `readServerConfigFromEnv`'s env config, never the vault** (ADR-003's pattern — the onboarding Anthropic key — extended to a second platform credential). Unlike every other field there, `google` is **optional**: `GOOGLE_OAUTH_CLIENT_ID`/`GOOGLE_OAUTH_CLIENT_SECRET` unset resolves to `google: null`, and the server boots fine either way — `/hands-oauth/google-calendar/start` just 404s with "isn't connectable yet" instead of the whole process refusing to start. This is deliberate, not a shortcut: these two values genuinely don't exist yet (Google's app isn't registered, verification hasn't started), and a `readServerConfigFromEnv`-style hard requirement would mean staging can't boot at all until they do.
4. **Fail-closed, no partial connect, matching ADR-020's property exactly**: every failure path (provider declines consent, invalid/expired/mismatched state, failed code exchange, a vault store failure) redirects with `?handsOAuth=error&reason=...` and stores nothing — `storeHandsKey` either writes one complete `credentialKind: "oauth"` record or the callback never calls it at all. There is no code path that writes a placeholder or half-populated credential.
5. **The only remaining step once real credentials exist is two `railway variable set` lines in `deploy-staging.yml`** — deliberately not added in this PR. `.github/workflows/` is CODEOWNERS-locked (trust-core-adjacent per its own header comment), and there's nothing real to set yet (no domain, no verified app, no client secret) — adding placeholder/empty values now would just be a second edit to make later for no benefit today. This is the literal answer to "build it so the only thing standing between it and working is the domain, not more code": the code merges as-is; the domain unlocks Google's verification; verification produces the two secret values; those two `railway variable set` lines (one PR, needing attestation because of the file they touch, not because of what they do) are the entire remaining task.

**Scope note, recorded rather than silently absorbed:** `handsAuth.ts`'s `Calendar` label covers both Google Calendar and Outlook Calendar per `tool-registry.md` §2b — this PR wires Google specifically (§2g's ranked recommendation), so a business on Microsoft 365 sees the same "Connect" button and completes a Google OAuth flow regardless of which calendar they actually use. Same category of imprecision as the existing `Shopify/Etsy` and `Resend/ConvertKit` combined-label entries — flagged in `handsAuth.ts`'s own comment, not solved here; the label would need to split by underlying service for a real fix.

## ADR-022 — Migrations run on every boot, not just on a tagged staging deploy; a second, independent schema-currency check backs it up

**Date:** 2026-08-12
**Context:** Staging's extraction pipeline returned a raw 500 (`column "tenant_id" does not exist`) for every real signup. Root cause, confirmed by reading the failing code path directly (`SignupExtractionBatchStore.start()`'s `RETURNING` clause references `tenant_id`, added by migration `0006`) and by querying staging's live schema (`signup_extraction_batches` had no `tenant_id`, `tenants` had no `monthly_ceiling_usd` — migration `0007`): **migrations hadn't run against staging since `v0.6.13-staging` (2026-08-08)**, confirmed via `git tag`. Everything since — eleven merged PRs, including both migrations this broke on — deployed fine, because Railway's own GitHub integration auto-redeploys `@byok/api`'s *code* on every push to `main` regardless (`railway.json`'s `startCommand` is just `npm run start`, no migration step), while the *schema* only advances inside `deploy-staging.yml`'s migration step, which only runs on a manually-pushed `v*.*.*-staging` tag. Nobody had pushed one in four days. The two deploy paths had quietly decoupled, and nothing surfaced that until a real request hit the gap.

**Decision: both (a) and (b), not either alone.**

1. **(a) — migrations run on every boot.** `apps/api/src/start.ts` and `dev.ts` now call `runMigrations(pool)` before `startServer(...)`, unconditionally, every process start — staging, and local dev. This removes the drift at the source: code and schema can no longer ship on different schedules, because they now ship on the same boot.
2. **(b) — a second, independent schema-currency check.** `verifySchemaCurrent(pool)` runs immediately after, as its own call, not folded into `runMigrations`. Deliberately redundant with (a): the point is to still catch drift if some future change to `start.ts` accidentally drops the `runMigrations` line but leaves this one, or if a not-yet-imagined deploy path never calls either. It checks a small, hand-maintained canary list (`SCHEMA_CANARIES` in `migrate.ts`) — one `{table, column, addedBy}` entry per migration that adds a column via `ALTER TABLE ... ADD COLUMN` — against `information_schema.columns`, and throws `SchemaDriftError` naming exactly what's missing and which migration adds it. Canaries are scoped to *column-adding* migrations specifically, not every migration: a `CREATE TABLE IF NOT EXISTS` migration against a database that's never seen it either creates the whole table or is a complete no-op — there's no way to end up silently half-missing a table the way a skipped `ADD COLUMN` silently leaves a column absent from an already-existing table. That asymmetry is exactly what let this incident happen invisibly for four days.

Both failures now happen the way ADR-007/008's guards already work in this codebase: the process refuses to start and crashes loudly on boot, rather than starting cleanly and serving a raw Postgres error to the first real user who hits the gap.

**On whether (a) is risky here — checked, not assumed, per the explicit ask:**
- **Long migrations blocking boot** — not a real risk *today*: all seven migration files are pure DDL (574 lines total, no data backfills — confirmed by reading every file), sub-second to apply. It's a real risk for the *pattern* going forward, though: once migrations run at boot, a future migration that does a heavy backfill on a large table would block every subsequent boot until it finishes, which could exceed Railway's ~2-minute healthcheck window and look like a failed deploy. Noted as a convention to carry forward, not fixed here since nothing today triggers it: a future slow migration should ship as an additive, backward-compatible step (add a nullable column, backfill via a separate background job, tighten the constraint in a later migration) rather than one blocking `ALTER`.
- **Concurrent replicas racing the same migration** — genuinely low today (every environment runs `replicas: { configured: 1 }`, confirmed via `railway service list --json`), but not zero risk in the code *pattern* if that ever changes without anyone revisiting this file. Most of this repo's migration statements tolerate a race fine — Postgres's own `CREATE TABLE IF NOT EXISTS` is race-safe. The one pattern that isn't: `DROP POLICY IF EXISTS` immediately followed by `CREATE POLICY`, used throughout for RLS (Ring 1 tenant isolation). Two replicas interleaving those two statements could leave a real, if narrow, window where a tenant-isolation policy is dropped but not yet recreated. Rather than accept that as a someday-problem, `runMigrations` now wraps the whole run in a Postgres advisory lock (`pg_advisory_lock`/`pg_advisory_unlock`, session-scoped, auto-released if the holding connection dies) — cheap insurance now, and it means scaling replicas later never requires remembering to come back and add this.

**Test coverage:** `packages/db/src/migrate.test.ts` — the advisory lock brackets every migration call and releases even when a migration throws (never left held on a crashed run); `verifySchemaCurrent` resolves cleanly when canaries are present, throws `SchemaDriftError` naming the exact missing column and its source migration when they're not, and reports every missing canary at once rather than just the first.

**Verified against the real incident, not just unit tests:** pushed `v0.6.14-staging`, watched `deploy-staging.yml`'s migration step succeed, then independently re-queried staging's live schema directly (not just trusted the green checkmark) — `tenant_id` and `monthly_ceiling_usd` both present. Drove a full real signup through interview → extraction → org chart → feedback on staging afterward; extraction completed with a real, idea-specific org chart and no error.

## ADR-023 — Template selection: structured interview answers are the primary signal, idea-text keywords are secondary

**Date:** 2026-08-13

**Context:** A real end-to-end run of "a subscription-based meal prep company in Vancouver" got routed to the `saas` template — a Build Agent proposing code via GitHub, a QA/smoke-test agent, a Deploy Coordinator — because `"subscription"` was a `saas` keyword in `templateSelect.ts`, despite the founder's payment model already being captured correctly by the structured `howMoneyArrives` field. `customization.added` came back empty: the customize pass had nothing structurally wrong to fix, since nothing in the *scaffold itself* pointed at food/kitchen/delivery at all — it just relabelled software-product task text with food-adjacent phrasing. A controlled comparison (a real barbershop run, the existing `saas-scheduler` fixture, `mortgage-brokerage` naming real regulators — BCFSA, FINTRAC — by name) confirmed the customize pass itself was not the problem: when template selection is right, it already does genuine, specific, structural work. The bug was entirely upstream, in a keyword table that let one generic word decide a business's entire vertical.

**A full keyword audit** (all six templates, every keyword, checked against "does this describe a business TYPE or a business MODEL/maturity/payment-structure") found this wasn't an isolated word: `saas`'s `"startup"` (maturity, not a vertical), `physical-space`'s `"membership"`/`"rental"`/`"booking"` (payment/access model, not a space type), `ecommerce`'s `"marketplace"` (ambiguous between "sells via a marketplace" and "is a marketplace platform"), and a separate but related flaw — `service`'s own `"service"`/`"services"` keywords are so generic ("meal-prep *service*," "subscription *service*") they function as noise, not signal. Also found: a `stage === "nothing-yet"` bonus wired to `saas` specifically — the exact same category of bug applied to a non-keyword signal (a brand-new *anything* nudged toward "software").

**Decision:**
1. **Structured answers are now the primary signal, weighted above keywords, not the other way around.** `howDeliveryReaches`/`howMoneyArrives`/`whoTheCustomerIs` each carry a per-template bonus (weight 3) that a single stray keyword hit (weight 1) can no longer outweigh. `howMoneyArrives` deliberately contributes **no** template-specific bonus at all — payment model doesn't predict business type, so encoding it as a signal for any one vertical would just be relocating the same bug, not fixing it.
2. **Every business-model/maturity keyword found in the audit was removed** from the keyword tables (`startup`, `membership`/`memberships`, `rental`/`rentals`/`equipment rental`, `booking`/`bookings`, `marketplace`, `platform`, `tool`, `build`, `service`/`services`). Verified via a regression check against all 8 real fixtures (the original 6 plus new barbershop and meal-prep ones — see below): zero change in outcome for any already-correctly-routed idea.
3. **A confidence signal**, surfaced on every `TemplateSelection` (`confidence: "high" | "low"`) and logged unconditionally when low — the top-two-scores-close case (the pre-existing makerspace/wedding-photographer "known limitation" and the meal-prep incident are the same shape: a genuinely ambiguous idea, silently resolved by an arbitrary tiebreak instead of being flagged). Two regressions were introduced and caught by this same process while wiring the structured-signal bonuses (a blanket `howDeliveryReaches: "shipped"` bonus that outweighed food-hospitality's own keywords and re-broke the meal-prep case a different way; a blanket `"in-person"` bonus that tied a wedding photographer against a food-specific category with zero food-keyword backing on either side) — both fixed before merge, both now covered by `templateSelect.test.ts`.
4. **When confidence is low, the founder is asked directly** instead of the system guessing silently: `interviewQuestions.ts`'s `buildDisambiguationQuestion` injects a real interview question (top two candidate templates, by name/description) in place of branch questions until it's answered. Requires no new UI — it's rendered by the same generic single-select question path every other interview question already uses, and the answer flows through the same `branchAnswers` bucketing `InterviewScreen.tsx` already does for any non-spine/non-context question id. `selectTemplate` treats an explicit `branchAnswers.templateDisambiguation` as an unconditional override, ahead of any score.
5. **A seventh template, `food-hospitality`**, was added — same depth as the other six (20 tasks, 3 branch questions, a real food-safety compliance task with `requiresProfessionalVerification: true`) — rather than leaving food/meal businesses to blend awkwardly across `local` and `service` (which, even once correctly routed there, pulled in `service`'s B2B sales-pipeline tasks — lead qualifier, outreach drafter — a poor fit for a consumer subscription business).
6. **`meal-prep-subscription.json` and `barbershop.json` are now permanent fixtures** in `test/fixtures/` (run automatically by `test/run-differentiation.ts`, no code change needed to include them going forward) — this exact regression class cannot silently return unnoticed.

**Verified against a real re-run, not just the regression check:** meal-prep now resolves to `food-hospitality` alone, confidently (score 3 vs. the next-best's 2, no blend) — the real customize pass added a BC food-safety/labelling compliance task, delivery-zone routing, cold-chain packaging inventory, subscription pause/churn handling, and a subscriber onboarding sequence; removed B2B invoicing as a poor fit for a pure consumer subscription. Zero software-product agents, zero B2B sales-pipeline agents — the two failure modes this ADR exists to close.

## ADR-024 — R2: the Charter becomes a versioned entity, and its prompt cascade is generated deterministically, never by an LLM

**Date:** 2026-08-13

**Context:** `docs/architecture/automation-runtime-plan.md` §2 describes R2 — the Charter compiler, editor, handoff ceremony, and three-tier prompt cascade (CEO / role-lead / sub-agent) — as the layer that turns an assembled org chart into something that actually runs. Before this ADR: a Charter *draft* already existed (`packages/agents/contracts/src/charter.ts`'s `Charter` interface, generated by the extraction pipeline's onboarding-batch call, issue #4) but was purely illustrative — never versioned, never tenant-owned, embedded only as JSON inside `signup_extraction_batches.org_chart`, with no state machine and no path to becoming the thing a prompt cascade could install from. Nothing composed a system prompt for any agent at all: `apps/router`'s `RouterTask`/`RouterTaskInput` had no prompt field, and `OpenMultiAgentExecutor` never populated `runAgent`'s (already-supported, just-unused) `systemPrompt` option.

**A citation error in the plan doc, caught before writing any code:** §2 attributed the "immutable role prompts... composed by the router per dispatch" rule to "ADR-011." ADR-011 (above) is about interview-question design (value-chain vs. founder-preference questions) and has nothing to do with prompts — full-text search of this file confirms zero occurrences of "prompt" or "immutable" outside this ADR. The actual rule lives in `docs/architecture/security-architecture.md` §4 (Ring 2: "Own system prompt (immutable per dispatch)") and §5.1 ("the agent's system prompt is composed by the router per dispatch from the versioned Charter + role definition; nothing an agent reads can modify it"). Similarly, "T10" (the CEO-recommender-only rule) is named directly in `security-architecture.md`'s threat table, not as a DECISIONS.md ADR label — the ADR that actually establishes it is **ADR-004** ("CEO agent is a recommender by architecture"), which the approval-queue package already enforces structurally: `RecommendationItem` has no `effect` field at all (not even `undefined`), and `submitRecommendation` throws if one is smuggled in via `as any`. The plan doc's citation is corrected in place (§2) to point at the real sources instead of silently leaving a wrong pointer for the next person who goes looking.

**What already existed vs. what R2 actually needed to add** — checked before designing, not assumed:
- The draft `Charter` shape covered `sharpenedIdea`, `mvpDefinition`, a bare `roleTasks: {roleTitle, tasks}[]` list, `monthOneGoals`, and a `budgetCeilingPlaceholder` — explicitly documented as a placeholder string ("you'll set a real ceiling when you connect your keys") because the interview never collects a budget figure.
- Missing: **role mandates** (an authority/scope statement per role, not just its task list), a **real numeric budget ceiling**, a **state machine** (draft → active → superseded, versioned, tenant-owned), and the **entire prompt cascade** — none of which existed anywhere.

**Decision:**

1. **Charter compiler — the mandate/ceiling split.** `roleTasks` is renamed `roleMandates`, gaining a `mandate: string` field per role, generated by the SAME haiku `generate_onboarding_batch` tool call the draft already used — a wider JSON schema on an existing call, not a new one. `budgetCeilingUsd` is no longer LLM-generated at all: the interview doesn't collect a budget figure, so asking the model to invent a dollar amount would produce a number disconnected from what actually gets enforced. It's resolved deterministically in code, post-call, to the exact same default the cost gate itself uses (`apps/api/src/routes/ceiling.ts`'s `DEFAULT_MONTHLY_CEILING_USD = 50`, duplicated as `packages/agents/extraction/src/onboardingBatch.ts`'s `DEFAULT_CHARTER_BUDGET_CEILING_USD` — extraction can't import from `apps/api`, ADR-015's ordering — kept in sync by comment cross-reference, not a shared import). **Measured cost delta: effectively zero.** Re-running the real 8-fixture differentiation suite before/after (see `test/results/differentiation-report.md`'s existing baseline, `$0.0348–0.0411/signup`) showed the mandate field adds a few dozen output tokens per role to an already-running haiku call — the ceiling computation costs nothing (pure code, no model call). No new LLM call was added anywhere in the batch.

2. **The versioned, tenant-owned Charter — a new entity, not a repurposed one.** `CompanyCharter` (new type, `packages/agents/contracts/src/charter.ts`) wraps `Charter` content with `id`, `tenantId`, `version`, `status: "draft" | "active" | "superseded"`, `cascade`, `createdAt`, `installedAt`. Persisted in a new `company_charters` table (migration `0008`, standard tenant-RLS pattern), created at **Charter acceptance** — not draft time — matching `master-plan-v2.md` Stage 4's actual ceremony and ADR-015's assignment of the org-chart-to-tenant handoff to exactly this moment. A partial unique index (`WHERE status = 'active'`) enforces at most one active version per tenant; accepting a new version supersedes the old one in the same transaction. The pre-acceptance draft (`OnboardingBatch.charterDraft`) is untouched and still the seed for the first `CompanyCharterStore.createDraft` call — two different lifecycle stages of the same content shape, not two competing sources of truth.

3. **The prompt cascade is generated deterministically — explicitly NOT an LLM call.** `packages/agents/extraction/src/cascade.ts`'s `generateCascade(charter, chart, previous?)` builds the CEO/role-lead/sub-agent prompt text from the Charter's own content and the org chart's own data (team mandates, task text, tool scopes, autonomy status) — same input always produces the same output, zero cost, zero latency, and nothing for a prompt-injection attempt to influence (the cascade never reads anything an agent or a user's connected tool produced). Stored as one JSONB blob on the `company_charters` row (`cascade`), regenerated wholesale on Charter edit — never a separate per-prompt table, matching the org chart's own existing "one JSONB blob" persistence pattern (`signup_extraction_batches.org_chart`) rather than introducing the first first-class per-agent DB rows in this codebase for what's still a fully derived artifact.

4. **Override preservation, enforced in the generator itself, not by convention.** Every generated prompt (`CeoPrompt`/`RoleLeadPrompt`/`SubAgentPrompt`) carries `overridden: boolean`. `generateCascade`'s regeneration path checks each `previous` entry first — an `overridden: true` entry is returned verbatim, never regenerated, until a human explicitly resets it. Covered directly in `cascade.test.ts`: an overridden CEO prompt survives a Charter content edit that changes every other prompt.

5. **T10 enforced structurally in the router, in front of the approval queue — not merely by routing to a different queue method.** `RouterTaskInput`/`RouterTask` gain `promptTier: "ceo" | "role-lead" | "sub-agent"` (default `"sub-agent"`, so every pre-R2 caller is unaffected) and an optional `systemPrompt`, threaded into `OpenMultiAgentExecutor`'s `runAgent()` call — the first real consumer of the library's already-existing, previously-unused `systemPrompt` option. In `router.ts`: a `promptTier === "ceo"` task's effect is forced to `undefined` **before** the approval-queue branch is ever reached (independent of, and in addition to, `RecommendationItem`'s type-level inability to hold one) and is submitted via `approvalQueue.submitRecommendation(...)`, never `submitProposedAction`. Two independent layers refusing the same thing is deliberate — "no matter what its prompt becomes" (T10's own wording) means the guarantee can't depend on a caller remembering not to pass `effect` for a CEO-tier task. Covered in `router.approvalQueue.test.ts`: a CEO-tier task never reaches `submitProposedAction`, and an effect requested on a CEO-tier task never dispatches, even with a real effect executor wired up. The durable `router_tasks` table gains matching `prompt_tier`/`system_prompt` columns (migration `0009`, with a `SCHEMA_CANARIES` entry — this is an `ALTER TABLE ADD COLUMN`, exactly the class of migration ADR-022 exists to catch if it's ever skipped) so a durably-replayed idempotent task reconstructs the same `promptTier` its caller originally set, not a silently-wrong default.

6. **The handoff ceremony reuses the existing claim endpoint's design intent exactly as it was written.** `apps/api/src/routes/me.ts`'s `POST /claim-org-chart` comment already said, back when it was built: "structured as its own idempotent operation so the Charter-acceptance screen (#16) can call the exact same endpoint later without this route or its logic changing at all, just the caller." That held — `/claim-org-chart` is untouched. The new `POST /me/charter/draft/:id/accept` (`apps/api/src/routes/charter.ts`) calls `generateCascade` against the tenant's already-claimed org chart and installs the result. `apps/web`'s `OnboardingScreen.tsx` now navigates to the new `/charter` screen instead of straight to `/dashboard` once org creation + claim succeed — the Charter review/edit/accept screen (`CharterScreen.tsx`) is what now owns the final `/dashboard` navigation, once the ceremony completes.

7. **Known, deliberate scope gap — not fabricated as done.** The plan's cascade-regeneration triggers are "Charter edit, agent rename, or autonomy change." Only the first is wired end-to-end in R2: `generateCascade` is called (and correctly preserves overrides) whenever a Charter is accepted, including a re-accepted "reopened" edit. Post-claim agent rename and autonomy-change endpoints **do not exist yet** — `packages/db`'s PR #94 explicitly scoped org-chart editing (`reassemble`/`rename-agent`) to pre-claim only ("a post-claim revisit to `/org-chart` can view but not edit"), and no autonomy-grant endpoint exists in `apps/api` at all yet. `CompanyCharterStore.updateActiveCascade` exists and is ready to be called once those mutations exist — but nothing calls it yet, and this ADR says so plainly rather than wiring a call to a codepath that doesn't exist or silently claiming the trigger is complete. This is the same honesty standard ADR-013 set for `Agent.brain: null`: a documented, complete gap, not a stub dressed up as done.

**Verified:** full-monorepo typecheck; `templates:test`/`extraction:test`/`router:test`/`api:test`/`web:test` all green, including new coverage — `cascade.test.ts` (generation, per-tier correctness, override preservation, content-edit regeneration), `charter.test.ts` (draft creation/idempotency/reopen-seeding/edit/accept, all 404/409 paths), `router.approvalQueue.test.ts`'s three new T10 tests, `openMultiAgentExecutor.test.ts`'s two new systemPrompt-threading tests. No trust-core test was deleted or weakened to make this land.

## ADR-025 — R3: the scheduler ships cadence triggers only, reuses Router.submitTask entirely for dispatch, and the tier-floor naming is reconciled to what's actually shipped

**Date:** 2026-08-13

**Context:** `docs/architecture/automation-runtime-plan.md` §3(a)/§7/§8 describe R3 as the smallest useful subset of the scheduler: BullMQ repeatable jobs driven by R1's cadence metadata, per-tenant scheduling, a pre-flight cost-gate check on every scheduled dispatch, pause-on-exhaustion with a resumable record, cadence floors per tier baked into the data model from day one, and the §7 instrumentation meter built alongside the scheduler rather than retrofitted later.

**A real prerequisite gap, found before writing scheduler code, not assumed away.** R1 (ADR entry 2026-08-13, "R1: cadence metadata on every sub-agent template task") added `cadence`/`batchable`/`triggerType` to `TemplateTask` (`packages/templates`) — but never to the assembled `Task` the extraction pipeline actually persists and the API serves (`packages/agents/contracts/src/orgChart.ts`). Checked directly: `pipeline.ts`'s `templateTaskToTask` (`{...t, origin: "template"}`) happened to carry the data through at the JS-object level via spread, but `Task`'s TypeScript shape never declared the fields, so nothing could read them in a type-checked way — and the customize-added-task path (`addedTasks`, built from the customize LLM's own `CustomizeAddition` output) never had the data at all, since a customize-added task has no template to inherit from. A scheduler built on top of this would have had no real cadence data to schedule from. Fixed as part of this PR, not deferred:
1. `Task` (contracts) gains `cadence`/`batchable`/`triggerType`, matching `TemplateTask` exactly.
2. `packages/agents/extraction/src/scheduleMetadata.ts`'s `deriveScheduleMetadata(frequency, agentType)` derives the same three fields **deterministically** for customize-added tasks — no second LLM call — calibrated against R1's own keyword-based heuristics (triage/escalation → event; expense-shaped → nightly-batched; cashflow/forecast-shaped → weekly; tax-shaped → monthly; inventory/reorder-shaped → threshold; `adhoc` frequency → event; otherwise cadence maps 1:1 to frequency), matched on agentType *keywords* rather than exact template ids, since a customize-added task's agentType is idea-specific and won't literally match a template's.
3. Every existing `Task`-literal construction site across the repo (test fixtures, the reassemble edit-op's zod schema in `apps/api/src/routes/extraction.ts`, `apps/web`'s client-side "add a custom task" feature) updated to carry the new required fields — found exhaustively via `npm run typecheck`, not by guessing which call sites existed.

**The tier-floor naming had to be reconciled, not invented fresh.** Plan §7 names its cadence-floor tiers "Founder $29 / Operator $79 / Agency $199." Checked against the actual shipped product before building anything: `apps/web/src/lib/pricingConstants.ts`'s `PRICING_TIERS` — the single source of truth for the real `/pricing` page — names them **Solo / Company / Scale**, with `priceLabel: "—"` (no monthly price has been set by product yet, an explicit, honest placeholder already in that file). "Founder/Operator/Agency" appears nowhere else in this codebase's real pricing surface; `docs/product/roles-and-api-key-guide.md`'s one "FOUNDER/CEO" hit is the org-chart role, not a subscription tier. No `tenants.tier` column existed at all, and no tier-selection UI exists anywhere in the signup/onboarding flow.

**Decision on naming:** the plan's real INTENT — three tiers, cadence floor tightening from daily → hourly → 15min as the tier goes up — is preserved exactly; only the LABELS change, to the tiers this product actually ships (`solo`/`company`/`scale`). `tenants.tier` (migration `0010`) defaults to `'solo'` — the most conservative (slowest) floor, fail-closed, since nothing selects a tier yet and no pricing is finalized. `packages/jobs/src/cadenceFloors.ts`'s `CADENCE_FLOOR_BY_TIER` and its UI-facing clamp-reason string (`"Runs daily on Solo — hourly available on Company."`) both use the real names, so a future pricing-tier UI never has to translate between two competing naming schemes.

**Decision — scope and design, point by point:**

1. **Cadence floors, clamped at schedule time, not run time (plan §7 rule 1).** `clampCadenceToTierFloor(declared, tier)` is a pure function: a task's declared cadence faster than its tenant's tier floor is rewritten to the floor's cadence, with a visible reason, computed once when the schedule is synced — never silently re-evaluated or dropped per-firing. Soft run-caps (§7's 50/300/1000 runs/day) are **not** enforced in R3 — only measured, via the instrumentation meter below; the plan's own §7 instrumentation section frames the caps as *"modelled, not measured, and should be treated as a starting hypothesis"* that the meter exists to correct, which only makes sense if enforcement is a later, data-informed step, not this one. Not fabricated as done.

2. **The real BullMQ API turned out to be better than what the plan doc's own phrasing ("repeatable jobs") implied — corrected mid-build, not shipped wrong.** The installed `bullmq@6.0.5` exposes `upsertJobScheduler`/`getJobSchedulers`/`removeJobScheduler` (BullMQ's newer "Job Scheduler" API), not the older `add({repeat})`/`getRepeatableJobs`/`removeRepeatableByKey` API this file's first draft assumed by name-pattern-matching the plan's prose. Caught for real by `npm run typecheck` failing against the actual installed type definitions (`Queue` didn't structurally satisfy the first-draft `RepeatableQueueLike` interface) — not discovered by reading docs first, but the mismatch was root-caused against `node_modules/bullmq`'s real `.d.ts` before redesigning, not patched around. `upsertJobScheduler` does an atomic create-or-update in one call keyed by a caller-chosen id, which is a strictly better fit than the old API's separate add/list/remove-by-derived-key dance — `packages/jobs/src/tenantScheduler.ts`'s `syncTenantSchedule` is simpler than its first draft because of this, not more complex.

3. **`packages/jobs` stays generic; the trust-core-touching orchestration lives in `apps/api`.** Same split `apps/api/src/extraction/runExtractionBatch.ts` already established for extraction (ADR-014): the reusable primitive (cadence-floor math, BullMQ sync logic) has no dependency on `@byok/router`/`@byok/cost-gate`/`@byok/db` and is fully unit-testable without Redis or Postgres; `apps/api/src/scheduler/computeDesiredSchedule.ts` (pure — Charter + org chart + tier → desired jobs) and `scheduledDispatchProcessor.ts` (the actual worker body) are where the real dependencies get wired.

4. **The scheduled-dispatch worker's whole job is composing the right input for `Router.submitTask` — R2 already does everything else.** T10 enforcement, the cost gate, the approval queue: all of it is already correct in `Router.submitTask` (ADR-024). `scheduledDispatchProcessor.ts` looks up the tenant's active Charter cascade, resolves `promptTier` from the dispatching agent's team (`"founder"` → `"ceo"`, everything else → `"sub-agent"`), resolves the model via the exact same `TierModelMap` every other `Router.submitTask` caller uses (now threaded onto `TrustCoreDeps` — it was constructed inline in `devTrustCore.ts` before and never exposed), and calls `submitTask`. No new cost-gate call, no new approval-queue logic, no second T10 check — one path, already proven in R2.

5. **Pause-on-exhaustion reuses the pre-existing, previously-unwired `DurableBatchStore`/`paused_batches` mechanism (`packages/cost-gate`) — this PR is its first real caller.** Checked before building a second mechanism: `BatchExhaustionManager`/`PostgresDurableBatchStore` already existed, fully built and tested, for exactly this "pause, preserve what's needed to resume, resume later" shape — nothing in `apps/api` had ever constructed or called it. `Router.submitTask` returning `"queued"`/`"skipped"` is, today, unambiguous evidence of a cost-gate ceiling verdict (the only code path that produces those two statuses) — the worker treats either as exhaustion, pauses the tenant via a new `tenant_schedule_state` row (migration `0010`) pointing at a real `paused_batches` record, and every subsequent job firing for that tenant becomes a cheap no-op (checked before any Charter/org-chart lookup) until `POST /me/scheduler/resume` clears it. The underlying BullMQ Job Schedulers are never removed while paused — only the worker's own pause check short-circuits them — so resuming needs no re-sync to pick back up.

6. **The §7 instrumentation meter is built now, with the scheduler, exactly as instructed — including the two columns nothing calls yet.** `scheduler_instrumentation_daily` (migration `0010`) has `scheduled_runs_executed`/`worker_seconds_consumed`/`ledger_rows_written` (incremented for real by `scheduledDispatchProcessor.ts` on every firing) and `event_triggers_received`/`chain_steps_completed` (columns exist, `SchedulerInstrumentationStore.recordEventTrigger`/`recordChainStep` exist — R5/task chains and R6/event triggers are what will actually call them). `ledger_rows_written` mirrors `router.ts`'s own `ledger.append` call count for each code path exactly (2 for QUEUE/SKIP — pending + terminal, no in_progress; 3 for everything else) rather than a guessed constant. Zero rows with nonzero values in the two not-yet-wired columns is the honest current state.

7. **The worker runs in-process with the HTTP server, not as a separate deployable — a direct lesson from this repo's own incident record.** `docs/TRACKING.md`'s "Railway auto-detects workspace packages as deployable services" entry: an accidentally-auto-provisioned second Railway service crash-looped for days because it inherited the wrong start command. A dedicated worker process is a legitimate future scaling change; reaching for it now, in a repo that has already been burned once by an extra deployable appearing where only one was intended, isn't free just because it's the more conventionally "correct" shape. `REDIS_URL` — already wired through CI and `deploy-staging.yml`, already documented in `.env.example`, never previously consumed by any code — required, same discipline as `DATABASE_URL`.

8. **`packages/jobs/` added to CODEOWNERS**, same reasoning already on record for `packages/db/`: it went from a generic, unused BullMQ wrapper to the thing that decides when an unattended, spend-triggering dispatch fires and enforces the cadence-floor cost-safety limits — load-bearing for trust-core now, same review bar.

**Verified:** full-monorepo typecheck (including the real installed BullMQ types, not assumed ones); `templates:test`/`extraction:test`/`router:test`/`db:test`/`jobs:test`/`api:test` all green — new coverage includes `scheduleMetadata.test.ts` (every heuristic + the fixed-frequency fallback), `cadenceFloors.test.ts` (every tier boundary, including that Scale is never clamped), `tenantScheduler.test.ts` (add/remove/unchanged/cadence-change-triggers-re-upsert, and strict per-tenant isolation on a shared queue), `computeDesiredSchedule.test.ts`, `scheduledDispatchProcessor.test.ts` (cascade-prompt composition for both CEO and sub-agent tiers, the paused-tenant no-op, both ledger-row-count branches, both QUEUE/SKIP-triggers-pause branches, and both "no active Charter" / "stale agent or task id" failure modes), and `scheduler.test.ts` (the sync/status/resume routes, including the clamp-reason surfaced end to end).

## ADR-026 — Staging boots on durable CostGate/ApprovalQueue storage, not dev wiring; Router's ledger/dedup stay in-memory, tracked separately

**Date:** 2026-08-14

**Context:** Driving the real staging verification R3's own review demanded — a scheduled dispatch firing unattended, hitting the cost gate, landing in the approval queue, recording in `scheduler_instrumentation_daily` — surfaced that `apps/api/src/start.ts` (the staging entrypoint) had booted on `createDevTrustCore()` since before R3 existed. That wiring's own comment said so plainly and, at the time, correctly: staging's original job was proving auth → tenant → RLS-scoped API resolves end to end, "which never touches trust-core's `/tasks` route." R3 is the first thing that actually calls `Router.submitTask` unattended in that environment, and the claim stopped being true the moment it shipped — nobody revisited the wiring decision when the thing it was scoped around changed.

Concretely, under `createDevTrustCore`: `CostGate` was built on `InMemoryDurableReservationStore` — real per-tenant ceiling enforcement for the life of one process, reset on every restart. `ApprovalQueue` had **no durable storage at all** — `pending`/`pendingRecommendations` were plain in-memory `Map`s inside `packages/approval-queue/src/queue.ts` itself; `PostgresDurableApprovalStore` existed, fully built and exported, but nothing in the codebase ever constructed it. A scheduled dispatch landing in the approval queue was real within that process's lifetime but invisible to any query, any route, or the next redeploy — there was no way to durably prove "the task landed in the approval queue" no matter how long staging ran.

**Decision — what became durable:**

1. **CostGate's reservation store** — a clean swap, `InMemoryDurableReservationStore` → `PostgresReservationStore` (`packages/cost-gate/src/durable/reservationStore.ts`), same `DurableReservationStore` interface, already covered by a real-Postgres `.itest.ts` suite. No other change to `CostGate`'s construction.

2. **ApprovalQueue's pending-item storage** — not a swap, a real build: `ApprovalQueue` (`packages/approval-queue/src/queue.ts`) had no constructor slot for `DurableApprovalStore` at all before this. It gained a 4th constructor parameter, `store: DurableApprovalStore = new InMemoryDurableApprovalStore()`, and `submitProposedAction`/`resolve`/`submitRecommendation`/`resolveRecommendation`/`pendingActions`/`pendingRecommendationItems` now read and write through it instead of the local Maps, which are gone. This is a breaking API change — `resolve`, `resolveRecommendation`, `pendingActions`, and `pendingRecommendationItems` now take a leading `tenantId` (matching `DurableApprovalStore`'s own tenant-scoped, RLS-friendly shape, and every other durable store in this codebase), and `submitRecommendation`/`resolveRecommendation` are now async. Checked before making the change, not after: grepping every real (non-test) call site in the monorepo found exactly one, `Router`'s `submitRecommendation(item)` call (now `await`ed) — everything else touching these methods was test code, updated to match. `PostgresDurableApprovalStore` writes through the same `withTenantScope`/`audit_log` mechanism `PostgresReservationStore` already used, via a shared `PostgresDurableAuditLog` instance passed to both — meaning a scheduled dispatch's approval-queue submission now shows up in `GET /dashboard`'s `recentActivity` (`audit_log`-backed) for real, which it structurally could not before.

3. **A construction guard, ADR-007/008-style, allowlist not denylist.** `packages/vault/src/env.ts` gained `isDevOrTestEnvironment()` — true only when `NODE_ENV` is unset, `"development"`, or `"test"`. `InMemoryDurableReservationStore` and `InMemoryDurableApprovalStore` both throw (`DevOnlyReservationStoreGuardError` / `DevOnlyApprovalStoreGuardError`) if constructed outside that allowlist. This is deliberately an allowlist rather than `isProductionEnvironment()`'s denylist: a new deploy target added later (staging today; whatever comes after) defaults to **refused**, not silently accepted, which is the direction this exact class of bug — dev wiring reaching a deployed environment unnoticed for months — needs to fail in. `apps/api/src/durableTrustCore.ts` is the new staging-appropriate construction (`start.ts` now calls it instead of `createDevTrustCore`); `apps/api/src/dev/devTrustCore.ts` (`dev.ts`, local dev) is untouched and still uses the in-memory stores, which is correct — `NODE_ENV` is unset there, so the guard passes.

**Decision — what deliberately did NOT become durable, and why:** Router's `TaskLedger` (`apps/router/src/ledger.ts`) and `DedupStore` (`apps/router/src/dedup.ts`) stay in-memory. Durable counterparts exist (`PostgresDurableTaskLedger`, `PostgresDurableDedupStore`, `apps/router/src/durable/`) but implement different, **async** interfaces (`DurableTaskLedger`, `DurableDedupStore`) than what `Router`'s constructor requires (the synchronous `TaskLedger`/`DedupStore`) — not a drop-in swap the way `CostGate`'s reservation store was. Making them durable means converting roughly ten synchronous ledger/dedup calls inside `Router.submitTask` to async, plus making the public `ledgerFor()` method async — a real, separate change, scoped out of this ADR deliberately rather than rushed into the same PR as the approval-queue work. Tracked in issue #120 (filed alongside this ADR): it becomes **required**, not optional, before any multi-replica deployment or real production traffic — an in-memory dedup store that only one replica can see means the same task can dispatch, and be paid for, twice under concurrent replicas. Single-replica staging today is not exposed to that risk; it will be the moment a second replica exists.

**What "staging now uses durable trust-core wiring" means, precisely, after this change:** the approval queue and the cost-gate reservation ledger survive a restart. The task ledger and the dedup store do not. Anyone extending this later should not assume the second half without checking — this ADR exists specifically so that assumption doesn't have to be reverse-engineered from the code.

**Verified:** full-monorepo typecheck; `approval-queue:test`/`router:test`/`cost-gate:test`/`vault:test`/`api:test` all green, including `queue.test.ts` and `router.approvalQueue.test.ts` updated for the new tenant-scoped async signatures, and `env.test.ts` (new) covering the allowlist guard's boundary. No staging deploy has yet been run against this wiring at the time of writing — that is the next step, not assumed complete here.

## ADR-027 — `bullmq`/`ioredis` are pinned exact together, and every Redis connection is guarded with a bounded readiness timeout

**Date:** 2026-08-18

**Context:** R3's scheduled dispatch never fired a single real time in staging — traced over several sessions through a Redis TLS-scheme bug (fixed) and a Postgres connection-pool bug (fixed, ADR/PR #131) before the actual root cause surfaced: `packages/jobs`'s `ioredis` dependency was `6.0.0` — at the time of writing, `ioredis`'s **only** 6.x release (plus a beta), meaning this codebase was running the newest, least-battle-tested major version of its Redis client in a trust-adjacent path, with no evidence anyone deliberately chose it. Git history confirms this directly: the commit that first added `packages/jobs/package.json` (2026-08-01) already had `"ioredis": "6.0.0"` hardcoded exactly, with no discussion of the version anywhere in that commit's message — consistent with `npm install ioredis` simply resolving to whatever was current the day `bullmq@6.0.5` (which made `ioredis` an *optional* peer dependency rather than requiring it directly, precisely so callers could choose) was adopted. Nobody chose 6.x; the tooling defaulted to it.

Direct diagnosis (a token-gated `/internal/scheduler-debug` route built for this investigation, hitting the live queue from inside Railway's own network) proved the underlying `ioredis` connection was stuck at `RedisConnection.status === "initializing"` **indefinitely** — never `"ready"`, never erroring, never closing. Every downstream BullMQ call (`getJobCounts`, `getJobSchedulers`, and by extension `syncTenantSchedule`'s registration path) hung forever as a result, silently. `commandTimeout` never helped, because it only bounds a command *after* it's dispatched — `RedisConnection.waitUntilReady()`, bullmq's own connection-bootstrap step that must complete before any command can be sent, has no timeout of its own in bullmq's source.

**Decision, part 1 — pin the pair, not just one half.** Pinning `ioredis` alone to a stable `5.x` was tried first and failed immediately and loudly: `bullmq@6.0.5`'s compiled code imports directly from `ioredis/built/utils`, an internal path that exists in `ioredis@6.0.0`'s package layout but not `5.x`'s — a hard `MODULE_NOT_FOUND` crash on require, not a subtle bug. `bullmq@5.81.3` (the current 5.x release) exact-pins its own `ioredis` dependency to `5.11.1` — the same version independently chosen here as "latest stable 5.x" — which is strong, direct evidence this is the pairing bullmq's own maintainers actually build and test against. Both packages moved together: `bullmq: "5.81.3"`, `ioredis: "5.11.1"`, both exact per ADR-006's pinning discipline (no `^`/`~`, lockfile committed) — extended here from ADR-006's original "trust-core dependencies" scope to this scheduler-critical pair, on the same reasoning: an unpinned version drifting underneath a system this deep in the dispatch path is exactly the risk ADR-006 exists to close, whether or not `packages/jobs` is formally CODEOWNERS-locked. `bullmq`'s Job Scheduler API (`upsertJobScheduler`/`getJobSchedulers`/`removeJobScheduler`) this codebase depends on predates the 6.x line and is present and type-compatible in `5.81.3` — confirmed by a clean typecheck and full test pass, not assumed.

**Decision, part 2 — a connection that never becomes ready must fail loud, on any version.** `packages/jobs/src/connectionHealth.ts`'s `trackConnectionHealth(client, timeoutMs = 15000)` races a Queue's or Worker's own public `waitUntilReady()` against a hard timeout, returning a live object (`{status: "initializing" | "ready" | "error", error?, readyAtMs?}`) mutated in place as the real outcome resolves — readable synchronously by anything holding a reference, without awaiting. On timeout or underlying error, it `console.error`s loudly. This is deliberately built against `waitUntilReady()` — BullMQ's own stable, public readiness API — not against `ioredis`- or `bullmq`-version-specific internals, so the guard survives whichever version pair is installed next; it would have caught the `6.0.0` hang immediately as a loud `"error"` status instead of the two-day silent investigation this session actually took.

**Decision, part 3 — surfaced as a first-class signal, not just a diagnostic.** Both the Queue's and Worker's connection health are threaded through `server.ts` into `createApp`, and from there into two routes: `GET /health`'s body now includes `redis: {queue, worker}` status strings (never the raw error message — that stays behind the token gate) so "the API reports healthy while its queue backend is dead" — the exact pattern that made this investigation take two days instead of two minutes — is no longer possible to miss. The HTTP status code stays `200` unconditionally, deliberately: Railway's own deploy verification gates on that status code, and a connection legitimately spends its first few seconds at `"initializing"` on every normal cold start — flipping the status code during that window would fail healthy deploys, trading one false-negative pattern for another. `GET /internal/scheduler-debug` (already token-gated, built earlier in this same investigation) now reports the same `connectionHealth` object alongside its `getJobCounts`/`getJobSchedulers` differential probes, replacing an earlier version of that route that reached directly into BullMQ internals (`Queue#getBackend().connection.status` — necessary at the time, since 6.x had just removed the public `Queue#client`) with this permanent, version-independent equivalent.

**Verified:** `npm run build`/`npm test` for `@byok/jobs` and `@byok/api` — both clean and fully green — run via each workspace's own `npm run build`/`test` script rather than a bare `npx tsc`, after discovering mid-investigation that this repo has no root-pinned TypeScript version at all: `npx tsc` from the repo root resolves to whatever floating version happens to hoist there (`6.0.3` at the time of writing, itself unpinned and untested against), not any individual package's own declared range. That produced a run of entirely spurious type errors against `packages/jobs` (a `Queue` generic-inference mismatch, `node:test`/`node:assert` "cannot find name," a `setTimeout(...).unref()` type error) that vanished completely once verified through the correct, package-local compiler. Left as a known, currently-unfixed gap — a future session should give this repo an explicit root-level `typescript` devDependency pin so `npx tsc` and CI use the same, deliberately-chosen version every package is actually developed and tested against, rather than whatever the dependency graph happens to hoist.

**Not yet confirmed at the time of writing:** whether the pinned `bullmq@5.81.3`/`ioredis@5.11.1` pair's Redis connection actually reaches `"ready"` in staging — that is the next, immediate verification step, not assumed complete by this ADR.

## ADR-028 — Full trust-core durability audit; Vault's key storage becomes durable; a guard only lands with its own fix, never before

**Date:** 2026-08-21

**Context:** Scoping "wire the real executor into scheduled dispatch" surfaced that `Vault` (`packages/vault/src/vault.ts`) stored every tenant's Brain and Hands key material — and the per-tenant DEK that encrypts it — entirely in plain JS `Map`s, with zero durability: a restart or redeploy silently lost every connected key, with no error, no warning, no way to detect it short of a user reporting "my key disconnected." This was the **third** in-memory store found gating genuinely trust-relevant behavior in three weeks (`ApprovalQueue`'s pending-item storage and `CostGate`'s reservation store, both fixed by ADR-026), which prompted a full audit of every in-memory store in trust-core rather than fixing this one and moving on — the ask being: find the rest now, at design time, not one at a time over the following weeks.

**The audit — every trust-core store, durable or not, as of this session:**

| Store | Holds | Status | Durable counterpart |
|---|---|---|---|
| `ApprovalQueue` pending items | Queued actions/recommendations awaiting human review | **Durable** (ADR-026) | `PostgresDurableApprovalStore` |
| `CostGate` reservation ledger | Per-tenant spend reservations against the monthly ceiling | **Durable** (ADR-026) | `PostgresReservationStore` |
| `Vault` key records + DEK | Brain/Hands key ciphertext, the per-tenant DEK that decrypts it | **Durable (this ADR)** | `PostgresVaultKeyStore`, `PostgresDekRecordStore` |
| `Router`'s `TaskLedger` + `DedupStore` | Task execution history, in-flight dedup keys | **Not durable** | `PostgresDurableTaskLedger`/`PostgresDurableDedupStore` exist but require `Router`'s constructor to go async — issue #120, explicitly deferred by ADR-026 itself |
| `ApprovalQueue`'s `AutonomyEngine` | Earned-autonomy consecutive-approval counters, active/spot-check state | **Not durable** | `PostgresDurableAutonomyStore` exists (`packages/approval-queue/src/durable/autonomyStore.ts`, fully built and itest-covered) but was never wired in — `AutonomyEngine`'s interface is synchronous, the durable store's is async, same shape of gap as `TaskLedger`/`DedupStore`. Sized this session: ~30 call sites, mostly test construction of `ApprovalQueue` with a concrete `AutonomyEngine`; scoped as the next durability task |
| `CostGate`'s own audit log (`GateAuditLog`) | The gate's internal decision trail — distinct from the shared `audit_log` table `PostgresReservationStore` writes to | **Not durable, previously undocumented** | None exists. `durableTrustCore.ts` constructs `CostGate` without a 5th argument, so it silently defaults to `InMemoryGateAuditLog` even in the "durable" trust core |
| `Vault`'s own audit log (`AuditLog`) | Every key store/rotate/revoke/decrypt-granted/decrypt-denied event | **Not durable, previously undocumented** | None exists. Same pattern: `durableTrustCore.ts`'s `Vault` construction leaves `audit` at its default `InMemoryAuditLog` |

The last two rows were not previously known or discussed — they surfaced only because this audit deliberately checked every constructor's default-parameter fallbacks in the durable trust-core wiring, not just the stores that had already been flagged. Both are undocumented in any ADR prior to this one. The Vault audit log is the higher-priority of the two: it is a security audit trail (every decrypt grant/denial against tenant credentials), and one that silently vanishes on every restart is the wrong thing to discover after an incident rather than before one. Issues tracking both are filed alongside this ADR: [#149](https://github.com/veltrixnextgen-arch/byok-business-autopilot/issues/149) (Vault's audit log) and [#150](https://github.com/veltrixnextgen-arch/byok-business-autopilot/issues/150) (CostGate's audit log).

**Decision — Vault's key storage becomes durable.** `packages/vault/src/durable/vaultKeyStore.ts` (`VaultKeyStore` interface, `InMemoryVaultKeyStore`, `PostgresVaultKeyStore`) and `durable/dekRecordStore.ts` (`DekRecordStore`, `InMemoryDekRecordStore`, `PostgresDekRecordStore`) replace `Vault`'s internal Maps. Migration `0011_vault_durable_storage.sql` adds `tenant_deks`, `brain_keys`, `hands_keys`, all RLS-enabled/forced with `tenant_isolation` policies, all key material columns `BYTEA` (ciphertext/iv/authTag only — plaintext never reaches Postgres). `Vault`'s public interface was already fully `Promise`-returning before this change, so every real caller needed zero signature-shape changes to adopt real I/O — the same async-interface property that made `CostGate`'s reservation-store swap clean in ADR-026, and the reason this fix, unlike `TaskLedger`/`DedupStore`/`AutonomyEngine`, was safe to do in one contained PR rather than needing its own separate scoping pass. `HandsKeyProvider.decryptHandsKey`/`resolveHandsKeyId` did gain a leading `tenantId` parameter (key records are now RLS-scoped Postgres rows, not a flat Map, so the lookup itself needs the tenant to scope by) — every real call site (`handsTool.ts`, `openMultiAgentExecutor.ts`) already had `tenantId` in scope, so this was a mechanical, not structural, change. Proven via `packages/vault/src/durable/vaultDurability.itest.ts` against a real Postgres: round-trip decrypt correctness, ciphertext-only storage (the raw row is asserted to never contain the plaintext), AAD scope-binding surviving the storage swap, `SecretHandle`'s TTL-zeroing behavior unchanged, and two RLS cross-tenant read tests (by guessed role id, and by exact key id) proving Postgres itself — not application-level filtering — is what blocks a cross-tenant read.

**Restart-mid-write safety.** Every real persistence operation here — `DekRecordStore.putIfAbsent`, `VaultKeyStore.putBrainKey`/`putHandsKey` — is a single Postgres statement. A crash between creating a tenant's DEK and writing the key record that would use it (`DekStore.getOrCreateDek`'s two-step sequence, see its own code comment) can only ever leave the DEK row committed and the key record row absent — never a half-written key record — because Postgres statement-level atomicity means each row is either fully committed or doesn't exist. The worst case is a harmless orphaned DEK, transparently reused by the next `getOrCreateDek` call for that tenant via its existing get-first branch. `vaultDurability.itest.ts` proves this directly: it simulates the crash window (create + persist a DEK, deliberately never write a key record), confirms no key row exists, then proves a subsequent real `storeBrainKey` call succeeds and reuses the orphaned DEK rather than erroring or duplicating it.

**Decision — the construction guard only lands with its own fix, never before.** `InMemoryVaultKeyStore`/`InMemoryDekRecordStore` both throw (`DevOnlyVaultKeyStoreGuardError`/`DevOnlyDekRecordStoreGuardError`) if constructed outside `isDevOrTestEnvironment()`, same ADR-007/008/026 allowlist pattern as `InMemoryDurableReservationStore`/`InMemoryDurableApprovalStore`. The general principle, articulated explicitly this session because it wasn't written down anywhere before: **a construction guard on an in-memory store is only safe to add at the exact moment that store's durable replacement is actually built AND wired into the real (staging/production) trust-core path.** Adding the guard earlier — before the durable replacement exists, or before it's actually plugged in — would make the server refuse to boot in production with nothing to fall back to, which is strictly worse than the silent-data-loss bug the guard exists to catch. This is precisely why `AutonomyEngine`, `CostGate`'s `GateAuditLog`, and `Vault`'s own `AuditLog` do **not** get a construction guard in this ADR: their durable replacements don't exist yet (or, for `AutonomyEngine`, exist but aren't wired in). Each guard lands in the same PR as its own fix, not before, not as a batch — the table above is the map of which stores still need both.

**Verified:** full-monorepo typecheck; `templates:test`/`extraction:test`/`db:test`/`auth:test`/`jobs:test`/`notifications:test`/`api:test`/`router:test`/`vault:test`/`cost-gate:test`/`approval-queue:test`/`web:test` all green (`vault.test.ts` fully rewritten for the new store-injection signatures, 36/36 passing; migration RLS-policy coverage added to `db:test`). `vaultDurability.itest.ts` type-checks cleanly against a real `@byok/db` pool and is wired into CI's Postgres-service-container job (`.github/workflows/ci.yml`, same `app_user`-role pattern as every other `.itest.ts` in this repo, so RLS is genuinely exercised, not just SQL-syntax-checked) — **not yet run against a live Postgres by this session directly**, since no local Postgres or Docker was available in the environment this work was done in; CI is where it gets its first real execution, and that run should be checked before this lands.

## ADR-029 — Deploy verification stops asking the platform what it deployed; the running process reports its own build SHA instead

**Date:** 2026-08-21

**Context:** Tagging `v0.6.23-staging` (this session, to deploy ADR-028's vault durability work) failed at `deploy-staging.yml`'s "Verify the deployment actually succeeded and is what's serving traffic" step — the third consecutive staging release (`v0.6.21`, `v0.6.22`, `v0.6.23`) to fail there, each in a genuinely different way, and this exact check had already been rewritten twice before that for two earlier failure modes (its own code comments document both). Three rewrites, three distinct failures:

1. **First version** matched `meta.commitHash` against `$GITHUB_SHA` — broke immediately (PR #133): `railway up`'s CLI-upload deploy path this workflow uses does not reliably populate that field. The deployment that actually became active/serving had no `commitHash` at all.
2. **Second version** matched by creation time instead (`created at/after deploy_start`) — broke on the very next run: `railway deployment list` sorted by `createdAt` can have a real `SUCCESS` entry followed chronologically later by an unrelated `SKIPPED` one (Railway's own native auto-deploy-on-push noticing nothing left to build and skipping), and "take the latest list entry" picked the harmless `SKIP`.
3. **Third version** asked `railway status --json` directly for the service's `activeDeployments[0]`, filtered by `createdAt >= deploy_start` — failed differently again on `v0.6.21` through `v0.6.23`: the field was never populated within the 300-second polling window at all (`id=none` for all 30 attempts), even though `railway status`'s plain (non-JSON) output, captured moments earlier in the same run, already showed `@byok/api: ● Online`.

Every version made the same category of mistake: it asked Railway's own API or CLI to describe its deployment record, in one shape or another, and that description proved unreliable specifically for the `railway up`-based CLI-upload deploy path this workflow has always used (a native git-webhook-triggered deploy would very likely behave differently — never tested here, since Railway's project is wired for CLI-upload deploys, not git integration). A check that has failed three consecutive real deploys in three different ways is not a flaky check being unlucky; it is a broken check, and a check that always fails trains the team to route around red rather than trust it.

**Decision — ask the running process, not the platform.** The actual question this step needs answered is "is the build currently serving traffic the one this run just produced" — and the process itself can answer that better than any external API describing it, regardless of deploy mechanism, Railway CLI version, or Railway's own JSON schema. `BUILD_SHA` is set as a Railway service variable to this run's `${{ github.sha }}` before every `railway up` call (`deploy-staging.yml`, alongside `DATABASE_URL`/`REDIS_URL`/etc.). `GET /health` (`apps/api/src/routes/health.ts`) now echoes it back verbatim as a `buildSha` field — `readServerConfigFromEnv` reads `BUILD_SHA` from the process's own environment (defaulting to `"unknown"`, not required, so local dev and any environment that hasn't opted in still boots fine), threaded through `ServerConfig` → `CreateAppOptions` → `healthRoute`. The verification step is now a single call to a new, standalone, reusable script — `apps/api/scripts/verify-build-sha.mjs <health-url> <expected-sha> [maxAttempts] [sleepMs]` — that polls the health URL and asserts `buildSha === expectedSha` exactly, matching the existing `apps/web/scripts/verify-staging-*.mjs` convention for extracted, independently-runnable staging-verification scripts. All of the old `railway status --json`/`railway deployment list`/`jq` parsing is gone — replaced, not patched a fourth time. The now-unused `deploy_start` output (recorded solely for the old creation-time-matching logic) was removed along with it.

**Proof the check can actually fail, not just pass — done before trusting it, per the explicit ask that a verification never observed failing correctly can't be trusted when it passes:**

1. **Logic-level, both directions, real network calls:** a local mock HTTP server was started returning `{"buildSha": "real-sha-abc123"}`, and `verify-build-sha.mjs` was run against it twice — once with the correct expected SHA (exit 0, "Confirmed: ... matching the expected ...", immediately) and once with a deliberately wrong one (exit 1 after exhausting `maxAttempts`, printing `::error::... never reported buildSha matching "wrong-sha-999" (last seen: real-sha-abc123) ...`). Both outcomes were the correct ones for their inputs.
2. **Live, against the real staging deploy:** `v0.6.24-staging` (carrying this fix, merged as PR #152) deployed clean end to end — every step green, including this one: `Confirmed: https://byokapi-production-6a57.up.railway.app/health reports buildSha=920117c55a0cfa6e5574c844f9b54f703017804b, matching the expected 920117c55a0cfa6e5574c844f9b54f703017804b.` Immediately after, the exact same script was run again directly against that same real, live URL with a deliberately wrong SHA — `Not yet matching ... expected 0000000000000000000000000000000000000wrong...` three times, then `::error::... never reported buildSha matching "0000...wrong" (last seen: 920117c...)`, exit 1 — and then once more with the real correct SHA, which matched immediately, exit 0. Both directions proven against genuinely live infrastructure, not a mock.

The script uses `process.exitCode` rather than calling `process.exit()` directly after an in-flight `fetch()` — an abrupt `process.exit()` racing `fetch()`'s (undici's) open keep-alive socket handles crashed with a libuv assertion (`UV_HANDLE_CLOSING`) during local testing on this session's Windows dev environment. Letting the event loop drain naturally avoids that race entirely; the CI runner is Linux (`ubuntu-latest`), where this specific crash likely wouldn't have reproduced anyway, but the fix is strictly more correct regardless of platform.

**What this does not fix:** Redis/`ioredis` connection health (ADR-027) and every other health-check-body concern are unrelated and untouched. This ADR is scoped entirely to "does the process answering `/health` know its own build" — a narrower, more reliable claim than "did Railway's API report a successful, promoted, currently-active deployment," which is what every prior version of this check tried and failed to establish indirectly.

**Verified:** `@byok/api` build and full test suite green (188/188, including two new `readServerConfigFromEnv` tests for `BUILD_SHA`'s presence/absence and `health.test.ts`'s existing suite extended to assert `buildSha` is echoed unmodified). Full monorepo typecheck clean. The workflow YAML parses. The negative/positive proof above ran against a real local HTTP server with real `fetch()` calls, not a mock of the script's own internals.

## ADR-030 — `createPool` bounds `connectionTimeoutMillis`/`statement_timeout`/`idle_in_transaction_session_timeout`; pool-wait saturation is now logged

**Date:** 2026-08-21

**Context:** Immediately after ADR-029's durability-proving redeploy (`v0.6.25-staging`), the first real sign-in for Acme — the first tenant with a real key stored in the new durable vault — hung indefinitely on "Signing in…" in the browser, and stayed stuck across page loads afterward. Investigating: sign-up and sign-in both reproduced cleanly for a brand-new throwaway account with no org/tenant history, ruling out a blanket regression in the auth flow itself. Every read/write in the new vault stores (`PostgresVaultKeyStore`, `PostgresDekRecordStore`) was confirmed to go through `withTenantScope` — no missing-scope bug was found, and direct evidence from this same session (an actual CI failure earlier: `invalid input syntax for type uuid: ""`) already shows what a genuinely unscoped RLS query does: it throws immediately. It does not hang. That ruled out the first, most obvious theory (a missed `withTenantScope` wrapper reading as "hang").

What actually explained "hangs, not errors" plus "stuck on other pages too" (not just the one route that touches the vault): `packages/db/src/connection.ts`'s `createPool` never set `connectionTimeoutMillis`. Checking `pg-pool`'s own source directly confirms that when this option is unset, a caller waiting for a free slot from a saturated pool (`max: 10`, unchanged) waits **forever** — no timeout, no error. Combined with two real, verifiable facts: (1) `tenant_deks`/`brain_keys` writes use `INSERT ... ON CONFLICT DO NOTHING`/`DO UPDATE`, which Postgres blocks on if another transaction touching the same conflicting key is still open and uncommitted; and (2) this session triggered two apps/api restarts in quick succession right around the same window (the durability redeploy immediately following the key connect). If any request touching Acme's `tenant_deks`/`brain_keys` row was genuinely mid-transaction when a container was killed, the resulting stuck lock would block every later write to that same row — and once enough of the pool's 10 connections queue up behind that lock, *any* other query on the same shared pool (including Better Auth's own sign-in lookup, which has nothing to do with the vault) hangs waiting for `pool.connect()` too, with nothing to observe except a hung page. This is the same silent-hang shape ADR-027 already found and fixed for the Redis/BullMQ connection — the second time this exact class of bug (an unbounded wait with no timeout, no log) has bitten this codebase.

**Decision — bound all three, not just the one that explains today's incident.** `createPool` now sets:
- `connectionTimeoutMillis` (default 10s) — how long to wait for a free pool slot or a new connection to establish.
- `statement_timeout` (default 30s) — how long any single query may run server-side, so a genuinely stuck query (not just a saturated pool) also fails loud.
- `idle_in_transaction_session_timeout` (default 30s) — how long a transaction may sit open with no activity. This is the one that would have prevented today's stuck lock from surviving past 30 seconds regardless of whatever Neon's own default happens to be — bounding it at our end rather than depending on the hosting provider's default.

All three are overridable per-caller (`DbConnectionOptions` gained `connectionTimeoutMillis`/`statementTimeoutMillis`/`idleInTransactionSessionTimeoutMillis`, all optional); every real caller (`dev.ts`, `start.ts`) uses the defaults. `packages/db/src/migrate-cli.ts` constructs its own raw `pg.Pool` directly rather than going through `createPool`, so migrations are unaffected by the new `statement_timeout` — deliberately not touched here, since a schema migration is a different risk profile than a per-request OLTP query.

**Decision — pool saturation is now observable, not just eventually bounded.** `logSlowConnectionWait` (a pure, unit-tested function — no real `pool.connect()` or live Postgres needed to test it) logs a loud `console.warn` whenever waiting for a connection takes longer than 2 seconds, well before the 10-second `connectionTimeoutMillis` would actually give up. This closes the actual gap that made today's incident take a human noticing a hung browser tab to discover: pool saturation creeping toward the ceiling is now a log line, not a silent, growing risk.

**A first version of that last decision introduced a second, worse live incident — caught in CI before merge, not after.** The first attempt wired `logSlowConnectionWait` in by reassigning the constructed `Pool` instance's own `connect()` method, on the reasoning that instrumenting the one place the real `pg.Pool` is built would cover every real caller for free without touching `withTenantScope`/`withUserScope` call sites individually. That reasoning missed something `pg-pool`'s own source makes clear: `Pool.prototype.query()` calls `this.connect(callback)` **internally, in callback style** — and an override that only implements the promise form (every explicit call site in this codebase's own code uses `await pool.connect()`, never a callback) silently swallows that callback, so it never fires. The result: every `pool.query()` call anywhere in the app — not just the `pool.connect()` sites the fix was meant to time — hung forever waiting for a callback that would never come. This shipped to a real PR and was caught live in CI: `@byok/db`'s integration test suite, which normally completes in seconds, ran for 24+ minutes before being cancelled, exactly matching the shape of the bug this whole ADR exists to fix (an unbounded wait, no error, no log) — self-inflicted, this time, by the fix itself.

**Corrected: instrument the call sites, never the library's own instance method.** The wrapping was removed from `createPool` entirely — the returned `Pool`'s `connect()` is now, again, exactly `pg-pool`'s own untouched `Pool.prototype.connect`, verified directly by a new regression test (`connection.test.ts`: `assert.equal(pool.connect, Pool.prototype.connect)`). The timing instead lives in a new `timedConnect(pool)` helper (`tenantContext.ts`), which every scope function in this codebase (`withTenantScope`, `withUserScope`, `withUserAndTenantScope`, `withInternalMetricsScope`, `listAllTenantIds`) now calls instead of `pool.connect()` directly. This times only the explicit, promise-style calls this codebase actually makes — it never touches, wraps, or reasons about `pg-pool`'s own internal call graph, which is exactly the category of assumption that broke the first version.

**The general principle, not just this instance — and this is the second time this exact class of mistake has bitten this codebase, not the first.** Never modify a third-party library's own instance in place (reassigning one of its methods, monkeypatching a prototype, reaching into its internals) to add behavior around it; wrap your own call sites instead. ADR-027 already found a milder version of the same underlying error: `bullmq@6.0.5` imported directly from `ioredis/built/utils`, an internal path that exists in `ioredis@6.0.0`'s layout but not `5.x`'s — trusting a specific version's internal structure broke the instant that structure changed underneath it. Here, the mistake was the same shape one level up: trusting a specific understanding of `pg-pool`'s *own* internal call graph (that nothing inside the library itself calls `connect()` in a way this codebase's override wouldn't handle) broke the instant that understanding turned out to be incomplete — `Pool.prototype.query()` calling `this.connect(callback)` internally was never something this codebase's own code needed to know about until reassigning `connect()` made it load-bearing. A library's public, documented call sites (`pool.connect()`, `pool.query()`) are a stable contract to depend on; its own internal wiring between those methods is not, and reassigning one of its methods in place implicitly bets on that internal wiring never mattering — a bet this codebase has now lost twice.

**Still unconfirmed — the evidence pull did not settle it either way.** The account holder ran both `pg_stat_activity`/`pg_locks` queries in Neon's SQL editor and pulled `railway logs` for the incident window, hours after the original hang. What came back wasn't usable evidence in either direction: the Neon output was the query planner's cost-estimate view (`Hash Join`, `Function Scan` node costs), not the actual result rows, so it's unknown whether either query returned zero rows or some; the Railway output was the CLI's own "new version available" banner, not log lines from the incident window. This is explicitly **not** the same as "confirmed empty" — an empty, successfully-executed result would have been reasonably strong evidence against the stuck-lock theory (Neon does reclaim idle-in-transaction sessions on its own timeout, so a clean result hours later wouldn't have been definitive either, but it would have been *something*). What actually came back settles nothing. Separately: sign-in now works again, consistent with several explanations (the stuck lock, if one existed, was reclaimed by Neon's own timeout in the hours since; or this fix's bounds are now in effect and would prevent recurrence regardless; or the two are unrelated) — its own success doesn't distinguish between them either.

The stuck-lock/redeploy-timing mechanism described in the Context section above remains **plausible, not confirmed, and not disproven**. If it turns out to be right on some future occurrence, the operational lesson is one worth carrying forward regardless of this fix: **a redeploy that lands while a write against a just-durable store is in flight can strand a lock that blocks every later access to that same row, for as long as the provider's own idle-in-transaction default allows** — worth knowing before real users (not test tenants) are depending on this system, since a redeploy timed badly could otherwise degrade into exactly this kind of hang for a real customer. Regardless of whether that specific mechanism was ever the true cause here, this ADR's actual fix (bounded `connectionTimeoutMillis`/`statement_timeout`/`idle_in_transaction_session_timeout`, pool-saturation logging) stands on its own merits — it closes a real, confirmed gap (no bound existed at all) independent of what caused this particular incident.

**Verified:** `@byok/db` build and full test suite green (46/46), including the connect()-override regression test above, `timedConnect`'s own two tests (returns the client unchanged; doesn't log for a fast wait), and the original 5 (three new bounds default correctly and are overridable, `max` still defaults to 10 unchanged, `logSlowConnectionWait` warns above threshold and stays silent at/under it). Full monorepo typecheck clean, full monorepo test suite clean (including a fully green `web:test` run — no flakiness this pass). No live Postgres was touched by any of these tests; every one constructs a real `pg.Pool` object or a fake `PoolLike`, matching this file's existing test pattern.

## ADR-031 — `STAGING_KMS_MASTER_KEY` becomes a real persisted secret; a decrypt-path health signal replaces "connected" as proof a key still works

**Date:** 2026-08-21

**Context:** Preparing to verify the real executor against Acme's real, connected Brain key (the last step of the vault-durability work), a close read of `deploy-staging.yml` surfaced that `STAGING_KMS_MASTER_KEY` was generated **fresh on every staging deploy**, bucketed in the workflow's own comment alongside `BETTER_AUTH_SECRET` as "acceptable... it invalidates existing sessions each deploy." That reasoning is correct for `BETTER_AUTH_SECRET` and wrong for `STAGING_KMS_MASTER_KEY`: the master key encrypts every tenant's DEK (`tenant_deks.encrypted_dek_ciphertext`), which in turn decrypts every tenant's actual Brain/Hands key material. Rotating a session secret costs a re-login. Rotating the KMS master key with no re-encryption path **permanently orphans every DEK encrypted under the previous key** — `kms.decryptDek()` on it just throws, forever, for every tenant, with no way back. Two of ADR-028's/ADR-030's own redeploys (the durability-proving one and the connection-timeout one) had already happened since Acme's key was connected, meaning this was live, not hypothetical, at the exact moment it was found.

**The gap had zero visible symptom, and that's the deeper problem.** `Vault.getBrainKeyStatus` — the only thing the "connected" indicator in the product has ever checked — reads whether a key row exists and isn't revoked. It has never attempted decryption. So a tenant whose DEK was silently orphaned by a KMS rotation would see "connected" exactly as green as a tenant whose key genuinely works, right up until something (originally: a scheduled dispatch trying to actually use the key) tried to decrypt it and failed. This is the fourth instance of "reports healthy, is broken" this project has hit (`/health` reporting `ok` while Redis was dead, pre-ADR-027; three consecutive deploy-verification failure modes, ADR-029; and now this) — a pattern worth naming directly: **a status field that means "the row exists" must never be allowed to read the same as "this actually works."**

**Decision 1 — `STAGING_KMS_MASTER_KEY` is now a real, persisted GitHub secret, generated once, never regenerated by the workflow.** Same durability discipline `INTERNAL_METRICS_TOKEN` already had, and the same reasoning: some values must survive a redeploy, not just tolerate one. `deploy-staging.yml` now reads it from `secrets.STAGING_KMS_MASTER_KEY` and fails the deploy loudly (`::error::`, before ever calling `railway up`) if that secret is unset, rather than silently booting Railway with an empty/undefined KMS master key. The workflow's own comment now explains the `BETTER_AUTH_SECRET`-vs-`STAGING_KMS_MASTER_KEY` distinction explicitly — the two were wrongly treated identically before this fix, and the comment should have said why they aren't from the start.

**Decision 2 — a real decrypt-path health signal, additive to (not a replacement for) `getBrainKeyStatus`.** `Vault.verifyBrainKeyDecryptable(tenantId, roleId): Promise<boolean>` (`packages/vault/src/vault.ts`) runs the exact same DEK-fetch-and-decrypt path `decryptBrainKey` does, immediately zeroes the recovered plaintext, and returns only whether it succeeded — no requester-identity gate, since nothing here can be misused the way exposing real plaintext could be. `GET /me/brain-key` now returns `{connected, decryptable, key}` — `decryptable` is `null` when there's no key row at all (nothing to check), and only actually attempts a decrypt when a row exists. Proven directly against the real failure mode: a test constructs two `Vault` instances sharing the same underlying key store and DEK store but built with two *different* `LocalKms` master keys — literally what a KMS rotation is, at the storage layer — and confirms `verifyBrainKeyDecryptable` correctly flips from `true` to `false` once the "rotation" happens.

**The signal is surfaced, not just computed.** `apps/web`'s Dashboard now shows a distinct "Your connected Brain key can't be used right now — reconnect it" banner when `connected && !decryptable`, separate from the existing "Connect a Brain to get started" CTA for `not connected at all` — a health signal nobody can see repeats the exact "reports healthy, is broken" shape this ADR exists to close, one layer further out.

**Scope, deliberately not covered by this ADR:** Hands keys have the identical `getHandsKeyStatus`-never-decrypts gap — not fixed here, since the immediate trigger (and the thing about to be verified) is Brain-key-specific; a natural, cheap follow-up once this pattern is proven out. Real KMS key rotation — the operational capability this incident makes clear this codebase will eventually need (a compromised key, a compliance-driven rotation schedule, migrating off `LocalKms`/`StagingKms` to a real cloud KMS) — is **not built here**: today there is still no concept of a master key *version*, no way for a DEK to record which version encrypted it, and no re-encryption path. That is a real, separate design gap, tracked in issue #156, not solved by making one environment's key stable.

**Verified:** `@byok/vault` full test suite green (41/41), including four new tests for `verifyBrainKeyDecryptable` (decryptable key, no key stored, revoked key, and the KMS-rotation simulation above). `@byok/api` full test suite green (189/189), including three new/updated tests on the `GET /me/brain-key` route (`decryptable: null` with no row and `verifyBrainKeyDecryptable` asserted never called in that case; `decryptable: true` for a working key; `decryptable: false` for a connected-but-undecryptable one). `@byok/web`: `DashboardScreen.test.tsx` extended with two new tests (the reconnect banner shows for connected-but-undecryptable, and neither banner shows for a healthy connected key) — 8/8 passing. Full monorepo typecheck clean. Full monorepo test suite clean end to end (one pre-existing, already-known-flaky `index.test.tsx` timing suite failed under full-suite load and passed cleanly in isolation — confirmed unrelated, not caused by this change, same flakiness class documented in ADR-030).

## ADR-032 — a tenant's undecryptable DEK is now recoverable on write, honest on read, instead of crashing; the connect-flow's error message stopped blaming the user's connection

**Date:** 2026-08-22

**Context:** Even after ADR-031 stabilized `STAGING_KMS_MASTER_KEY`, reconnecting Acme's Brain key still failed outright — the connect form showed "Something went wrong connecting that key — check your connection and try again," which sent the first look at the wrong layer entirely. The actual mechanism, found directly in the code (not inferred from logs): `DekStore.getOrCreateDek` **reuses whatever DEK already exists for a tenant** — `if (existing) return this.kms.decryptDek(existing);` — and never checks whether that DEK can actually still be decrypted under the *currently configured* master key before handing it back. Acme's `tenant_deks` row predates ADR-031's fix, encrypted under an ephemeral master key that no longer exists anywhere. So `storeBrainKey` — called on every reconnect attempt, including a deliberately fresh one — always hit the same dead DEK first, before ever touching the new plaintext, and `kms.decryptDek()` threw a raw, unclassified crypto exception (a GCM auth-tag mismatch) that propagated all the way to the client with no useful shape, where it landed in a generic catch-all that blamed the user's network.

**The bug is bigger than this one incident.** Any future, legitimate KMS master key rotation — a compromised key, a compliance-driven rotation schedule, migrating `LocalKms`/`StagingKms` to a real cloud KMS (issue #156) — produces this *exact* state for **every tenant, all at once**: every DEK simultaneously undecryptable, every write and read against it crashing instead of failing honestly. This ADR closes that gap generally, not just for Acme's one row.

**Decision — the same failure needs two different recoveries, depending on which side of the vault hits it.** `DekStore.getOrCreateDek` now catches the KMS decrypt failure, logs it loudly (`console.error` — a tenant's keys becoming unreadable belongs in an audit trail, not silent), and throws a new, specifically-typed `DekUndecryptableError` — never a raw crypto exception. What happens next is caller-specific, and deliberately not decided inside `getOrCreateDek` itself:
- **Write paths** (`storeBrainKey`, `storeHandsKey`, `rotateBrainKey`, `rotateHandsKey`, the OAuth silent-refresh re-encrypt) now go through a new `Vault.getDekForWrite` helper: catch `DekUndecryptableError`, call `DekStore.discardAndRecreateDek` (a new `DekRecordStore.replace` method unconditionally overwrites the dead DEK row — safe, because a DEK that can't be decrypted is already permanently useless; there is nothing left to lose by discarding it), and proceed to encrypt the *new* plaintext under the fresh DEK. A reconnect now just works.
- **Read paths** (`decryptBrainKey`, `decryptHandsKey`, `verifyBrainKeyDecryptable`) do **not** get this treatment — `DekUndecryptableError` propagates as-is (or, for `verifyBrainKeyDecryptable`, is caught by its own existing try/catch and reported as `false`, unchanged from ADR-031). Discarding and recreating on a passive read would be a surprising side effect that doesn't even help: the EXISTING encrypted material was bound to the DEK that just died, and a fresh DEK cannot decrypt it either — recreating would just waste a DEK generation and silently mask that the tenant's existing key is genuinely gone. The honest answer for a read is "this can no longer be decrypted, reconnect it" (already what ADR-031's dashboard/settings/connect-screen banners say), not a silent fix-up.

**Decision — the connect flow's error message stopped attributing server-side failures to the user.** `ConnectScreen.tsx`'s `Walkthrough` component previously folded *any* non-`BrainKeyRejectedError` (i.e. anything that wasn't specifically a 422 "the provider rejected this key") into a single hardcoded "check your connection and try again" message — which is exactly backwards for a genuine server-side failure like this one. It now reads: "We couldn't store that key on our end just now — this isn't a problem with your key or connection." A provider rejection is still shown verbatim (still the user's to fix); everything else is now honestly attributed to the server. `ConnectScreen`/`SettingsScreen` also now respect the `decryptable` field directly (ADR-031's own follow-up, done here since it's what actually surfaced the confusion live): a connected-but-undecryptable key skips straight to the provider-choice/reconnect flow instead of showing a misleading "you're all set" summary, and Settings shows a distinct "Needs reconnect" badge instead of "Connected".

**Linking to issue #156 (KMS key rotation has no design):** this incident is that gap surfacing early and by accident, not a new one. #156 is updated with a direct link to this ADR — the write-side recovery here (discard-and-recreate) is a reasonable STOPGAP for the "a DEK became undecryptable" symptom, but it is explicitly **not** real key rotation: there is still no concept of a master key *version*, no way for a DEK to record which version encrypted it, and no path to re-encrypt existing, still-good DEKs onto a new master key without losing them. A deliberate rotation (as opposed to this incident's accidental one) still needs #156's full design.

**Acme's orphaned rows:** the `tenant_deks` row (and any `brain_keys` rows encrypted under it) that predate ADR-031's fix are permanently unrecoverable — no code change makes a DEK encrypted under a truly-gone master key readable again. These are being deleted directly (scoped to Acme's `tenant_id` only, `brain_keys` and `tenant_deks`, never the `tenants` row itself) rather than left as permanently-broken rows that would otherwise keep reporting `connected: true` forever.

**Verified:** `@byok/vault` full test suite green (51/51) — 5 new dedicated `dekStore.test.ts` tests (fresh-DEK creation, per-tenant isolation, `DekUndecryptableError` on a rotated master key, `discardAndRecreateDek` producing a genuinely usable fresh DEK, and confirming the discarded DEK is truly gone even to the original master key) plus 6 new `vault.test.ts` integration tests proving the write-vs-read distinction end to end (`storeBrainKey`/`storeHandsKey` succeed transparently against a dead DEK; `decryptBrainKey`/`decryptHandsKey` throw `DekUndecryptableError` rather than silently recovering; `verifyBrainKeyDecryptable` confirmed to have zero side effect on the dead DEK it just checked). Full monorepo typecheck and full test suite clean end to end, including `@byok/web`'s full suite (109/109) with the updated `ConnectScreen`/`SettingsScreen` tests.

## ADR-034 — A circuit breaker stops BullMQ's Redis-error retry storm from becoming an unbounded cost leak (issue #160)

**Date:** 2026-08-22

**Context:** ADR-033's verification pulled real deploy logs from the minutes before the Upstash quota fix landed, and found a tight, uninterrupted retry storm: nearly every BullMQ key for both queues (`scheduled-dispatch:*`, `digest-daily:*`) was being retried on every tick, fast enough that Railway's own log pipeline started dropping thousands of lines/sec. Tracing it into `bullmq`'s own source (`Worker.retryIfFailed`, vendored at `node_modules/bullmq/dist/cjs/classes/worker.js`) explains exactly why: it classifies an error via `isNotConnectionError`, and Upstash's "max requests limit exceeded" is a real Redis `ERR` reply on a live connection, not a dropped one — so it takes the "not a connection error" branch, which re-throws **immediately, with zero delay**, on purpose. BullMQ's own built-in delay-and-retry (`opts.delayInMs`) only applies to the *other* branch (actual connection failures). The Worker's main loop then just calls back in right away, so a single command-level Redis error becomes an unbounded tight loop with nothing internal to stop it.

**Why this can't be fixed with ioredis connection options.** `retryStrategy`/`maxRetriesPerRequest` govern reconnecting after the TCP connection itself drops — a different failure mode than a healthy connection returning error replies, which is what this actually is. Nothing in ioredis or BullMQ throttles this shape on its own; it has to be handled at the application level.

**Why this matters beyond the original quota incident:** this loop is very plausibly *how* the free-tier quota got exhausted in the first place. Now that Redis is on pay-as-you-go (a direct request from this incident), the identical failure shape — any transient Redis error, not just a quota rejection — becomes a live, unbounded billing risk: nothing stops the loop from running up real cost for as long as Redis keeps erroring.

**Decision:** `packages/jobs/src/redisErrorCircuitBreaker.ts`'s `attachRedisErrorCircuitBreaker` watches a Worker's own `error` events (BullMQ workers already emit one on every `retryIfFailed` failure) for a burst — 10+ errors within a 5-second sliding window, by default — and when tripped, calls `worker.pause(true)` (the `true` is `doNotWaitActive`: the point is to stop calling Redis *right now*, not wait around for in-flight jobs that may themselves be stuck on the same failure) rather than letting the loop continue. Confirmed directly in `bullmq`'s source that `pause()` is purely local/in-process (sets a flag, stops the stalled-check timer) — it needs no successful Redis round-trip to take effect, so it works even while Redis itself is actively erroring. After a cooldown (30s initially), it resumes automatically. The cooldown escalates (doubling, capped at 10 minutes) if the breaker trips again shortly after resuming — Redis is still unhealthy — and resets back to the 30s starting point once a resume is followed by a genuinely healthy stretch, so one bad incident doesn't leave the worker parked at a 10-minute cooldown indefinitely afterward. Wired onto both the scheduled-dispatch worker and the digest worker in `apps/api/src/server.ts` (both were visibly affected in the logs); not wired onto the Queue instances, since the storm's driver is specifically the Worker's own internal processing/stalled-check loop, not the occasional HTTP-triggered `queue.add`/`upsertJobScheduler` call.

**Verified:** `@byok/jobs` full test suite green (28/28), including 8 new dedicated tests for the circuit breaker (doesn't trip below threshold; trips and pauses at threshold; sliding window correctly ages out old errors; ignores further errors while already tripped instead of re-pausing; auto-resumes after cooldown; escalates cooldown on a re-trip shortly after resuming; resets to the initial cooldown after a genuinely healthy stretch; a failing `pause()` call is caught, not thrown from the listener) — all using an injected fake clock/timer, no real waiting. `@byok/api` full suite green (189/189). Full monorepo typecheck clean.

## ADR-035 — Issue #161's output corruption was not reproducible; traced the full call path and found no code defect

**Date:** 2026-08-22

**Context:** ADR-033's verification found scattered doubled letters ("Createss", "Buddget", "Reegulatory") in a real CEO-tier recommendation's draft text, filed as issue #161 on the theory that it looked like a streaming/token-concatenation bug rather than a model sampling error. Before writing a fix, the actual call path needed tracing, since a fix aimed at the wrong layer (or a nonexistent bug) would be worse than no fix at all.

**What the trace found:** `apps/router/src/openMultiAgentExecutor.ts` passes `orchestrator.runAgent()`'s `result.output` straight through into `ExecutionOutcome.result` with zero string manipulation. For a single-turn, no-tool-use task like this one, `@open-multi-agent/core`'s `runAgent` goes through its **non-streaming** `chat()` method (`node_modules/@open-multi-agent/core/dist/llm/anthropic.js:282`) — one `messages.create()` call, whose response content is mapped block-for-block (`{ type: 'text', text: block.text }`) with no buffering, no chunk-boundary arithmetic, nothing that touches individual characters. The streaming delta-accumulation code in the same file (`stream()`, `text_delta` handling) — the code originally suspected — never runs for this call shape at all. Postgres JSONB storage is a lossless round-trip for text. No code path between "Anthropic's API response" and "the row in `approval_queue_items`" does anything that could plausibly double an isolated letter mid-word.

**Verification, not assumption:** rather than conclude "must be a model artifact" from the absence of a found bug, triggered a second real dispatch and had the check script (`packages/jobs/scripts/check-scheduled-dispatch-result.mjs`, extended with an optional `outFile` argument) write the raw row directly to a file on disk, then read that file directly — bypassing the terminal entirely, since the original corrupted text only ever existed in a long JSON blob copy-pasted from a PowerShell terminal into chat, never in a file read programmatically. The byte-level file content was completely clean: no doubled letters anywhere in a ~2200-word document, full cost-reservation lifecycle (`reserved` → `settled`), full audit trail (`reserved` + `recommendation-submitted`, both present this time — the first run's paste had been cut off before the second entry).

**Decision:** close issue #161 as not reproducible. No code change ships. The working theory — supported by the byte-clean re-verification and the absence of any plausible mechanism in the traced call path — is that the original corruption was introduced by the terminal itself during copy-paste of very long output, not by the runtime. Recorded here specifically because the user asked, ahead of Brain-per-role's provider-dispatch work, whether `@open-multi-agent/core` itself carried this defect (which would have meant every future provider inheriting it) — the answer is no: this call path has no character-level text assembly to be buggy in the first place. `check-scheduled-dispatch-result.mjs`'s new `outFile` option is kept for future verifications where output fidelity matters — read structured evidence from a file, not a terminal paste.

**Verified:** re-ran a real dispatch end to end; raw database content read directly from a file, confirmed byte-clean. No test changes — this was an investigation, not a code fix.

## ADR-036 — `WEB_ORIGIN` trusted exactly one origin; attaching a real custom domain broke sign-in entirely

**Date:** 2026-08-25

**Context:** The user bought `runwisely.cc` and attached both `https://www.runwisely.cc` and `https://runwisely.cc` to the Vercel project (confirmed via Vercel's own API — both are real, attached domains). Sign-in on the new domain failed outright: browser console showed a CORS preflight rejection (`Access-Control-Allow-Origin` missing) against `apps/api`'s `/api/auth/sign-in/email`, then a `NetworkError`. Root cause, traced directly rather than guessed: both `apps/api/src/index.ts`'s Hono `cors()` middleware and Better Auth's `trustedOrigins` (`server.ts`) were built around a single `WEB_ORIGIN` env var holding exactly one origin string — correct when the only real origin was Vercel's auto-generated `<project>.vercel.app` alias, but structurally incapable of trusting more than one origin the moment a real domain (in two forms, `www` and bare apex) entered the picture.

**A second, sharper problem underneath the first:** `.github/workflows/deploy-staging.yml` derives `WEB_ORIGIN` fresh on every single deploy from Vercel's API (`https://<project-name>.vercel.app`) and unconditionally overwrites the Railway variable with it (line ~170). Even a one-off manual fix — hand-setting `WEB_ORIGIN=https://www.runwisely.cc` directly on Railway — would have been silently reverted by the very next merge's automated deploy. Any fix needed to survive that, not just work once.

**Decision:** `WEB_ORIGIN` keeps its existing job — the one canonical origin every redirect/URL-building call site (`dashboardUrl`, `handsOAuth.ts`'s `redirectToOrgChart`, etc.) uses, and the deploy workflow keeps auto-deriving it exactly as before. A new, additive `ADDITIONAL_WEB_ORIGINS` (comma-separated) feeds a new `ServerConfig.webOrigins: string[]` (`[webOrigin, ...additional]`, deduped) — this is what CORS and `trustedOrigins` actually check against now, since a browser sends whichever origin the user actually typed. `ADDITIONAL_WEB_ORIGINS` is deliberately never set anywhere in `deploy-staging.yml` — it's a plain Railway variable set directly on the service, once, and left alone, the same "some values MUST survive a redeploy" discipline already established for `STAGING_KMS_MASTER_KEY`/`INTERNAL_METRICS_TOKEN` (ADR-028, ADR-031), just via an ordinary variable rather than a GitHub secret, since a domain name isn't sensitive.

**Known follow-up, deliberately not fixed here:** `WEB_ORIGIN` (the canonical, singular value) still resolves to the auto-generated `.vercel.app` alias, not the real custom domain — meaning dashboard links in emails and the Hands-OAuth redirect-back-to-org-chart URL still point at the ugly internal domain, not `www.runwisely.cc`, even after this fix. That's a real, separate gap (not a CORS/auth blocker — sign-in itself works once `ADDITIONAL_WEB_ORIGINS` is set), scoped out of this PR deliberately: fixing it means deciding how the deploy workflow learns which domain is "the real one" (a new secret/variable, or preferring an attached custom domain over the Vercel alias when one exists), which deserves its own consideration rather than being rushed into an urgent unblock.

**Not addressed here, and explicitly out of scope:** issue #144 (same-origin proxy) remains open. This fix makes the current cross-site-cookie architecture correctly trust the real domain; it does not replace that architecture. Per the user's own explicit sequencing decision: patch this now (small, well-scoped, unblocks a live outage), design and build the proxy properly afterward, not rushed together with an urgent fix touching the auth entry point.

**Verified:** `@byok/api` full suite green (192/192), including 3 new dedicated tests for `webOrigins`/`ADDITIONAL_WEB_ORIGINS` parsing (defaults to exactly `[webOrigin]` when unset; comma-separated values added correctly with trimming; empty entries ignored and `webOrigin` never duplicated even if repeated in `ADDITIONAL_WEB_ORIGINS`). Full monorepo typecheck clean. Not yet verified against the live domain — that requires the user to set the Railway variable and test sign-in for real, which this PR's description asks for.

## ADR-037 — Autonomy durability: `ApprovalQueue` reads a real Postgres-backed `DurableAutonomyStore`, closing the accept-offer split-brain

**Date:** 2026-08-25

**Context:** `ApprovalQueue`'s live dispatch gating (`submitProposedAction`'s bypass check) read a synchronous, in-memory `AutonomyEngine` — reset on every restart, invisible outside the process. A real, durable counterpart (`PostgresDurableAutonomyStore`, `autonomy_counters` table) already existed and was already being written to — but only by `apps/api/src/routes/approvals.ts`'s accept-offer route, which called it directly, bypassing `ApprovalQueue` entirely. The route's own doc comment already named this precisely: accepting an offer durably recorded `active = true` in Postgres, with zero effect on live dispatch behavior, because the object that mattered for dispatch never read that table. Two independent, never-synced sources of truth for one property.

**The scoping question that decided the shape of this work: does `shouldSpotCheck()` need to become async?** No — it's a pure function of an injected RNG and static config (`this.random() < this.config.spotCheckRate`), holding no per-tenant state at all. "Spot-checks run forever, not just during a probation period" (the engine's own original comment) means it's deliberately memoryless — there's nothing to persist, so nothing forces it into the async boundary. That answer settled the rest: every state-bearing call `ApprovalQueue` makes (`isActive`, `recordApproval`, `recordRejection`, `recordSpotCheckRejection`, `revoke`) already lived inside an already-`async` method — this was a contained storage swap, not a control-flow refactor.

**Decision:**
- `AutonomyEngine` (the synchronous, in-memory class) is deleted outright — after this change it had zero real consumers left; its shared types (`AutonomyConfig`, `AutonomyState`, `AutonomyEvent`, `DEFAULT_AUTONOMY_CONFIG`, `NoPendingOfferError`) stay in `autonomyEngine.ts`, now purely a types module.
- `DurableAutonomyStore` (`durable/autonomyStore.ts`) gains `shouldSpotCheck(): boolean` — sync, same injectable-RNG constructor parameter `AutonomyEngine` took, on the interface for the same reason `isDeniable` already was: a pure, stateless decision that still belongs on the one object `ApprovalQueue` depends on, not a second dependency.
- `ApprovalQueue`'s constructor now takes `autonomy: DurableAutonomyStore`. The durable store has no event-emission mechanism of its own (unlike the old engine, which called `this.emit(...)` internally) — every `AutonomyEvent` is now synthesized by `ApprovalQueue` itself, right after the awaited store call that used to trigger it synchronously: `autonomy.offered` from `recordApproval`'s returned `{offered, consecutiveApprovals}`, `autonomy.revoked` (reason `spot-check-rejected`) after `recordSpotCheckRejection`, and `autonomy.revoked` (reason `manual`) once per task type `revoke()` actually reports as revoked.
- **The one real design decision, as flagged in scoping:** `revoke(tenantId, taskType?)`'s signature changed from `Promise<void>` to `Promise<{ revokedTaskTypes: string[] }>`, both implementations (`PostgresDurableAutonomyStore` via `UPDATE ... WHERE active = true RETURNING task_type`). The old engine emitted one `autonomy.revoked` per task type it actually flipped, skipping already-inactive ones — `ApprovalQueue` can't reproduce that from a void return, so the store now reports back exactly what changed.
- New `ApprovalQueue.acceptOffer(tenantId, taskType)` — a thin passthrough to `this.autonomy.acceptOffer`. This is what actually closes the split-brain structurally rather than by convention: `apps/api/src/routes/approvals.ts` no longer takes a separate `autonomyStore` dependency at all — it calls `deps.approvalQueue.acceptOffer(...)`, the same object `submitProposedAction` reads.
- `apps/api/src/durableTrustCore.ts` and `apps/api/src/dev/devTrustCore.ts` both construct exactly one `PostgresDurableAutonomyStore(pool)` now (dev already required `pool` for `TenantCeilingStore`, so it gets the same real store, not the in-memory one) and pass it straight into `ApprovalQueue`. `apps/api/src/index.ts`'s previously-separate `PostgresDurableAutonomyStore` construction is deleted — there is exactly one instance now, not two.
- **Construction guard, landing with the fix per ADR-028's principle, not after:** `InMemoryDurableAutonomyStore` was missing the dev/test-only guard every sibling in-memory durable store has (`InMemoryDurableApprovalStore`, etc.) — a real, pre-existing gap, not new scope. It now throws `DevOnlyAutonomyStoreGuardError` outside a dev/test environment, same as the others.

**Verified:**
- `@byok/approval-queue` full suite green (38/38) — every guarantee the old `AutonomyEngine` test suite carried (threshold-crossing offers, deny-list immunity including the full million-iteration run — still cheap, still in-memory — per-tag deny-list coverage, normal-vs-spot-check rejection semantics, per-tenant/task-type isolation, deterministic sampling) ported to `InMemoryDurableAutonomyStore`, plus new coverage `autonomyEngine.test.ts` never had: `revoke()`'s new return value (exactly the task types actually revoked, empty when nothing was active), and the construction guard.
- New `PostgresDurableAutonomyStore` itest: deny-list immunity holds against the real database too — proven as "never creates or mutates a row" (the check happens before any query), not a literal million real round-trips.
- New `ApprovalQueue` tests proving the event synthesis is behaviorally equivalent to the old engine's internal emit (offered/revoked events land correctly), plus the money test: `acceptOffer()` flips `isActive` on the exact same store `submitProposedAction` reads, in one call — the structural proof the split-brain is closed, not just documented as fixed.
- `@byok/router` full suite green (56/56) against the new store. `@byok/api` full suite green (192/192). Full monorepo typecheck clean.

## ADR-039 — Router durability: `Router` reads real Postgres-backed `DurableTaskLedger`/`DurableDedupStore`, closing the crash-orphans-a-reserved-cost-row gap

**Date:** 2026-08-25

**Context:** Issue #120 — `Router`'s constructor took a synchronous, in-memory `TaskLedger`/`DedupStore` pair (`ledger.ts`/`dedup.ts`), same shape as the old `AutonomyEngine` this codebase already fixed once (ADR-037): reset on every restart, invisible outside the process. Concretely, a crash mid-`submitTask` (after `CostGate.evaluateAndReserve` but before settle/release) lost every trace of the in-flight task, leaving an orphaned reserved-cost row nothing could ever reconcile, and a multi-replica deployment couldn't dedupe a resubmitted `dedupKey` across processes at all — the in-memory `Map`'s `get()`-then-`set()` pattern isn't atomic across replicas.

**The scoping question that decided the shape of this work, done before writing anything:** does making `ledgerFor()` async ripple into callers, or is this a contained swap? Grepped the full codebase — `ledgerFor()` has **zero production callers**; the real dashboard/digest data path is `PostgresCostActivityQueries` (`durable/queries.ts`), querying `cost_reservations`/`autonomy_counters`/`audit_log` directly, entirely independent of the ledger. Making it `async` was a non-issue. The one caller that genuinely needed rethinking was `runExtractionBatch.ts` (the platform-key onboarding batch, ADR-003/ADR-015): it runs **before any tenant exists**, using a placeholder `subAgentId: "extraction-batch"` with no real `tenantId` — structurally incompatible with the new tenant-scoped `DurableTaskLedger.append`. Decoupled entirely rather than force-fit: `SignupExtractionBatchStore.start/complete/fail` (already called in the same function) already durably tracks this exact batch's lifecycle in Postgres, and — per the scoping grep above — nothing in production ever read `ledgerFor()` for this or any `subAgentId`. Nothing lost.

**Decision:**
- `Router`'s constructor now takes `DurableTaskLedger`/`DurableDedupStore` (`durable/ledgerStore.ts`/`durable/dedupStore.ts`) — Postgres-backed for any deployed environment, tenant-scoped throughout. `ledger.ts`/`dedup.ts` (the old synchronous, in-memory classes) are deleted outright, along with `types.ts`'s now-orphaned `LedgerEntry` — zero remaining consumers, confirmed by grep before deleting, same standard as ADR-037's `AutonomyEngine` removal.
- `DedupStore`'s old `get(key)`/`set(key, task)` shape becomes `getOrCreate(tenantId, dedupKey, factory): Promise<{task, created}>` plus a separate `update(task): Promise<void>` — `getOrCreate` is the actual multi-replica fix, not just an async rename: the row carries a `UNIQUE(tenant_id, dedup_key)` constraint and `INSERT ... ON CONFLICT DO NOTHING`, so two replicas racing the same `dedupKey` can't both "win." `submitTask` calls `getOrCreate` once at intake and `update` at every subsequent status transition (queued/skipped, in_progress, terminal) — every `ledger.append` call is now `await`ed and tenant-scoped.
- `runExtractionBatch.ts` (`apps/api`) had its `ledger` dependency removed entirely — `RunExtractionBatchDeps`, `TrustCoreDeps` (`context.ts`), and the `extractionRoute` wiring (`index.ts`) all drop the field. The operator-visible detail the old ledger note carried (the technical QUEUE/SKIP reason, and any failure message) is unaffected — it was already also being written to `batchStore.fail(...)`'s `error` argument, which is what `runExtractionBatch.test.ts`'s leak-guard and plain-language-reason tests now assert against instead.
- **Construction guards, landing with the fix per ADR-028's principle, not after:** `InMemoryDurableTaskLedger` and `InMemoryDurableDedupStore` were both missing the dev/test-only guard every sibling in-memory durable store already has (`InMemoryDurableApprovalStore`, `InMemoryDurableAutonomyStore`, vault's `InMemoryDekRecordStore`) — a real, pre-existing gap, not new scope. Both now throw (`DevOnlyTaskLedgerGuardError`/`DevOnlyDedupStoreGuardError`) outside a dev/test environment.
- `apps/api/src/durableTrustCore.ts` (staging/production wiring) now constructs `PostgresDurableTaskLedger(pool)`/`PostgresDurableDedupStore(pool)` — closing the gap ADR-026 had explicitly deferred ("Router's ledger and dedup store are DELIBERATELY still in-memory here... a larger, separate change, tracked in issue TBD"). `apps/api/src/dev/devTrustCore.ts` (local dev) constructs the guarded in-memory variants instead, unchanged in substance from before, just renamed to the durable interface.

**Verified:** `@byok/router` full suite green (56/56) — including one test (`ADR-008: production refuses to construct a Router missing either CostGate or ApprovalQueue`) that needed its own fix: it flips `NODE_ENV` to `"production"` mid-test, and the ledger/dedup store's own new construction guard fired first (same class of ordering issue ADR-037's `queue` variable already worked around) — fixed by constructing the ledger/dedupStore before the `NODE_ENV` flip, same pattern. `@byok/api` full suite green (192/192), including `runExtractionBatch.test.ts`'s 7 tests rewritten to assert against `batchStore.failedWith` instead of the removed ledger. Full monorepo typecheck clean (`apps/web`'s Vite/Nitro build included).

## ADR-040 — Issues #149/#150: Vault's and CostGate's own audit logs are now the shared, durable `DurableAuditLog`, not bespoke always-in-memory ones

**Date:** 2026-08-26

**Context:** `Vault`'s `AuditLog` (key store/rotate/revoke/decrypt-granted/decrypt-denied) and `CostGate`'s `GateAuditLog` (every evaluateAndReserve verdict) were each a bespoke, synchronous, always-in-memory class — distinct from the shared `audit_log` table (`@byok/db`'s `DurableAuditLog`/`PostgresDurableAuditLog`) that `PostgresReservationStore` and `PostgresDurableApprovalStore` already write reservation/approval events to. Neither package ever wired anything else in: `durableTrustCore.ts` (staging/production) constructed `CostGate` with only 4 of its 5 constructor arguments, and passed `undefined` for `Vault`'s audit-log argument — so even the "durable" trust core kept both these specific trails in a plain array that vanished on every restart or redeploy. Vault's is the security-relevant one of the two: it's the record of who decrypted which tenant's Brain/Hands key, and when, and whether a decrypt was denied.

**Scoping question, per the working pattern established for #120/#037: contained swap, or does this ripple into control flow?** Answer: contained, with one real architectural finding along the way. Every `this.audit.append(...)` call site in both classes already sits inside an `async` method (13 in Vault, 1 in CostGate) — awaiting them is mechanical, not a control-flow rewrite. `Vault`'s own `AuditEvent` already carried `tenantId`; `CostGate`'s call site already had `input.tenantId` in scope. Neither package's own `auditEvents()` getter has a single consumer outside its own test file (confirmed by grep before touching anything) — same "safe to change the shape" finding #120's `ledgerFor()` scoping made.

**The one real design decision:** the natural place to add the dev/test-only construction guard (ADR-028's principle) is `InMemoryDurableAuditLog` itself, matching how `InMemoryDurableTaskLedger`/`InMemoryDurableDedupStore` guard themselves — but `InMemoryDurableAuditLog` lives in `@byok/db`, which `@byok/vault` depends ON (not the other direction), and `isDevOrTestEnvironment()` lives in `@byok/vault`. Guarding the shared class itself would require a genuine dependency-direction change (moving the env helper down into `@byok/db`, or introducing a new shared package beneath both). Not worth it for this fix: the guard instead lives at each consumer's own construction decision — `Vault`'s and `CostGate`'s constructors each throw their own error (`DevOnlyVaultAuditGuardError` / `DevOnlyCostGateAuditGuardError`) if `audit` is omitted outside dev/test, rather than silently defaulting. `InMemoryDurableAuditLog` itself stays unguarded in `@byok/db` — it's a generic, reusable in-memory implementation of the shared interface (cost-gate's and approval-queue's own tests already construct it directly), not itself the trust-core boundary.

**Decision:**
- `AuditSource` (`@byok/db`) widened to `"cost-gate" | "approval-queue" | "vault"`.
- `Vault`'s constructor: `audit` is now an optional `DurableAuditLog` (no default-parameter expression); the constructor body defaults to a guarded `InMemoryDurableAuditLog()` when omitted. All 13 `this.audit.append(...)` call sites now go through a new private `logAudit(kind, tenantId, refId, detail?)` helper and are awaited. `auditEvents()` is now `async auditEvents(tenantId, limit?)`, delegating to `recentForTenant` — tenant-scoped, like every other durable read in this codebase, not a global "everything" dump the old `all()` gave.
- `CostGate`: identical shape — `audit` optional, same guard pattern, one call site updated, `auditEvents(tenantId, limit?)` now async.
- Both packages' old bespoke files (`vault/src/auditLog.ts`, `cost-gate/src/auditLog.ts`) deleted outright — zero remaining consumers, confirmed by grep before deleting, same standard as every prior dead-code removal this session.
- `apps/api/src/durableTrustCore.ts` now passes its single existing `PostgresDurableAuditLog(pool)` instance into both `CostGate` and `Vault`, alongside its existing uses for `PostgresReservationStore` and `PostgresDurableApprovalStore` — one shared audit trail across all four trust-core components, differentiated by the `source` column. `devTrustCore.ts` (local dev) is unchanged — omitting the argument there safely defaults to the guarded in-memory implementation.
- One real, deliberate behavior change surfaced by the swap, not introduced by it: `recentForTenant` (and therefore both packages' new `auditEvents()`) reads newest-first, matching `PostgresDurableAuditLog`'s own `ORDER BY seq DESC` — the old `all()`/bespoke getters returned insertion order (oldest-first). Both packages' audit-log tests were rewritten to expect the new order, not worked around.

**Addendum — a real CI catch, found only once `apps/web`'s own typecheck actually ran (initial verification checked only the backend packages, not the full monorepo build — a gap in the verification itself, not just the fix):** `apps/router/src/durable/queries.ts`'s `recentActivity` — the tenant-facing dashboard's "recent activity" feed — reads directly from the same `audit_log` table this PR just started writing `source: "vault"` rows into, with no filter. Left as-is, Vault's own key store/rotate/revoke/decrypt security trail would have started appearing in the dashboard's task-activity feed as an unannounced side effect of a durability fix. Fixed by filtering the query itself (`source IN ('cost-gate', 'approval-queue')`) and narrowing `recentActivity`'s declared return type to a purpose-built `DashboardActivityEvent` rather than the shared 3-way `StoredAuditEvent` — the dashboard's own frontend type (`apps/web/src/components/DashboardScreen.tsx`) needed no change at all once the backend type stayed accurately narrow. New test: `queries.test.ts` asserts the SQL itself excludes `source='vault'`, not just that the row-mapping still works.

**Verified:** `@byok/db` 46/46, `@byok/vault` 51/51, `@byok/cost-gate` 53/53, `@byok/router` 57/57, `@byok/api` 192/192, `@byok/web` 109/109. Full monorepo typecheck clean, including `apps/web`'s real `vite build` — the step the initial verification pass skipped.

## ADR-041 — Database moved from Neon to Supabase; two real Supabase-specific security defaults found and closed before any real data moved

**Date:** 2026-08-26

**Context:** Neon's free plan allows exactly one project — with the real staging environment (Phase 1 item 4) needing its own database, the choice was a paid Neon plan or Supabase (free tier allows multiple projects, already connected via MCP, a project already existed). Decided to move rather than pay for a second Neon project. Scoped first — six explicit questions (RLS parity, connection-role trap, pooling, data migration order/rollback, migration portability, what breaks) — before touching anything; this entry is the outcome.

**1. RLS parity — portable, confirmed against the live project, not assumed.** All 11 pre-existing migrations are plain, provider-agnostic SQL (`ENABLE`/`FORCE ROW LEVEL SECURITY`, `set_config('app.tenant_id', true)`) with zero Neon-specific dependency, applied cleanly. Supabase's own RLS conventions (`auth.uid()`, PostgREST role-switching) live entirely in a request path this app never uses (a direct Postgres connection, not Supabase's Data API) — no actual overlap.

**2. Connection role — same trap, different mechanism, closed the same way.** Queried live: Supabase's `postgres` and `service_role` both carry `rolbypassrls = true` (Neon's version was console-created roles inheriting `neon_superuser`). Created `app_user` via plain SQL (`NOSUPERUSER NOBYPASSRLS`), matching `ci.yml`'s own established GRANT pattern.

**3. A real gap `ci.yml`'s pattern doesn't cover: `runMigrations()` runs on every boot (ADR-022) as the SAME role the app connects as** — meaning that role needs real DDL rights, not just DML, unlike CI's split (an owning role runs migrations once, `app_user` only ever does DML in tests). `apply_migration` bootstrapped the schema as Supabase's own admin role, so `app_user` initially owned nothing and `runMigrations()` failed outright (`permission denied for schema public`) when run for real. Fixed by transferring ownership of every table and sequence to `app_user` (`GRANT CREATE ON SCHEMA public` first — Postgres requires the new owner already have schema-create rights before an ownership transfer succeeds, discovered by hitting the error, not by reading ahead) and re-verifying `runMigrations()`/`verifySchemaCurrent()` end to end as `app_user` — both passed clean on the second attempt. This is the more accurate production pattern regardless of provider: a real deployed role that owns its own schema, protected from itself by `FORCE ROW LEVEL SECURITY`, not a maximally-restricted role that happens to work only because migrations ran once as something else.

**4. Pooling — the user's own instinct, confirmed by real production history, not just architectural reasoning.** Found live: production already runs against Neon's *pooled* endpoint (pgbouncer transaction mode) today — only migrations/RLS-verification use the direct one. `withTenantScope`'s whole design (one `BEGIN…COMMIT`, `set_config(..., true)` scoped to that one transaction) is safe under any correct transaction-mode pooler by construction. The one real open question — whether `statement_timeout`/`idle_in_transaction_session_timeout` (session-level `SET`s issued once per physical socket) reliably survive Supavisor's transaction-mode backend rotation — isn't one this session could resolve by reading code, and Supabase's own docs flag session-level `SET` as unreliable in transaction mode. Given two prior real pooled-connection incidents in this exact codebase (ADR-030's `connection.ts` header), the decision is to sidestep the question entirely: **the app connects to Supabase's direct endpoint, not Supavisor in any mode.** `pg.Pool` already caps concurrency (`max: 10`) client-side; a second, transaction-mode pooling layer underneath buys nothing this app doesn't already have, and removes an entire class of untested behavior. Recorded explicitly so a future "optimize the connection" pass doesn't reach for Supavisor transaction mode without re-deriving this.

**5. Two real Supabase-specific security defaults found before any data moved — neither exists on Neon, both would have been a real exposure if missed:**
- **Supabase auto-enables RLS on every new `public`-schema table** (its own `rls_auto_enable()` trigger, confirmed via `pg_class.relrowsecurity` directly and Supabase's own security advisor). This silently applied RLS-with-zero-policies to `tenants`, `users`, and Better Auth's eight tables — all deliberately unprotected by design (0001/0003's own comments) — which for a non-owner role means silent deny-all on every read and write. Fixed with a new migration (`0013_disable_rls_on_unprotected_tables.sql`) explicitly disabling RLS on exactly those ten tables; a no-op on Neon, so portable either direction.
- **Supabase grants `anon`/`authenticated` (the roles its own public REST API connects as) full `SELECT/INSERT/UPDATE/DELETE` on every table by default** — confirmed directly via `information_schema.role_table_grants`. Combined with the RLS-disabled tables above, this would have meant anyone holding the project's public anon key could read or write tenant and session data directly through Supabase's REST API — an exposure Neon has no equivalent surface for at all, since it has no public API layer. Fixed with `0014_revoke_supabase_api_roles.sql` (revokes all grants and default privileges from both roles on every table) — this app never uses Supabase's Data API/Auth layer, so these roles have no legitimate reason to touch anything here.

**6. Migration files 0012-0014, and what changed in deploy tooling:** `0012_audit_log_vault_source.sql` (ADR-040's own gap — the `audit_log.source` CHECK constraint never allowed `'vault'`, caught here because this was the first time `runMigrations()` ran for real against a database with that constraint) landed on #173's branch, since it's that PR's own bug. `0013`/`0014` are Supabase-specific, landed here. `deploy-staging.yml`'s Neon-pooler hostname derivation (a `-pooler` string substitution on the direct URL) doesn't translate — Supabase's connection format is structurally different, replaced with the real Supabase direct connection string. The GitHub Actions secret is `SUPABASE_DATABASE_URL` (replacing `NEON_DATABASE_URL`); Railway's own env var name is unchanged — it's still `DATABASE_URL`, just set from the new secret at deploy time (`railway variable set "DATABASE_URL=$SUPABASE_DATABASE_URL"`).

**7. Data migration — Acme only, by explicit decision, with what was left behind fully accounted for.** Neon's real production data had 94 "tenants," not one: querying every tenant-scoped table found exactly one, `acme`, with any real activity (6 brain keys, 1 charter, 33 cost reservations, 30 approvals) — the other 93 are accumulated deploy-verification/manual-test artifacts going back to the project's earliest days, confirmed to have **zero** brain_keys, hands_keys, tenant_deks, cost_reservations, approval_queue_items, audit_log, router_tasks, or task_ledger_entries. Two exceptions checked individually, not assumed away: one non-Acme tenant (`r3-final-co`) has an active charter and one claimed extraction batch, three others have a claimed batch each — all four traced to R3 scheduler-verification dry-runs and extraction-fixture testing (fake "ceramic mugs" test ideas, matching fixtures already in `test/results/`), none real. Decision: migrate Acme only; the 93 test-artifact tenants stay on Neon, not carried into Supabase's clean start. Filed issue #175 separately: these disposable accounts are never cleaned up by the deploy-verification scripts that create them, and would recur on Supabase from day one unless fixed — no self-service delete-account API exists to fix it inline, so it's scoped as its own follow-up rather than bolted on here.

**What actually moved for Acme, verified byte-exact:** `tenants`, `users`, `tenant_members`, Better Auth's `user`/`account` (credential sign-in preserved)/`organization`/`member` (only the one Acme-linked row, not all 8 orgs this same real user owns across the test tenants), `tenant_deks`, `brain_keys` (6 rows), `company_charters`, `cost_reservations` (33 rows). Every `BYTEA` column (the DEK and all six Brain key ciphertexts/IVs/auth tags) transferred via hex round-trip (`encode(..., 'hex')` → `decode(..., 'hex')`) and was `md5()`-checksummed identical on both sides before proceeding — lossless by construction, verified, not assumed.

**`approval_queue_items` was NOT a blanket skip — checked first, and it mattered.** The initial pass deprioritized it as "pure historical, not correctness-critical," the same reasoning that held for `cost_reservations`. That reasoning is wrong for anything still `status = 'pending'`: an unresolved approval item isn't history, it's live state a real person still owes a decision on — silently leaving it behind is a real, user-visible loss, not a tidiness call. Checked directly before deciding anything: Acme had 30 items, **14 still pending** (12 `proposed-action`, 2 `recommendation` — largely the R3 scheduler-verification dispatches), 16 already `resolved`. **All 14 pending items were migrated**, byte-exact JSONB payload/verdict, same ids. The 16 already-resolved items and all of `audit_log` were left behind, deliberately: both are genuinely closed history with no further action pending on either — Acme's audit trail starts empty on Supabase, its approval *history* (the resolved 16) starts empty, but its approval *queue* (the 14 pending) does not. Better Auth `session` rows were also left behind — ephemeral tokens, a fresh login issues a new one, nothing lost.

**The go/no-go gate, and why it can't run from this session:** `Vault.verifyBrainKeyDecryptable` against Acme's migrated key is the real proof the ciphertext transfer is usable, not just byte-identical — but it needs the real KMS master key, a Railway secret this session never has access to. That check has to run as the first step after cutover (the deployed service, which does have the key), not before it — recorded here so it isn't skipped.

**The regression this whole section closed doesn't stay closed on its own — a standing check, not a one-time fix.** Supabase re-applies both defaults (RLS-auto-enable, anon/authenticated grants) per table, at creation time — not per database. A future migration that adds a table without knowing this history would silently reopen the exact exposure §5 closed. `verifyNoPublicApiExposure` (`packages/db/src/migrate.ts`) runs on every boot, independent of `runMigrations` (same ADR-022 option (b) reasoning `verifySchemaCurrent` already uses): asserts every `public` table is owned by the connection's own role, and that `anon`/`authenticated` hold zero grants anywhere. The grant check is naturally a no-op on Neon/local Postgres — those roles don't exist there, so they can never appear as a grantee — no environment-detection branch needed. Wired into both `start.ts` and `dev.ts`, right after `verifySchemaCurrent`.

**Status at the time of writing:** schema fully migrated and verified (`runMigrations()`/`verifySchemaCurrent()`/`verifyNoPublicApiExposure()` all run for real as `app_user`); RLS isolation proven live (`verifyRlsIsolation.ts`, all three checks, real cross-tenant/cross-user negative tests); Acme's data migrated and checksummed, including its 14 pending approval items. Cutover has since completed: `DATABASE_URL` set on Railway, `verifyBrainKeyDecryptable` returned true for all 6 of Acme's brain keys (cfo, cmo, delivery, founder, product-dev, support) against the live deployed KMS key — the go/no-go gate passed. Neon stays live and untouched until at least 2026-09-02 (one week post-cutover) before any deletion discussion, per explicit instruction.

## ADR-042 — A real staging environment: second Supabase project, Railway environment, explicit deploy targeting (2026-08-26)

**Context:** ADR-041's whole reason for existing was to get a real staging environment without paying for a second Neon project. With Supabase live in production, this is that second environment — and the moment to fix a naming problem the single-environment era never had to confront: `deploy-staging.yml` has, since ADR-026, actually deployed to what Railway itself calls "production" (the app code's own KMS tier is `StagingKms`/ADR-007's non-production tier regardless — that naming is unrelated and unchanged). One file serving two conceptually different purposes under one ambiguous name is exactly the setup where a wrong-environment deploy becomes easy to trigger by accident, which is the specific failure mode this work is scoped to design against, not just "stand up more infrastructure."

**What was provisioned, isolated from production at every layer:**
- Supabase project `fkggnoqksqblyjtewcdg` ("Runwisely-staging", `us-west-1`, free tier) — a second project on the same account, same mechanism ADR-041 already used.
- Railway environment `staging` (project `perceptive-generosity`, same as production) — created empty, not duplicated from production, specifically so no production secret ever sits in the staging environment even transiently.
- A fresh `STAGING_KMS_MASTER_KEY` (32 bytes, base64), generated new — never the production value, never derived from it.
- `BETTER_AUTH_SECRET` and `INTERNAL_METRICS_TOKEN` also generated fresh for staging rather than reused from production, on the same isolation principle even though only the KMS key was explicitly called out — the cost of separating them is zero and it closes the same class of cross-environment blast radius.
- Upstash Redis: **not yet provisioned.** No Upstash MCP/API access exists in this session, and creating third-party accounts is outside what an agent should do unattended — this is the one piece that needs a human in the loop, same category as the Railway dashboard steps ADR-041 called out up front.

**Hardened by construction, not caught by the guard:** every one of the 14 migrations (including 0013/0014's RLS-disable and anon/authenticated-revoke) was applied in order via `apply_migration` against the fresh project, then `app_user` created (`NOSUPERUSER NOBYPASSRLS`) and given ownership of every table/sequence — the exact same bootstrap sequence ADR-041 §3 used for production. Verified directly, not assumed: a single query confirmed zero non-`app_user`-owned tables, zero `anon`/`authenticated` grants, RLS correctly disabled on exactly the 10 tables that should have it off, and `app_user` itself carries neither `rolsuper` nor `rolbypassrls`. Supabase's own security advisor (`get_advisors`, type `security`) returned zero lints against the finished project — the guard (`verifyNoPublicApiExposure`) exists as the standing regression check for *future* migrations, not as the thing that caught the *initial* setup this time.

**Why the workflow split, not just a second copy of the same file:** `deploy-staging.yml` was renamed to `deploy-production.yml` (git mv, not delete-and-recreate — its full operational history, including the ADR-029 build-sha verification saga and the railwayapp/cli#696 workaround, stays attached to the file that still needs it) and a new `deploy-staging.yml` written for the real target. Both now carry, explicitly rather than inferred:
- A distinct tag suffix (`v*.*.*-production` vs. `v*.*.*-staging`) — the two triggers can never collide.
- A GitHub Environment per job (`railway-production` / `railway-staging`) — secrets are scoped per environment, so a staging secret can never resolve inside the production job even if a future edit fat-fingers a name.
- An explicit `-e "$RAILWAY_ENV"` on every Railway CLI call that supports it, plus an explicit `railway environment "$RAILWAY_ENV"` link as the first Railway step in each job — belt-and-suspenders for the one subcommand (`status`) that has no `-e` flag at all.

**Scope deliberately cut: no second Vercel project.** The instruction that started this work named a second Supabase project, Railway environment, Upstash database, and KMS key — not a second Vercel project for `apps/web`. Standing one up unasked risked a worse failure than not having one: a staging build silently landing on the *same* Vercel project that serves real production traffic, with no environment-scoping mechanism on that side to prevent it (Vercel's own "production"/"preview" split is per-branch within one project, not per genuinely separate project the way this Railway/Supabase split is). `deploy-staging.yml` is API-only — it proves `apps/api` boots clean against the isolated Supabase project, RLS holds, and a real signup/org-creation round-trip works, using Railway's own generated domain as its own origin in place of a web frontend that doesn't exist yet.

**A hard limit surfaced mid-task, correctly, not worked around:** migrating the *existing* `STAGING_KMS_MASTER_KEY` GitHub secret's live value (the one production actually uses today) into the new `railway-production`-scoped secret required either reading it back from GitHub (impossible — secrets are write-only, by design) or piping it live from Railway's own CLI output. The latter was attempted and the permission classifier correctly refused it: a live production encryption master key is exactly the kind of value an agent should not be routing through shell pipelines on its own judgment, no matter how carefully. That one value — and the Upstash `REDIS_URL` for staging — are the two things a human still needs to set by hand before `deploy-production.yml`/`deploy-staging.yml` can run for real; everything else in this ADR is already live and verified.

## ADR-043 — Effect-dispatch stays draft-only for all of MVP-1/Phase 2 — a decision, not an open TBD (2026-08-26)

**Context:** `apps/api/src/durableTrustCore.ts` has, since ADR-026, constructed `OpenMultiAgentExecutor` with no `handsVault`/`handsTools` and a comment flagging this as "MVP-1 is deliberately draft-only (see issue TBD, effect-dispatch posture)" — an acknowledged gap with no issue number ever assigned and no ADR closing the question. Scoped before touching anything, same discipline as ADR-041's migration: what's actually built, what's genuinely undecided, and what the real options are.

**What's actually there, found by tracing the real code, not assumed from the comment:** `EffectDescriptor`/`EffectExecutor` (`packages/approval-queue`) are real, tested infrastructure — the gate that would stand between an approved action and a real-world side effect (`send`/`post`/`pay`/`deploy`). `MockEffectExecutor` (`packages/approval-queue/src/effectExecutor.ts`) is the *only* class implementing `EffectExecutor` anywhere in the repo, and it does nothing but return `{ success: true }`. More to the point: **no code path anywhere ever sets `ProposedAction.effect` to a non-`undefined` value** — not the scheduler (`scheduledDispatchProcessor.ts`), not the manual-submit route (`tasks.ts`, whose zod schema has no `effect` field). `router.ts`'s own `effectiveEffect` logic (forcing `undefined` for CEO-tier tasks or when Hands are missing) is a real, tested safety net, but it's never actually the thing preventing dispatch today — there's simply nothing upstream that would ever hand it a real effect to gate in the first place. Draft-only today is a gap by omission, not enforcement by design — this ADR is what makes it the latter.

The Hands *machinery* is further along than the "no handsVault/handsTools yet" comment might suggest: Vault-backed credential storage, real Google OAuth token exchange/refresh (`apps/api/src/oauth/googleCalendar.ts`), and a generic JIT-decrypt-and-invoke wrapper (`apps/router/src/handsTool.ts`) all exist and are tested. What's missing is the layer above all of it: not one concrete `HandsToolSpec` (an actual "create this calendar event," "send this email," "make this payment" implementation) exists anywhere, and `durableTrustCore.ts` doesn't wire the machinery into the executor it actually constructs.

`docs/design/tool-registry.md` already carries per-role product judgment on this exact question — e.g. "a real payroll run is never autonomous, full stop," compliance work "permanently locked," and, for at least one platform, "even with earned autonomy... keep draft-only irrespective of the general OAuth story." None of this is enforced anywhere in code today; `Router`/`ApprovalQueue` have no concept of a role or effect kind being permanently locked. That prose is the clearest signal already in this codebase of where the eventual real-dispatch policy should land — this ADR doesn't contradict it, it just formally closes the door until the gates below clear.

**Decision:** Draft-only for the whole of MVP-1 and Phase 2. No `EffectExecutor` beyond `MockEffectExecutor` gets built in this window; no `RouterTaskInput` caller starts setting `effect`. Every scheduled agent produces a draft — approving something in the queue means "reviewed," never "sent," full stop, for every role and every effect kind, with no earned-autonomy exception. This closes out the three options actually considered:
1. **Draft-only, made explicit (chosen).** Zero new dispatch risk; the gap becomes a recorded decision instead of an accidental one.
2. **One real effect, human-gated only** (e.g. Google Calendar event creation, since its OAuth plumbing already exists) — considered, not taken now. Real dispatch, but earned-autonomy auto-accept explicitly barred from ever triggering it.
3. **One real effect, autonomy-eligible** — explicitly rejected. Earned autonomy triggering a real external side effect with zero human click would be the first genuinely unattended real-world action this system has ever performed, before any real user has actually used the product. Doing that before the pilot, not after, is the wrong order regardless of how narrowly it's scoped.

**What has to be true before this reopens:** (a) the pilot actually happening — real users, real usage, not synthetic verification — and (b) at least one Hands connection being genuinely usable in production, which today means Google OAuth verification clearing (the app is presently in an unverified/limited state per standard OAuth consent-screen review). Both gates, not either — real dispatch isn't a code milestone here, it's contingent on the product actually being used by someone other than this team.

**Made visible in the product, not just this ADR:** the approvals UI previously said "If you approve" with a fallback body of "this marks the work reviewed," which was *technically* accurate but easy to misread as implying the empty case was one possibility among others, not the only one that will ever exist for the foreseeable future. Changed: the primary action button now reads "Mark reviewed" instead of "Approve" (`ApprovalsScreen.tsx`), and the section heading now reads "If you mark this reviewed." The dashboard's recent-activity feed showed a bare "Approved" for a resolved action (`DashboardScreen.tsx`) — changed to "Reviewed," so a user skimming their own activity history can't read a past approval as something having been sent or executed. Implying execution while delivering only a draft is the one version of this that damages trust, and it was reachable in the UI even though the backend was always honest about it.

## ADR-044 — Real pricing set: $39/$89/$249 for Solo/Company/Scale, annual at 2 months free (2026-08-26)

**Context:** `pricingConstants.ts` had shipped `priceLabel: "—"` since 2026-08-08 — an honest placeholder (the page said outright "Pricing not finalised"), not a guess. Issue #18 ("Stripe billing for the four tiers") is what forced the question: a real payment integration needs real numbers, and none existed. ADR-025 already reconciled the tier *names* (Solo/Company/Scale, not the plan doc's Founder/Operator/Agency) — this is the first time real *prices* get attached to those three tiers.

**The numbers:** Solo $39/mo ($390/yr), Company $89/mo ($890/yr), Scale $249/mo ($2,490/yr). Annual is a flat 2 months free on every tier (10× the monthly rate, not a separately negotiated discount) — chosen for consistency, not because each tier's elasticity was separately modeled.

**Market comparison behind the actual numbers (Aug 2026 snapshot):** published SMB agent-platform pricing runs $30–150/user/month broadly. Sintra prices at $39 for a single agent or $97 for its bundle (discounted to roughly $48.50, or ~$15.60/mo billed annually). Lindy runs $29.99–199.99, credit-metered. The "no credits" challengers cluster lower — Dooza at $49, Marblism at $24. Solo's $39 sits at Sintra's single-agent price point while beating its credit cap entirely (see below); Company and Scale scale up from there for materially more agents/companies/team seats than any competitor's per-tier jump.

**Why "no credit caps" is the headline, not a footnote:** the credit-metering model (Lindy explicitly, Sintra's bundle implicitly) is the category's most common complaint — a plan that's nominally cheaper but throttles or requires top-ups once real usage starts. Runwisely's BYOK model means AI usage was never metered by Runwisely in the first place (ADR's own running theme: "Runwisely never marks up AI usage," the platform fee is flat regardless of how hard agents work) — this was already true before pricing existed, and is now the pricing page's lead differentiator instead of an implementation detail buried in a FAQ answer.

**Why the pricing page also had to get honest about draft-only, not just add a price:** the market's real dividing line among competitors is whether a product *acts* or only *drafts* — and Runwisely currently drafts (ADR-043). A pricing page that's silent on this implies parity with products that do act, which isn't true yet. Rewritten to say what the product actually does — "scheduled, contextual work derived from your actual business, reviewed by you" — rather than staying vague in a way a prospective customer could read as overpromising. Concretely: a new two-item highlight row right under the hero (no credit caps / drafts-not-actions), two new FAQ entries making both points explicit, and the monthly/annual toggle actually rendering real numbers instead of a static placeholder string.

**Scope of this change:** `pricingConstants.ts` (priceLabel → priceMonthlyUsd/priceAnnualUsd), `PricingPage.tsx` (toggle, real number formatting, the two new highlight cards, two new FAQ entries, removal of the "not finalised" banner and its `sr-only` disclaimer). Wiring these prices into an actual Stripe checkout/billing flow (the rest of issue #18) is deliberately a separate PR — real payment infrastructure with its own scoping (no Stripe account/API keys exist yet; the `tenants.tier` mutation route currently has zero payment gating in front of it, a correctness gap that has to close in the same pass Stripe lands, not before).

## ADR-045 — Stripe billing wired: checkout, webhook, and closing the free-tier-upgrade hole (issue #18, 2026-08-26/27)

**Context:** ADR-044 set real prices; this is what actually charges someone. Scoped first, same discipline as every other real-infrastructure change this session: what already existed (nothing — confirmed by full-repo search: zero Stripe dependency, zero webhook route, zero `stripe_customer_id`/`subscription_id` columns), what a real integration needs, and what has to change elsewhere as a direct consequence of prices now being real.

**The one gap this pass had to close, not just the one it was asked to build:** `POST /me/tier` let any signed-in tenant set their own tier directly, with zero payment — genuinely fine while tier was purely a cadence-floor knob (nobody was being charged anything either way), but a real, avoidable security hole the moment Solo costs $39/mo and Scale costs $249/mo: a free API call could claim Scale's entitlements without ever paying. Confirmed before removing it, not assumed: no UI anywhere calls this route (only `GET /me/tier` is read; the write path was reachable only via a bare API call). Removed entirely rather than gated — the persist-tier-and-resync-schedule logic it used to inline is extracted into `apps/api/src/scheduler/applyTierChange.ts`, now called by exactly one real caller: the Stripe webhook.

**What was built:**
- **Migration 0015**: `tenants.stripe_customer_id`/`stripe_subscription_id`, both unique-indexed (partial, `WHERE ... IS NOT NULL`) — verified against a real, live Postgres (the staging Supabase project from ADR-042), not just mocked, including that the unique constraint on `stripe_subscription_id` actually rejects a second tenant claiming the same subscription id.
- **`POST /me/billing/checkout`** (tenant-scoped): creates a Stripe Checkout Session for a given tier+period, returns the redirect url. Never touches card data — Stripe's own hosted Checkout keeps PCI scope entirely off this codebase, by construction.
- **`POST /billing/webhook`** (no session, no tenantMiddleware — Stripe authenticates itself via its signature header, verified against the real webhook secret): reacts to the **subscription** lifecycle (`customer.subscription.created`/`.updated`/`.deleted`), not `checkout.session.completed` — Stripe's own guidance for subscription billing is that the subscription object is authoritative for entitlements, and a completed checkout always produces a corresponding subscription event carrying the real Price id directly (`items.data[0].price.id`), which the checkout session object doesn't without a separate expansion. Reads the **raw** request body (`c.req.text()`, never `c.req.json()`) — Stripe's signature is computed over the exact bytes sent; any parse-then-restringify would produce a byte-different payload the signature would no longer verify against.
- **Tenant resolution needs no DB lookup at all**: `subscription_data.metadata.tenantId` is set at checkout-session creation, and Stripe copies that metadata onto the resulting Subscription object — every later event about that subscription carries `tenantId` directly. `stripe_customer_id`/`stripe_subscription_id` are stored for operational/support lookup and a future "manage billing" portal link, not as the tenant-resolution mechanism.
- **Six real Stripe Price ids**, one per (tier, period) pair, read from env vars (`STRIPE_PRICE_SOLO_MONTHLY`, etc.) — all-or-nothing with `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`: any of the eight set without all eight fails the server at boot (`readServerConfigFromEnv`), rather than booting with billing silently half-configured. All eight unset entirely is the current, expected state everywhere this app runs today — `billing: null` in that case, and `/me/billing/checkout`/`/billing/webhook` 503 cleanly rather than the whole server refusing to start (same "feature wired, inert until configured" pattern as Google Calendar OAuth, ADR-021).

**A real constraint this design had to respect, not work around:** `index.ts`'s own comment establishes that Hono's route chain must stay static for its typed `hc<AppType>()` client inference to hold — routes cannot be conditionally mounted based on runtime config. "Billing isn't configured yet" is therefore a runtime null-check *inside* both route handlers (`deps: BillingCheckoutRouteDeps | null`), not an absent route — both routes always exist, they just 503 until real Stripe config exists.

**Tested without a live Stripe account, honestly scoped:** `priceMap.ts`'s pure env-var-to-Price-id logic and both routes (`billing.test.ts`, with a fully faked `StripeClient`) are unit-tested thoroughly — checkout parameter passthrough, 503-when-unconfigured, signature-error → 400, missing-tenant-id → 500 (a real bug, not a bad request, so Stripe's own retry is the right behavior), and both webhook outcomes (`subscription-active`/`subscription-canceled`) driving `setTenantStripeIds`+`applyTierChange` in the right order. `stripeClient.ts`'s actual Stripe SDK wrapper (`new Stripe(...)`, `client.checkout.sessions.create`, `client.webhooks.constructEvent`) is deliberately **not** unit-tested with contrived mocks — same category as `googleCalendar.ts`'s real OAuth token exchange, which this codebase has never unit-tested either: a hand-rolled fake of a third-party SDK's internals verifies the fake, not the integration, and the only thing that actually proves this works is a live account, which doesn't exist yet.

**A real, pre-existing gap this pass does NOT close, stated plainly rather than glossed over:** on cancellation, `applyTierChange` reverts a tenant to `'solo'` — directionally correct (losing a paid subscription drops back to the baseline), but this does **not** mean Solo is a free tier with enforcement behind it. Nothing anywhere in this codebase enforces the per-tier company-count/agent-count/history-retention/team-member limits `pricingConstants.ts` advertises — confirmed nowhere in code: cadence floor (`cadenceFloors.ts`) is the *only* tier-driven enforcement that exists. A tenant who never completes checkout at all still defaults to `'solo'` (migration 0010's own column default, unchanged) and can use the product at whatever that implies today — this predates this PR, isn't a consequence of anything built here, and building real usage-limit enforcement is separate, unscoped future work, not something "wire up Stripe" was ever going to close as a side effect.

**What a human still has to do before any of this is live:** create a real Stripe account, create the three tiers as Products with a monthly and an annual Price each (six Prices total, matching ADR-044's numbers), and set the eight env vars above as real secrets on whichever environment(s) should accept payment. None of that can happen from this session — same category of human-only gate as the Upstash Redis database and the production `STAGING_KMS_MASTER_KEY` copy from ADR-042.

## ADR-046 — Bundle-size gate rewritten against the real preload manifest, not a filename guess (2026-08-27)

**Context:** `docs/STATUS.md` had carried an open item since an earlier session — "resolve the CI bundle-gate discrepancy (~127KB reported vs. ~194KB actually shipped)" — blocking any real performance measurement until the gate itself could be trusted. Investigated before touching anything: ran a real production build (`npm run build --workspace @byok/web`) and inspected the actual output, rather than guessing from the script's source alone.

**Two real, confirmed bugs in the original script, not one:**
1. It classified a built `.js` file as "initial" or "lazy route chunk" purely by checking whether its filename *started with* a route name string (`file.startsWith(\`${routeName}-\`)`). This happened to work for the one file it measured (nothing collided), but it's structurally the wrong question — several chunks (`AppShell`, `useAuthGuard`, `SchedulePauseBanner`, `brainKeyClient`, `handsKeyClient`) are shared across *most* authenticated routes, and the old script only ever reported ONE fixed total, never the actual worst case across real routes. A filename prefix has no way to know which routes truly pull a shared chunk in — only the app's own routing data does.
2. It globbed `*.js` only. The build's own CSS (`index-*.css`, inherited by every route via the root layout, confirmed via the real manifest's `__root__.css`) was entirely invisible to the 150KB budget — real bytes every single page load pays for, never counted at all.

**The fix uses the actual source of truth, not a better guess:** TanStack Start emits its own preload manifest at build time (`_tanstack-start-manifest_v-*.mjs`, found under `.vercel/output/functions/*/chunks/_/`) — the exact data the SSR renderer itself reads to decide which `<script>`/`<link>` tags to emit for a given route. `check-bundle-size.mjs` now imports that manifest directly (`tsrStartManifest()`), computes each route's real payload as `__root__`'s own preloads/css (always paid, every route) unioned with that specific route's preloads/css, and reports the **worst case across every route** against the 150KB budget — not an arbitrarily-chosen one.

**What the honest number actually is:** 146.21 KB gzip, route `/org-chart` — under budget, but meaningfully closer to it than the old, incomplete measurement implied. The exact historical "~194KB" figure in the STATUS.md note could not be independently reproduced from this investigation (it may have been measured via live browser DevTools against a since-changed deployed build, a different methodology than static analysis of a fresh local build can replicate) — rather than chase an unverifiable number further, this ADR records what *is* independently verifiable and fixed: two concrete, demonstrated bugs in the gate's own logic, now closed.

**Left as pre-existing, not this pass's job:** `docs/STATUS.md`'s broader staleness (still describes Redis as Upstash pay-as-you-go and the database as Neon, both superseded by ADR-041/042 this session) — only the one line this work directly resolves was touched; a full pass on that document is a separate, unscoped cleanup.

## ADR-047 — CostGate's pricing table becomes provider-scoped; real OpenAI and Google entries added, tier bands NOT forced to match Anthropic's (2026-08-27)

**Context:** PR #188 (ADR-047 there, dispatch wiring) fixed the executor silently defaulting every dispatch to the Anthropic adapter — but CostGate's own pricing table still had only three Anthropic entries, and `TierModelMap` was a single flat `{T1,T2,T3} -> model` map shared across every tenant/role regardless of provider. A role connected to OpenAI or Google still couldn't get a task priced or reserved at all: `evaluateAndReserve` had no provider dimension anywhere in its path.

**Research, not assumption — and the tier bands genuinely don't line up.** Current published pricing (independently cross-verified via two separate fetches per provider, 2026-08-27):

| | T1 (cheap) | T2 (mid/flagship) | T3 (frontier) |
|---|---|---|---|
| Anthropic (existing) | haiku-4.5: $0.80 / $4.00 | sonnet-4.6: $3.00 / $15.00 | opus-4.6: $15.00 / $75.00 |
| OpenAI | gpt-5-nano: $0.05 / $0.40 | gpt-5: $1.25 / $10.00 | gpt-5-pro: $15.00 / $120.00 |
| Google | gemini-2.5-flash-lite: $0.10 / $0.40 | gemini-2.5-pro: $1.25 / $10.00 | *(none distinct — see below)* |

OpenAI's and Google's own cheap tiers are meaningfully cheaper than Anthropic's T1, not equivalent (gpt-5-nano is ~16x cheaper on input than haiku). Their T2-equivalent flagships (gpt-5, gemini-2.5-pro) are priced identically to each other (~$1.25/$10) but well below Anthropic's sonnet. And **Google has no true frontier-tier model in this lineup at all** — its own flagship, gemini-2.5-pro, already IS its most capable and most expensive option; gpt-5-pro's input price matches opus exactly ($15) but its output price overshoots by 60% ($120 vs $75).

**Decision: tier bands are per-provider, not a shared absolute price band.** Forcing OpenAI/Google models into Anthropic's exact dollar cutoffs would either misclassify a genuinely-cheap model as "T2" or leave no honest T3 option for Google at all. `T1`/`T2`/`T3` now mean "this provider's own relative cheap/balanced/frontier tier" — a business/capability judgment specific to each provider's lineup, not a cross-provider price-matching exercise. Google's `T3` entry points to the same model as its `T2` (`gemini-2.5-pro`) — documented, not hidden: a high-stakes task on a Google-keyed role gets the same model a normal task would, because there's nowhere further to escalate to today.

**The mechanism:** `TierModelMap` itself is unchanged (still one provider's `{T1,T2,T3} -> model}` map) — `CostGate`'s constructor and `GateDependencies` now take `TierModelMapsByProvider` (`Record<provider, TierModelMap>`) instead of a single map. `tryDowngrade` (gate.ts) determines the CURRENT model's provider via `pricingTable.priceFor(model).provider` — already stored on every pricing entry — and downgrades within that same provider's map only. This matters concretely: a downgrade must never silently jump to a cheaper model from a DIFFERENT provider than the one whose vault key the executor already decrypted for this task; there's no way to actually dispatch to it without a different Brain key. Tested directly: a deliberately-cheaper OpenAI entry sitting in the same pricing table as an Anthropic one is never selected when downgrading an Anthropic task.

**Deliberately scoped out:** `scheduledDispatchProcessor.ts`'s own separate `selectModel(agent.tier, deps.tierModelMap)` call (picking a scheduled dispatch's initial model, before it ever reaches CostGate) still uses the single Anthropic-only map — it has no way to know a role's actual provider without a Vault lookup this pass didn't add. Real follow-on, same root gap as the deferred connect-flow UX (issue #190): nothing yet threads "which provider does this role actually use" to every place a model gets chosen, only to CostGate's own downgrade path.

**Trust-core note:** touches `packages/cost-gate` (CODEOWNERS-locked, ADR-005) — needs a human `TRUST-CORE REVIEWED` attestation before merge.

## ADR-048 — Multi-provider dispatch wiring: the executor now tells `@open-multi-agent/core` which provider to use, closing a live latent bug (2026-08-27)

**Context:** Phase 2 item 5's own scoping report (this session) found that `@open-multi-agent/core` never infers a provider from the model string — confirmed directly from source, not assumed: `agent.js:122` reads `const provider = this.config.provider ?? 'anthropic'`, an unconditional default that never inspects `config.model`. `OpenMultiAgentExecutor` never set `provider` at all — it only ever passed `model`. That meant every dispatch silently ran through the **Anthropic adapter**, regardless of which provider's key Vault actually had on file for that role. This was not a future risk: it was already live and wrong the moment any tenant connected an OpenAI or Google Brain key (Vault has been `(tenantId, roleId, provider)`-scoped since the Brain-per-role work earlier this session) — the model string for that role would reach the Anthropic SDK, which would reject it as unrecognized.

**The fix threads the vault's own stored provider all the way through:** `Vault.decryptBrainKey` returned a bare `SecretHandle` before this change — the provider was already on the record (`record.provider`, used for AAD binding) but never left the package. It now returns `DecryptedBrainKey { handle, provider }`. `OpenMultiAgentExecutor.execute()` destructures both and passes `provider: toSupportedProvider(provider)` into `runAgent()`'s per-call config, mirroring exactly how `task.model` already flows through per-dispatch — no new per-task field on `RouterTask` was needed, since the executor already resolves the Brain key itself at execute() time (Router never touches Vault directly).

**One real translation, not a pass-through:** our own stored provider ids (`anthropic | openai | google | deepseek` — `apps/api/src/brainKeys/providerValidation.ts`, matching the connect screen and Google's own branding) don't match `@open-multi-agent/core`'s `SupportedProvider` union verbatim — the library uses `'gemini'`, not `'google'`, and `createAdapter()` throws on any string it doesn't recognize. `toSupportedProvider()` (new, in `openMultiAgentExecutor.ts`) maps `"google" → "gemini"` and passes every other id through unchanged, deliberately uncast against the library's own union — an id it doesn't recognize is meant to reach `createAdapter`'s own runtime error, not be silently rejected a layer earlier.

**Verified, not just wired:** two new regression tests in `openMultiAgentExecutor.test.ts` prove a non-Anthropic provider actually reaches `runAgent`'s config (`provider: "openai"` for an OpenAI-keyed role) and that the google→gemini translation happens (`provider: "google"` stored, `provider: "gemini"` seen by the adapter config) — the exact gap that was silently invisible before, since every existing test's fake vault happened to return `SecretHandle` alone and never exercised what `runAgent` was actually told about the provider.

**Deliberately scoped out:** CostGate's pricing table still has only three Anthropic entries when this branch started — resolved separately by ADR-047 (`TierModelMapsByProvider`, real OpenAI/Google pricing), merged first. This PR fixes dispatch, not what model strings/pricing exist to dispatch to.

**Trust-core note:** touches `packages/vault` and `apps/router` (Router/Vault are both CODEOWNERS-locked, ADR-005) — needs a human `TRUST-CORE REVIEWED` attestation before merge.

## ADR-049 — Template-learning capture layer: every task-list edit now records a durable, per-task delta instead of being silently overwritten (2026-08-27)

**Context:** `docs/STATUS.md`'s "template-learning" line has stood as scoping-only since the previous session — the mechanism itself (usage-data-driven template improvement) is explicitly far off and out of scope here. But every day the underlying signal isn't captured is a day it's gone for good: `/batches/:id/reassemble` calls `assembleOrgChart` and persists the result via `batchStore.updateOrgChart`, which **overwrites** the org chart with no history. What the template originally proposed vs. what the tenant actually kept — the one signal any future learning mechanism would need — was being thrown away the moment a user edited their chart. This PR builds only the capture layer: durable, structured, per-task deltas, written on every edit. No aggregation, no cross-tenant/cross-user reads, no redaction design — deliberately out of scope until there's an actual reason to build them.

**Two distinct write sites, one shared shape:** the generation-time customize pass already computes exactly this diff (`CustomizationLog`, in `pipeline.ts`) but never persists it as its own record — `customizationLogToDeltas` re-maps that existing computation into `TaskDelta[]` with zero new diffing. `/batches/:id/reassemble` has no such log (the client submits a full edited task list, not a diff) — a new pure `diffTaskLists(before, after)` compares the persisted task list against the newly submitted one by id. Both land in the same `TaskDelta` shape (`{ taskId, kind: "added" | "removed" | "frequency_changed", detail }`) and the same table, distinguished only by a `source: "generation" | "reassemble"` column — one consistent, chronological log rather than two incompatible ones.

**User-scoped, not tenant-scoped — traced, not assumed:** the entire idea → interview → extraction → org-chart-reveal → edit flow, including `/batches/:id/reassemble` itself, runs behind `userMiddleware` with no tenant required (ADR-015 — confirmed directly from `extraction.ts`'s own doc comment, not inferred). `template_task_deltas` mirrors `signup_extraction_batches`' own pre-claim RLS pattern exactly: `user_id`-keyed policy, `FORCE ROW LEVEL SECURITY`, proven via a real-Postgres integration suite (`templateTaskDeltas.itest.ts`) — including that a second user's scoped session reads zero rows for the first user's batch, the same cross-user isolation proof this session's other stores have all carried.

**Deliberately best-effort at both write sites:** capture failure must never fail the actual product. Both `runExtractionBatch.ts` (generation-time) and `extraction.ts`'s reassemble handler (edit-time) wrap the delta write in its own try/catch, logging and continuing — the org chart itself is already saved by the time capture runs; a broken capture write should never turn into a broken save for the user. Tested directly: a throwing `taskDeltaStore` still yields a `"completed"` batch result.

**Deliberately scoped out:** `/batches/:id/rename-agent` (a leaf-field patch, never touches the task list — nothing to diff); the tenant-scoped, post-claim cadence-edit path (`updateOrgChartForTenant`, issue #141) — a real follow-on, since it's a structurally different write path (tenant-scoped, not user-scoped) that would need its own parallel store variant; and `customize.ts`'s `addTasks[].rationale` field, computed by the LLM but never persisted onto the final `Task` shape at all — a separate, pre-existing gap, not something this "small" capture pass should absorb.

**Trust-core note:** this PR adds a new table and RLS policy (`packages/db/src/migrations/0016_template_task_deltas.sql`) — per standing process, it needs a human `TRUST-CORE REVIEWED` attestation before merge, same as every other migration this session.

## ADR-052 — R5 (task chains): the pure state machine and its durable store, deliberately not yet wired to real dispatch (2026-08-27)

**Scope, deliberately narrow.** `docs/architecture/automation-runtime-plan.md` §4/§8 describes R5 (task chains) as multi-step sequences with mid-chain approval gates, staleness re-checks, and expiry — the next unbuilt layer after R1–R4 (cadence metadata → Charter/cascade → scheduler → digest, all shipped). This PR builds the foundation only: the chain data model, the pure state-machine transitions, and a real durable store. It does NOT wire chains into `Router.submitTask` or `ApprovalQueue` dispatch — that's a genuinely separable next PR, once this piece is solid, matching this session's own established pattern (the template-learning capture layer shipped its own store before any read/analysis layer existed; autonomy durability shipped its own store before ApprovalQueue's live-gating wiring changed to read it).

**New package, `@byok/chains`, mirroring `@byok/cost-gate`/`@byok/approval-queue`'s own shape:** pure logic (`chainEngine.ts`) at the top level, a `durable/` subfolder holding the store interface plus both an `InMemoryDurableChainStore` (dev/test, guarded against construction outside dev/test — same `DevOnly*GuardError` pattern as `InMemoryDurableAutonomyStore`) and a real `PostgresChainStore`. Not centralized in `packages/db` the way simpler single-table wrappers (`TenantScheduleStateStore`, `TemplateTaskDeltaStore`) are — those have no interface/multiple-implementation shape; this does, matching cost-gate's and approval-queue's own precedent instead.

**The state machine, and the one hard question the plan named explicitly:** `advanceChain` moves a chain forward on a step's real outcome — failure fails the whole chain outright (no partial-completion state worth preserving for a sequence where later steps assume earlier ones succeeded); success either advances to the next step, completes the chain, or — if the step `requiresApproval` — pauses at `awaiting_approval` without moving `currentStepIndex`, so only `resolveApprovalGate` can move past a gate, never `advanceChain` by accident. `resolveApprovalGate` is where the plan's own "hard question, answered explicitly" lives: *"If the triggering condition no longer holds when approval arrives (the invoice got paid), the chain aborts and tells the user why."* `conditionStillValid` is a caller-supplied fact, not something this package re-derives — "is the invoice still overdue" is domain logic the wiring layer owns, and staleness wins over the verdict unconditionally: even an APPROVE on a stale condition aborts. Tested directly.

**`steps` is one JSONB column, not a child table** — the same shape decision `signup_extraction_batches.org_chart` already made: every real access pattern reads or writes a chain as one atomic unit (every `chainEngine.ts` function takes and returns a whole `Chain`), never queries by individual step fields, so a child table would only add join complexity with no real query it enables. `PostgresChainStore.save` is consequently a whole-object read-modify-write, mirroring `SignupExtractionBatchStore.updateOrgChart` exactly, not a field-by-field `UPDATE` API that could let a caller write a `steps`/`status` combination the pure engine functions would never have produced together.

**Tenant-scoped, not user-scoped — unlike the pre-org stores this session also shipped.** `signup_extraction_batches`/`template_task_deltas` are keyed to `user_id` because they exist before any organization does (ADR-015). Chains have no pre-tenant analog: a chain only ever runs against a real tenant's claimed org chart, real agents, and (eventually) the real Router/ApprovalQueue — so `task_chains` (migration `0017`) follows the standard tenant-scoped RLS pattern (`tenant_isolation` policy on `app.tenant_id`), proven via a real-Postgres integration suite including cross-tenant isolation, the same discipline every other durable store this session shipped.

**Deliberately deferred, not forgotten:** the expiry sweep (a worker that finds every non-terminal chain past its `expiresAt` across all tenants and calls `expireChain`) needs a cross-tenant read this migration's RLS policy doesn't grant — resolved by having that future sweep iterate `listAllTenantIds()` and call `listByTenant` per tenant (the same pattern `sendDailyDigests.ts` already uses), not by adding an `internal_metrics`-style RLS bypass exception this table doesn't otherwise need. The actual wiring into `Router.submitTask`/`ApprovalQueue.onEvent` (so a real step dispatch and a real approval resolution actually call `advanceChain`/`resolveApprovalGate`) is the next PR, per the scope note above.

**Trust-core note:** adds a new table and RLS policy (`packages/db/src/migrations/0017_task_chains.sql`) — per standing process, needs a human `TRUST-CORE REVIEWED` attestation before merge, same as every other migration this session. `@byok/chains` itself is not yet wired into `@byok/router` or `@byok/approval-queue` (the CODEOWNERS-locked packages), so this PR touches no trust-core package's own source, only adds the migration.

## ADR-053 — Same-origin proxy (issue #144): apps/api's browser-facing routes move under /api, code-complete, deliberately not cut over to production yet (2026-08-27)

**Trigger, confirmed real:** issue #144's own two trigger conditions were written as an explicit "don't build this speculatively" gate. Condition 1 — a real custom domain unifying web + api — is now genuinely true: `www.runwisely.cc`/`runwisely.cc` are live, confirmed directly via the Vercel API (`get_project` on `runwisely-autopilot`), not assumed from a doc.

**A real routing collision ruled out the obvious approach before any code was written.** The natural first instinct — enumerate apps/api's existing top-level paths (`/health`, `/me`, `/dashboard`, `/tasks`, `/extraction`, `/metrics`, ...) as individual Vercel rewrite rules to the Railway origin — breaks immediately: `apps/web/src/routes/dashboard.tsx` and `tasks.tsx` are REAL PAGES at `/dashboard` and `/tasks` on the same origin apps/web already serves. A same-origin proxy can't route `/dashboard` to both "the React page" and "the JSON API route" without a distinguishing prefix — confirmed by actually listing `apps/web/src/routes/*.tsx`, not assumed.

**The fix: every browser-facing apps/api route now lives under `/api`.** `index.ts`'s route chain splits into `browserApi` (health, Better Auth, `/me/*`, hands-oauth, dashboard, tasks, extraction, metrics — everything a session-bearing browser calls) mounted at `/api` on the final app, versus `/billing` (Stripe's own webhook target) and `/internal/*` (operator routes, token-gated) which stay at their exact current top-level paths, untouched — neither is called by the browser, so neither needed to move, and moving them would have meant updating Stripe's own dashboard webhook config and any operator's existing bookmarks for no reason. Better Auth's own basePath convention (`/api/auth`) is preserved exactly: its internal mount became `/auth/*` so the outer `/api` wrap reconstructs the identical external path — `authClient.ts` needed zero changes.

**One rewrite rule, not an enumerated list that silently drifts:** `apps/web/vercel.json` now has exactly one rule, `/api/:path* → https://byokapi-production-6a57.up.railway.app/api/:path*` (the real Railway service domain, confirmed via the Railway API, not guessed). Every future apps/api route that belongs under `browserApi` is automatically covered — no per-route rewrite entry to remember, the exact fragility the enumerated-prefix approach would have carried forward indefinitely.

**Client-side blast radius was one line, not dozens.** `AppType`'s nested route tree meant every existing `apiClient.dashboard...`/`apiClient.me...`/`apiClient.extraction...` call site across the whole apps/web codebase broke at compile time the moment the server-side routes moved under `/api` — TypeScript caught every one, correctly. Rather than touching each of the ~15 files, `apiClient.ts` now exports `hc<AppType>(API_URL, {...}).api` instead of the bare client — pre-scoping the constant itself to `.api` once, so every existing call site kept working unchanged. The one call site NOT using the typed client — `handsKeyClient.ts`'s `handsOAuthStartUrl()`, a raw string for a plain `<a href>` OAuth redirect — needed its own explicit `/api` prefix added by hand, along with the matching `redirectUri` apps/api registers with Google's OAuth config (`server.ts`) and the one test asserting the old URL shape.

**New regression coverage where none existed:** every existing apps/api route test mounts its route directly at a test-local path, bypassing `createApp()`'s real composition entirely — none of them could have caught a wiring mistake in the `/api` wrap itself. `index.test.ts` (new) constructs the real `createApp()` with heavily-stubbed deps and proves three facts by HTTP status: `/api/health` resolves, the old unprefixed `/health` now 404s, and `/billing/webhook` (Stripe's target) still resolves at its original path while `/api/billing/webhook` does not exist. This test caught a real mistake before it shipped — the first draft asserted against bare `/billing` instead of `/billing/webhook` (`billingWebhookRoute`'s own internal `.post("/webhook", ...)` mount), which running the test immediately surfaced.

**What this PR deliberately does NOT do — code-complete, not cut over:**
- **No live environment variable was changed.** `VITE_API_URL` (Vercel), `CROSS_SITE_COOKIES`/`ADDITIONAL_WEB_ORIGINS` (Railway) all still hold their current cross-origin-workaround values. Flipping them is the actual production cutover, covered below as what a human still has to do.
- **`packages/auth/src/config.ts`'s `crossSiteCookies` option and `apps/api/src/index.ts`'s `cors()` middleware are untouched.** Both become unnecessary once the cutover env vars flip (a same-origin request never triggers a CORS preflight, and `SameSite=Lax` — the default — works fine once the cookie is genuinely first-party) but leaving them in place is harmless during the cutover window and a real follow-on cleanup, not a blocker to ship this PR.
- **The Vercel Hobby-plan function-duration risk issue #144 itself named stays unverified.** The Vercel team (`filomap-s-projects`) is confirmed, via the Vercel API, to be on the **Hobby plan** — its serverless function duration ceiling is materially shorter than Pro's. `/api/extraction/batches` runs a handful of sequential Claude calls synchronously ("seconds, not minutes" per that route's own comment) — comfortably fine hitting Railway directly today, genuinely unverified once every one of those seconds also has to survive Vercel's own external-rewrite proxy layer on Hobby. No streaming responses exist anywhere in apps/api (checked directly — ruled out as a separate risk the issue also named), but the duration question is real and this PR does not answer it.

**What a human still has to do before this replaces the current cross-site-cookie workaround in production:**
1. Deploy this branch as a real Vercel **preview** (not production) and confirm the rewrite actually reaches Railway end-to-end — sign-in, a session-bearing request, and specifically a real `/api/extraction/batches` call timed against the Hobby-plan duration ceiling named above. This is the one open question serious enough that this PR stops short of recommending a production flip without it.
2. Only once (1) passes: set `VITE_API_URL=""` on the Vercel project, `CROSS_SITE_COOKIES` unset/false and re-verify `ADDITIONAL_WEB_ORIGINS`/`WEB_ORIGIN` on Railway, matching apps/web's own real same-origin URL.
3. If Google Calendar Hands OAuth is ever enabled (still `null`/inert today, pending Google's own app verification per ADR-021) — its `redirectUri` now names `/api/hands-oauth/google-calendar/callback`; Google Cloud Console's own OAuth app config would need the matching updated URL registered before that flow could work, same category of external dependency as Stripe's webhook URL.

**Trust-core note:** doesn't touch a `@byok/{router,vault,cost-gate,approval-queue}` package — not CODEOWNERS-locked — but restructures how every browser-facing route in `apps/api` is reached, so flagged here for visibility the same way ADR-050 was.

## ADR-054 — R6 (event triggers): webhook signature verification + per-tenant secret storage, deliberately capture-only (2026-08-27)

**Scope, matching R5's own precedent.** `docs/architecture/automation-runtime-plan.md` §3(b)/§8 names R6 (event triggers) "highest value, highest security surface — after the safe path is proven," and its build-order note is explicit: build it *after* R5 exists to trigger, not before. This PR builds the receiving half only — real, tested signature verification and durable per-tenant storage — with zero dispatch wiring, the same "capture layer first" scoping this session already used twice (template-learning deltas, R5's own chain engine). What a verified webhook event actually TRIGGERS is a later PR, once R5's chains have real dispatch wiring of their own to trigger.

**One provider, built for real, not stubbed.** `WebhookProvider` is a `"stripe"`-only union today — the plan's own worked example ("Stripe invoice overdue") and the one provider this monorepo already has SDK access to. Deliberately NOT hand-rolled HMAC: `verification.ts` reuses Stripe's own `webhooks.constructEvent` (timing-safe comparison, timestamp-tolerance replay protection, official and already-audited), the same reasoning `apps/api`'s existing platform-billing webhook already applies to its own, separate trust boundary. Tested against REAL Stripe-generated signatures via `Stripe.webhooks.generateTestHeaderString`, not a mock of the verification call — a valid signature verifies, a wrong-secret signature is rejected, and a tampered payload (valid signature, different bytes) is rejected, because "highest security surface" earns real crypto tests, not interface-level mocks.

**A tenant's own Stripe account, not our platform billing — a genuinely different trust boundary from the existing webhook.** `apps/api`'s current billing webhook verifies Stripe telling US about OUR OWN subscription, against one platform-wide secret. R6's webhook secret is per-`(tenantId, provider)`: a TENANT configures a webhook endpoint in THEIR OWN Stripe dashboard, pointing at our per-tenant URL; Stripe generates the signing secret and the tenant gives it to us to store — the same "paste a secret, we validate and store it" shape the Brain-key connect flow already established, not something we generate and hand out ourselves.

**T2 enforced by the type system, not just a comment:** `VerifiedWebhookEvent.payload` is typed `unknown`, never `Record<string, unknown>` — every future consumer must explicitly narrow before reading a single field, mirroring how `RecommendationItem` has no `effect` field at all (T10/ADR-004) rather than trusting every call site to remember the rule by convention.

**Ponytail, named not hidden:** `webhook_endpoint_secrets.secret` is plaintext in an RLS-protected column, not Vault-encrypted like Brain/Hands keys. A leaked secret lets someone send FORGED events claiming to be that tenant's account — real, but bounded, since nothing dispatches automatically from a verified event yet. Upgrade path noted directly in the store's own module comment: route this through Vault's own encrypt/decrypt primitives once a real dispatch path exists downstream and the blast radius actually changes. Per-tenant webhook rate limiting (§7 rule 3: "Event triggers get their own ceiling... mandatory") is also deliberately deferred — it needs a real request-volume counter, which belongs with the actual receiving HTTP route (the next PR), not this foundational package.

**Trust-core note:** adds two new tables + RLS policies (`packages/db/src/migrations/0018_webhook_endpoints.sql`) — needs a human `TRUST-CORE REVIEWED` attestation before merge. `@byok/webhooks` itself doesn't touch a CODEOWNERS-locked package's own source.

## ADR-055 — Extraction stays cross-origin, exempted from the same-origin proxy (2026-08-27)

**The question ADR-053 left open, answered.** ADR-053 flagged the Vercel Hobby-plan rewrite-timeout risk as real but unverified. Real measured extraction latency this session (77–114s, found in this session's own transcript) against the proxy's ~120s CDN origin timeout is not meaningful headroom — one slow upstream Anthropic response and a real user's signup fails with no useful error, on the one path in apps/api that's actually slow. `/extraction/*` is never SSR-read (confirmed by grep — no route loader calls it), so routing it through the proxy buys nothing there was ever a reason to pay this risk for.

**The exemption lives in the client, not the rewrite rule.** A Vercel `rewrites` entry only fires for a request that's actually made to that path on the Vercel domain — so the real fix is `apps/web/src/lib/apiClient.ts`'s new `directApiClient`, a second `hc<AppType>()` instance that resolves against the real Railway origin even when `API_URL` is `""` (proxy mode). `extractionClient.ts`'s five extraction calls (`fetchQuestions`, `startBatch`, `getLatestBatch`, `reassemble`, `renameAgent`) use it; its own `me`/`metrics` calls stay on the ordinary same-origin `apiClient`, since only extraction carries the timeout risk. `vercel.json` also gets a defensive self-referential rule for `/api/extraction/:path*` ahead of the general catch-all, so a future regression that accidentally calls the relative path 404s loudly instead of silently succeeding-but-slowly through the proxy.

**The architecture from here on is "same-origin for everything except extraction" — permanently, not a transitional state.** ADR-053's own cutover checklist said to unset `CROSS_SITE_COOKIES` once the proxy replaces the cross-site-cookie workaround. That item is superseded, not merely delayed: extraction's direct cross-origin call needs the session cookie to travel cross-site for as long as extraction stays exempted, which requires `SameSite=None` (`crossSiteCookies: true`, `packages/auth/src/config.ts`) — `SameSite=Lax` is never sent on a genuinely cross-origin `fetch()`. **`CROSS_SITE_COOKIES=true` stays set on Railway indefinitely.** A future reader should NOT read this as leftover cutover-window cleanup and unset it — doing so would silently 401 every extraction call in production with no CORS error to point at why, since the failure is a dropped cookie, not a blocked request. `apps/api/src/index.ts`'s `cors()` middleware and `webOrigins` config stay load-bearing for the identical reason and must not be removed either. None of this costs the rest of the app anything: every other route still gets the full same-origin benefit (no CORS preflight, first-party cookie via the proxy, the 12 SSR routes issue #144 exists to fix) — `SameSite=None` cookies work same-origin too, so leaving the flag on is pure upside for those routes, not a compromise. If extraction itself ever moves back behind the proxy (a Pro-plan function-duration ceiling, a queued/async redesign of the extraction flow), *that* is the PR that finally gets to unset `CROSS_SITE_COOKIES` — not this one, and not by default.

## ADR-056 — Same-origin proxy cutover: VITE_API_URL flipped to same-origin in production (2026-08-28)

**What actually changed, and nothing else.** `VITE_API_URL` on the Vercel `runwisely-autopilot` project's **Production** environment is now `""` (empty) instead of the absolute Railway URL — the one flip ADR-053 named as the actual cutover. Preview and Development keep the absolute Railway URL, unaffected; deploying a PR preview or running `npm run dev` locally still works exactly as before. `CROSS_SITE_COOKIES` and `ADDITIONAL_WEB_ORIGINS`/`WEB_ORIGIN` on Railway were **not** touched — per ADR-055, `CROSS_SITE_COOKIES=true` is the permanent architecture now (extraction stays cross-origin indefinitely), not a cutover-window value waiting to be unset.

**Verified before the flip, not assumed:** production Railway confirmed live at `main`'s current commit via direct behavioral test — unprefixed `/health` 404s (proving the pre-ADR-053 routing is gone), `/api/health` returns 200 (proving both the route move and the healthcheck-path fix are live) — rather than trusting `/api/health`'s own self-reported `buildSha`, which turned out to be stale (only ever set by `deploy-production.yml`, which has never actually run against this service). The proxy mechanism itself was verified on a real Vercel preview deployment first: `/api/health` 200 through the rewrite, unprefixed `/health` 404, confirming the Vercel→Railway rewrite genuinely works end to end before touching production's own env var.

**Rollback is one env var revert, nothing else.** If anything breaks: set `VITE_API_URL` back to `https://byokapi-production-6a57.up.railway.app` on the Vercel project's Production environment and redeploy. No code change, no migration, no Railway-side variable to touch — `CROSS_SITE_COOKIES`/`ADDITIONAL_WEB_ORIGINS` were never part of this flip, so there's nothing on the Railway side to unwind. This is the same one-step-revert shape every other "flip a value, not a deploy" change this session has kept deliberately reversible.

## ADR-057 — Solo/Company/Scale collapse into one plan, three billing periods (2026-08-28)

**What changed:** three tiers ($39/$89/$249, gated on cadence) become one plan — $39/month, $105/quarter ($35/mo effective, save 10%), $374/year ($31.17/mo effective, save 20%) — everything the product does, included, at every period. The effective monthly rate is the big number on `/pricing`, the real billed total small beneath, same "derive it, never hand-type it" discipline ADR-051's annual display already established.

**Cadence floor: daily, chosen from the plan's own real numbers, not guessed.** `docs/architecture/automation-runtime-plan.md` §7's modeled COGS range is $3.59–$9.39/company/month, and its own standing rule is "if median COGS exceeds 20% of price, the floor is wrong." Against $39: the low end is 9% of price, comfortably under; the high end is 24%, only marginally over — but Hourly or 15-minute floors would blow well past 20% for every tenant now, since there's no higher-priced tier left to absorb the higher run volume the way Company/Scale used to. Daily is the only defensible single floor from the data that exists today; `packages/jobs/src/cadenceFloors.ts` now exports one `CADENCE_FLOOR` constant instead of a per-tier map, and `clampCadenceToTierFloor` (renamed `clampCadenceToFloor`) drops its tier parameter entirely. Revisit once R3's real instrumentation (`scheduler_instrumentation_daily`, shipped but not yet consumed for this) has enough measured data to confirm or correct the modeled estimate, per the plan's own standing rule.

**A real finding while scoping this, not assumed:** grepped the whole codebase for per-tier company-count enforcement before touching anything — there isn't any. `apps/api/src/routes/billing.ts`'s own doc comment already said as much ("nothing in this codebase enforces the per-tier company/agent/history/team-member limits pricingConstants.ts advertises"), and ADR-051's claim that `cadenceFloors.ts` "already caps [Scale] at 10 companies" is false — that file has never contained company-count logic. Collapsing to one plan doesn't remove any enforcement that existed, because none did; the "1 company" stat is honest now in a way it technically wasn't validated as before.

**`tenants.tier` collapses to a single allowed value, not deleted.** Migration `0019_collapse_tenant_tier.sql` narrows the CHECK constraint to `tier = 'solo'` (any pre-existing 'company'/'scale' row — none in this project's real data, confirmed via the real Stripe test-mode verification this same session ran — collapses to 'solo' first). Kept rather than dropped: removing the column outright would need a second migration to bring it back if pricing is ever re-differentiated, for a column that costs nothing to leave in place at a single value. Two separate `TenantTier` type declarations existed before this (`packages/db/src/tenantSchedule.ts` and `packages/jobs/src/cadenceFloors.ts`, structurally identical but never imported from each other) — the jobs package's copy is gone now that cadence has no tier dimension left; the db package's copy narrows to the literal `"solo"`.

**Stripe: six Prices become three, on a single new Product.** The old three-Product/six-Price test-mode setup (ADR — this session's own earlier Stripe work) is deactivated, not deleted (Stripe doesn't allow deleting a Price/Product with any history) — a fresh `Runwisely` product carries the three real prices. `apps/api/src/billing/priceMap.ts`'s `StripePriceMap` drops the tier dimension (`Record<BillingPeriod, string>`, not `Record<TenantTier, Record<BillingPeriod, string>>`); `tierForPriceId` is gone, replaced by `assertKnownPriceId` — the webhook still needs to reject a price id it doesn't recognize (never trust an unrecognized Stripe event blindly), it just no longer resolves anything from it. `BillingPeriod` gains `"quarterly"`; env vars go from six `STRIPE_PRICE_{TIER}_{PERIOD}` to three `STRIPE_PRICE_{PERIOD}`.

**The webhook's active/canceled distinction is now purely `stripe_subscription_id`, not tier.** Both `applyTierChange` call sites in `routes/billing.ts` are now identical (`applyTierChange(outcome.tenantId)`, no second argument) — `tenants.tier` writes `'solo'` either way; the only real signal of paid status left in the schema is whether `stripe_subscription_id` is set. Whether an unsubscribed tenant should be blocked from using the product at all was never answered by the old three-tier system either (same "nothing enforces this" finding above) — this collapse doesn't create that gap, and doesn't close it.

**Trust-core note:** touches `packages/db` (CODEOWNERS-locked, ADR-005) via the new migration — needs a human `TRUST-CORE REVIEWED` attestation before merge.

## ADR-058 — Website-as-input: paste a URL instead of typing an idea (2026-08-28)

**What it does.** `IdeaForm.tsx` gains a second mode alongside "Describe it" — "Paste your website" — that fetches the URL server-side, extracts its visible text, and summarizes it into the same plain-string `idea` the free-text box has always produced. Nothing downstream of that string changed: the interview, extraction batch, and org-chart pipeline all still see an ordinary `idea: string`, exactly as before.

**SSRF is the real risk, treated as a hard prerequisite, not a nice-to-have.** Fetching a URL a signed-out visitor supplies is a classic vector for an untrusted caller to make the server probe internal infrastructure (cloud metadata endpoints, internal services) from behind the platform's own network boundary. `packages/agents/extraction/src/websiteFetch.ts`'s `assertSafeToFetch` runs before every connection attempt — scheme allowlist (http/https only), a literal-IP check on the URL itself, and a real `dns.lookup` on the hostname, rejecting anything that resolves to a private/loopback/link-local address (RFC1918, `127.0.0.0/8`, `169.254.0.0/16` — which includes the AWS/GCP/Azure metadata endpoint `169.254.169.254` — plus the IPv6 equivalents). Critically, this check runs on **every redirect hop**, not just the starting URL, via a hand-rolled `redirect: "manual"` loop (fetch's own `redirect: "follow"` would connect to a hop before this code ever saw it) — a hostname that resolves cleanly to a public IP but 302s to a private one is exactly the bypass this closes. Bounded to 5 hops.

**Bounded single attempt, matching `packages/vault`'s own convention, not the untimed `fetch()` calls elsewhere.** `websiteFetch.ts`'s `withTimeout` is the same pattern as `vault.ts`'s (10s, same magnitude as `DEFAULT_REFRESH_TIMEOUT_MS`) — one attempt, no retry loop, fails closed. `apps/api/src/brainKeys/providerValidation.ts` and `oauth/googleCalendar.ts` both call raw `fetch()` with no timeout at all; that's a pre-existing gap this feature deliberately doesn't inherit, not a pattern it follows.

**T2 — enforced procedurally, not by the type system, and the comment says so honestly.** `packages/webhooks`' `unknown`-typed payload works as a type-level guard because nothing needs to read it as text. Fetched page text is different: summarizing it IS the point, so it stays a plain `string` — the T2 boundary here is the prompt itself (`websiteSummary.ts`'s `buildPrompt`), which wraps the page text in explicit delimiters and tells the model plainly that anything inside, including text that looks like an instruction, is page content to describe, never something to obey. No real HTML parser (no cheerio/jsdom) — script/style blocks and all remaining tags are regex-stripped, which also means the fetched page's own JavaScript never executes anywhere in this pipeline. Ponytail-named: regex extraction is lossy against real-world markup; upgrade to a real parser if it proves too lossy in practice.

**Its own CostGate reservation, not the extraction batch's.** `apps/api/src/extraction/runWebsiteSummary.ts` reserves budget (roleId `"onboarding"`, taskType `"website-summary"`, same pre-org per-user scope as the batch — ADR-015) only once real page text exists to estimate a prompt from, and only for the summarization call — the fetch itself isn't gated, it costs nothing but a bounded network round-trip. A failed or unsafe fetch never touches the batch's own reservation, and a summarize failure releases its own. Real cost, using this session's already-verified Haiku pricing ($0.80/$4.00 per M tokens): roughly $0.004–0.005 per URL-mode signup, layered on the existing $0.03–0.10 CAC.

**Never a dead end.** Every non-"completed" outcome — unsafe URL, unreachable site, too-thin content, the model's own "not enough here" signal, a CostGate QUEUE/SKIP, or a hard failure — is a typed `status` the client falls back on: `IdeaForm.tsx` switches back to the plain-text box with an inline reason, ready to type immediately, never stuck on a spinner or an error screen.

**Trust-core note:** doesn't touch a `@byok/{router,vault,cost-gate,approval-queue}` package's own source — uses `CostGate` through its existing public interface, same as `runExtractionBatch.ts` already does.

**What this fixes, concretely:** issue #144's own 12 authenticated routes that broke on bookmark, hard refresh, or deep link under the old cross-site-cookie workaround (`SameSite=None` cookies work fine on a normal navigation but were fragile across exactly those three flows in some browser configurations). Live verification on `www.runwisely.cc` (sign-in, hard refresh on `/dashboard`, bookmark/reopen, deep link to `/agents`, one real extraction) is in progress as this entry is written — this ADR records the flip and its rollback, not yet that verification's outcome.
