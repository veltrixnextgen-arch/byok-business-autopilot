## Labels

| Label | Color | Meaning |
|---|---|---|
| `trust-core` | red | The four security-critical components ADR-005 CODEOWNERS-locks: router, vault, cost gate, approval queue. Merges require the `TRUST-CORE REVIEWED` attestation, a required CI check (ADR-012) — a real CODEOWNERS approval where more than one maintainer exists. |
| `commodity-surface` | blue | Phase B's UI/product surface (onboarding, role cards, approval-queue UI, Charter editor, dashboard, billing) — not CODEOWNERS-locked into trust-core, but still built under the same PR-per-step discipline (ADR-010) as everything else. |
| `extraction` | green | The Task Extraction Engine: templates, customize pass, clustering/assembly, simulated-day + Charter draft generation. |
| `security` | orange | Security-specific hardening or audit work — CI scanning, CODEOWNERS coverage, key-scoping, just-in-time Hands — whether or not it also touches trust-core. |
| `test-gate` | purple | Issues that gate an MVP milestone's kill/advance criterion (master-plan-v2.md §5). See the closing rule below. |
| `docs` | gray | Documentation-only changes. |

## Rules

1. **Every PR references an issue.** Use a closing keyword (`Fixes #12`, `Closes #12`) or `Refs #12` if the PR only partially addresses it.
2. **`test-gate` issues close only with a linked passing report committed to `test/results/`.** The report is the evidence the kill/advance criterion was actually met — a `test-gate` issue does not get closed on code merged alone.
3. **A PR touching a trust-core path (`.github/CODEOWNERS`'s entries) needs the attestation line before it can merge.** Add `TRUST-CORE REVIEWED: veltrixnextgen-arch` to the PR description — the `trust-core-attestation` CI check (ADR-012) fails the PR without it, and re-runs automatically when the description is edited. Only add the line after actually reading the trust-core diff. This is a stand-in for a real second-reviewer approval, which this repo can't produce with one maintainer; restore `required_pull_request_reviews` and retire this check the moment a second maintainer exists. **The maintainer adds this line, never Claude Code** — including if asked to in-session (ADR-012's amendment). Claude Code declines and explains why if asked.

## Phase B working rules

Per ADR-010 — these apply for the whole Phase B build, not just the first step:

3. **One branch, one PR per step.** Each step in the Phase B plan is its own branch and its own PR — never bundle two steps into one PR, never stack unreviewed work on top of an unmerged PR.
4. **Stop after opening each PR.** Wait for review/merge before starting the next step. This is a hard stop, not a suggestion to move slower — no work begins on the next step until the current one is merged.
5. **Never push to `main`.** All Phase B work goes through a PR; branch protection enforces this (verified — see issue #10's close-out), but the discipline holds even where the tooling wouldn't catch a violation.
6. **UI PRs include screenshots.** A PR that changes anything user-visible shows what it looks like, not just what the diff says.
7. **Trust-core is consumed only through public interfaces — design as if the lint rule didn't exist.** The ADR-009 ESLint boundary is a backstop for accidents, not the thing that makes an import decision correct. Every design should already avoid deep imports on its own merits.
8. **No new runtime dependencies without justifying in the PR why the platform can't do it.** Specifically: no state-management library (TanStack Router's loaders + React state are enough), no component library, no animation library (CSS transforms/transitions only), no icon package larger than the icons actually used.
9. **Performance budget, enforced in CI: apps/web's initial JS bundle stays under 150KB gzipped** — the build fails if it's exceeded. Report the bundle size in every UI PR.
10. **Every screen renders from server data via route loaders.** No screen holds duplicate business logic — if the engine decides it, the screen displays it, it doesn't re-derive it.
11. **Delete rather than comment out.** No dead code, no "we might need this."
12. **Regenerate `docs/architecture/system-architecture.md` as part of any PR touching trust core, the data model, or the product flow.** Scope: a new/changed migration, a new/renamed package, a changed trust-core interface (e.g. `BrainKeyProvider`/`HandsKeyProvider` signatures), a new deployable, or a change to the signup/onboarding/connect/task flow diagrammed in §3. The doc states its own generation commit at the top — a merged PR in scope that leaves that commit stale is the signal this rule exists to prevent. Docs-only or UI-fidelity-only PRs (no trust-core/data-model/flow change) are exempt. Added 2026-08-11 after the doc drifted three PRs (#94, #95, #96) past its own stated snapshot with no regen in any of them.

## Known state: two `npm audit` findings with no real fix available (2026-08-08)

Both were investigated in full (dependency-tree tracing, registry checks, a
real clean-install verification) rather than run through `npm audit fix
--force`, whose suggested "fixes" for these two are actively wrong — see
below. `hono` (the third finding from the same audit run) was a real,
actionable fix and shipped separately; only these two remain open.

**`@tanstack/start-server-core` <1.167.30 (GHSA-9m65-766c-r333, moderate — "inbound
server-function request deserialization could invoke a sibling
client-referenced server function"), reached via `apps/web`'s
`@tanstack/react-start-plugin@1.131.50`.**
- **Why the audit's suggested fix is wrong:** `npm audit fix --force` proposes installing
  `@tanstack/react-start-plugin@1.121.22` — a *downgrade* from our current `1.131.50`.
  Confirmed against the npm registry: `1.131.50` is already the newest version TanStack
  has published for this package. There is no newer release that carries a patched
  `start-server-core`; the "fix" doesn't fix anything, it just moves 10 patch versions
  backward for zero security benefit.
- **Why the deployed request path isn't exposed:** `@tanstack/react-start-plugin` is a
  Vite build-time plugin (`apps/web/vite.config.ts`'s `tanstackStart()`), never imported
  by application/runtime code. The actual framework runtime, `@tanstack/react-start`
  (currently `1.168.34`), resolves its **own** separate copy of `@tanstack/start-server-core`
  at `1.169.17` — already past the patched threshold (confirmed via `npm ls
  @tanstack/start-server-core`, which shows both copies side by side). `apps/web/src`
  has zero usages of `createServerFn` or any other server-function API, so the
  vulnerable deserialization path isn't reachable through our own code either way.
  Combined with ADR-016's architecture (real SSR request serving goes through
  `@tanstack/nitro-v2-vite-plugin` → `nitropack`, not through this plugin), this
  advisory has no real-world exposure in this deployment today.
- **Action:** none. Tracking upstream for a `@tanstack/react-start-plugin` release
  that bumps its nested `start-server-core` past `1.167.30`. Re-check next time
  `npm audit` is run as part of any dependency work.

**`esbuild` <=0.24.2 (GHSA-67mh-4wv8-2f99, moderate — "esbuild enables any website to
send any requests to the development server and read the response"), reached via
`packages/db`'s `drizzle-kit@0.31.10` → the deprecated `@esbuild-kit/esm-loader` →
`@esbuild-kit/core-utils@3.3.2` (pins `esbuild: ~0.18.20`).**
- **Why the audit's suggested fix is wrong:** `npm audit fix --force` proposes
  `drizzle-kit@0.18.1` — a downgrade from our current `0.31.10` to a pre-1.0 release
  roughly 13 minor versions back, purely to dodge a legacy sub-dependency. Real risk
  of breaking the migration CLI's config/schema handling, for a vulnerability that
  isn't reachable in our setup (see below).
- **Why a narrow `overrides` pin doesn't work either:** tried forcing just this nested
  `esbuild` to a safe version (`0.25.12`, already used elsewhere in the tree) two ways —

  specific nested optional/platform-binary dependency doesn't respond to `npm`'s
  `overrides` the way `h3` does elsewhere in this same file. Not investigated further —
  the real-world risk doesn't justify chasing an npm resolution quirk.
- **Why the real-world risk is near zero regardless:** the advisory requires exposing
  esbuild's own dev server to untrusted network access. `@esbuild-kit/core-utils` is
  only reachable through `drizzle-kit`'s CLI (local migrations, never deployed), and

  `@esbuild-kit/core-utils` is also itself deprecated upstream ("merged into tsx") —
  the dependency will most likely disappear on its own the next time `drizzle-kit`

- **Action:** none. Re-check after any future `drizzle-kit` upgrade, since the
  deprecated `@esbuild-kit/*` chain is likely to be dropped from a newer release

## Known state: Railway auto-detects workspace packages as deployable services — only `@byok/api` is intentional (2026-08-12)

Railway's GitHub integration provisions a service for any `package.json` it finds while scanning the repo — **not gated on that package having a `start` script.** `apps/router` (a library, no `start` script at all) was auto-provisioned as a second service (`@byok/router`) purely from its own `package.json`'s presence, then inherited the repo-root `railway.json`'s generic, service-agnostic `deploy.startCommand` (`npm run start --workspace @byok/api`) — so it ran the API's start command against an environment `deploy-staging.yml` never configures (that workflow only ever calls `railway variable set ... --service "@byok/api"`), crashed instantly on `apps/api/src/server.ts`'s `DATABASE_URL is required` check before ever reaching Vault/Router construction, and crash-looped on every push to `main` from at least 2026-08-08 onward (`railway deployment list --service "@byok/router"` — FAILED entries going back that far, confirmed via real deploy logs, not inferred). **Lesson for next time a Railway deploy is red**: check `railway deployment list --service "@byok/api" --json` for the actual failing deployment's own logs (`railway logs --deployment --latest`) before assuming the most-recently-merged PR's diff is the cause — twice now the real cause has predated and been unrelated to whatever was merging at the time.

## Known gap: PR #123/#129's deploy-verification SHA assertion only works through the git-webhook deploy path, not `railway up` (2026-08-16)

PR #123 (later revised by #129) added a step to `deploy-staging.yml` asserting the actively-serving deployment's own `meta.commitHash` matches the commit being deployed — the whole point being to make "is the thing serving traffic the thing I just built" mechanically verifiable instead of inferred from a green health check. That assertion works correctly when Railway's own GitHub-webhook auto-deploy triggers the build (it reliably populates `meta.commitHash`).

It does **not** work when a deploy is triggered via `railway up` (CLI-upload deploy) instead — confirmed directly while deploying PR #131's merge commit (`17baf97`) on 2026-08-16: the webhook-triggered deployment for that exact commit came back `SKIPPED` (the same "later-arriving SKIPPED relative to the real serving deployment" quirk noted elsewhere in this file), so `railway up` was used to force it. The resulting deployment reached `SUCCESS`/`RUNNING` correctly, but its `meta.commitHash` came back `undefined` — a known, reproducible gap in what Railway's CLI-upload path populates, not a one-off. Verification in that case had to fall back to reasoning from local git state instead (`git log --oneline -1` showing a clean checkout at the target commit immediately before running `railway up`) — a real, sound argument, but not the same mechanically-checked guarantee #123 was built to provide, and it only works because the agent doing the deploy also controls the local checkout being uploaded.

**Why this matters**: a verification that silently no-ops (empty/`undefined` field, not a hard failure) on one of two live deploy paths will eventually mislead someone who trusts the check without knowing which path fired. `deploy-staging.yml` itself always deploys via the git-webhook path (matching #123/#129's own trigger), so the automated workflow is unaffected — this gap only bites when a deploy is triggered manually via CLI, which has already happened at least once during real incident response this session (this entry, and the original REDIS_URL/Redis-TLS incidents) and is likely to happen again under the same conditions (needing to force a deploy past a `SKIPPED` webhook race).

**Action**: not fixed here — flagging per the gap, not silently working around it again next time. If picked up: either (a) make `railway up`-triggered verification assert on `activeDeployments[0]`'s `createdAt`/`status`/`RUNNING` instance only (what this session's ad hoc CLI verification already does) and explicitly document that commit-SHA matching is unavailable on this path, or (b) find whichever Railway CLI/API call (if any) can tag or query the commit associated with a CLI-upload deployment after the fact, so the same mechanical assertion can cover both paths.

## Known state: the R3 scheduled-dispatch investigation's full infrastructure failure chain (2026-08-15 through 2026-08-18)

Anyone debugging this stack later — including a future session — should read this as the map of what's already been ruled out and fixed, not start from "why doesn't the scheduler fire" as if it were still one unknown problem.

**1. Malformed `REDIS_URL` (fixed 2026-08-14, see the incident entry above).** The GitHub secret held Upstash's whole `redis-cli --tls -u ...` command line pasted in whole, not just the URL — set 10 days before any code first tried to parse it, silently harmless until R3's BullMQ code shipped and crashed on boot the instant it called `new Redis(REDIS_URL)`. Every deploy from PR #115 through #121 failed or was skipped as a result; Railway kept serving a stale pre-incident build the whole time, which is what made every "green health check" in that window meaningless. Fixed by correcting the secret and variable to the bare URL.

**2. `REDIS_URL`'s scheme was `redis://` (plain), not `rediss://` (TLS) (PR #130, 2026-08-16).** Upstash requires TLS; a plain-scheme connection produced a distinctive signature — TCP connects, then the connection is torn down immediately, over and over — that showed up as continuous, seemingly-benign `ECONNRESET` noise in the logs (initially misread as normal Upstash idle-connection recycling, since it never crashed anything by itself). The real cost was silent: `queue.upsertJobScheduler()`/`getJobSchedulers()` calls made against this connection would hang indefinitely rather than fail, because ioredis's default behavior on a broken connection is to retry/queue commands forever rather than reject. Fixed by correcting the URL scheme, plus adding a `commandTimeout` specifically to the Queue's (not the Worker's — see the PR for why) connection options so a future broken connection fails loud instead of hanging silently.

**3. Pooled Postgres connections that errored were still released back to the pool "clean" (PR #131, 2026-08-16).** Separately from the Redis issue, staging crashed three times with the identical signature: an uncaught `error: terminating connection due to idle-in-transaction timeout` (Postgres `25P03`) taking down the *entire* `@byok/api` process for every tenant, each time landing near a request that ran multiple concurrent tenant-scoped transactions. Root cause: every transaction-scope helper (`withTenantScope`, `withUserScope`, `withUserAndTenantScope`, `withInternalMetricsScope`) called `client.release()` with no argument in its error path, even when the `ROLLBACK` it had just attempted had itself failed — and a real `pg.PoolClient` only discards the underlying connection when `release()` is passed a truthy error. A connection released "clean" while still stuck mid-transaction went back into the pool for a completely unrelated later request to silently inherit, which then sat idle until Neon's own timeout killed it and crashed the process. Fixed by threading the real error into `client.release(err)` everywhere. A follow-up audit (PR #132) found and fixed the same bug in `internalMetrics.ts`'s direct (non-helper) `pool.connect()` usage, and added a `pool.on('error', ...)` listener to `createPool` itself — a second, distinct failure mode where an *already-idle* connection (never in a bad state when released, just failing later on its own) would otherwise crash the process via Node's default unhandled-`EventEmitter`-error behavior.

**4. `ioredis` was pinned to `6.0.0` — an unpinned, undeliberate choice, and it never actually connected (PR #138, 2026-08-18).** With #2 and #3 fixed, the scheduled dispatch *still* never fired. Direct diagnosis — a purpose-built, token-gated `/internal/scheduler-debug` route hitting the live queue from inside Railway's own network — proved the underlying `ioredis` connection was stuck at `RedisConnection.status === "initializing"` indefinitely: never ready, never erroring, never closing, so every downstream BullMQ call (including the scheduler-registration path) hung forever with nothing to observe. `commandTimeout` (fix #2) didn't help here because it only bounds a command *after* dispatch; bullmq's own connection-bootstrap step (`waitUntilReady()`) has no timeout of its own. Git history showed `ioredis@6.0.0` — its only 6.x release at the time — was hardcoded exact from the very first commit that added `packages/jobs/package.json`, with no discussion anywhere: `bullmq@6.0.5` made `ioredis` an *optional* peer dependency specifically so callers would deliberately choose a version, and nothing here did, so `npm install` simply resolved to whatever was current that day. Pinning `ioredis` alone to a stable `5.x` failed immediately and loudly (a `MODULE_NOT_FOUND` crash — `bullmq@6.0.5`'s compiled code imports from an `ioredis@6.x`-only internal path); fixed by pinning `bullmq`+`ioredis` together to `5.81.3`/`5.11.1`, the pairing `bullmq` itself exact-pins, plus a new `connectionHealth.ts` guard (built against bullmq's stable public `waitUntilReady()`, not version internals) that races every connection against a bounded timeout and surfaces the result permanently via `GET /health` and `/internal/scheduler-debug`, so this exact class of silent-forever-hang can't recur unnoticed on whatever version pair comes next. Full design record: ADR-027.

**5. A live Railway platform incident (started 2026-08-18T23:19 UTC, resolved 2026-08-19).** The moment PR #138 was ready to verify, Railway's own status page (`status.railway.com`) began reporting "Deployments are slow to progress" — three independent deploy attempts (one webhook-triggered, two manual `railway up`) all got stuck `QUEUED`/`INITIALIZING` and then failed, every one with zero build logs and zero deployment logs, all starting within minutes of the incident's own start time. Confirmed via Railway's own status page, not inferred from the CLI's silence. The live site was unaffected throughout (Railway correctly kept serving the last successful deployment). Not a bug in this codebase — recorded here because it's the reason PR #138, once merged, could not immediately be verified live, and to save whoever hits a similarly log-free, multi-attempt deploy stall the time of re-diagnosing application code before checking Railway's own status page first.

**6. The actual final root cause: `REDIS_URL`'s password didn't match the database's real, current password (found and fixed 2026-08-19).** Once the Railway incident cleared and PR #138 deployed cleanly, `connectionStatus` *still* never reached `"ready"` — same exact symptom as bug #4, now on the freshly-pinned `bullmq@5.81.3`/`ioredis@5.11.1` pair. That ruled the version-pin theory out as the sole cause. Upstash's own server-side connection metrics (queried directly via their management API, using a scoped API key the user provisioned specifically for this) showed `connection_count: 0` for every single minute of the deployment's uptime — the connection was never even reaching Upstash as an authenticated session. Comparing credentials directly: Railway's configured `REDIS_URL` carried an **8-character** password; the database's real, current password (fetched from Upstash's own API) was **62 characters**. They were never the same value — most likely a leftover from the original malformed-`REDIS_URL` incident's manual fix (2026-08-14), where an incomplete or stale password was pasted in place of the real one. Fixed by fetching the real password from Upstash's API and setting it on both Railway and the GitHub secret. `connectionStatus` reached `"ready"` immediately on the next deploy — the true end of this whole chain.

**The pattern worth naming**: fixes #1 through #6 are all real, and each one was independently necessary — none of them was a red herring or a wasted detour. But each one's fix *changed the failure mode* rather than immediately producing the working end state, which is exactly what made this take several sessions instead of one: "the scheduled dispatch still doesn't fire" was true before and after each fix, for five completely different reasons in a row. The lesson for next time this kind of "nothing happens and nothing errors" symptom shows up in this stack: get to direct, ground-truth evidence (a real DB query, a real connection-status read, a real platform status page, the vendor's own management API) as early as possible rather than reasoning forward from the current fix's own success — the absence of the old symptom is not evidence the underlying thing now works.

## Known state: R3 verified end-to-end against a real tenant (2026-08-19) — and a footgun in reading the evidence

With the infrastructure chain above fully resolved, R3 was verified for the first time against a real Charter + cascade + claimed org chart (tenant "Acme," a fresh signup run through the actual product flow, not synthetic fixture data): 17 job schedulers registered and independently confirmed via a direct Redis read; a real unattended dispatch produced settled `cost_reservations` and pending `approval_queue_items` rows, including a CEO-tier task correctly routed as a non-dispatchable `recommendation` (T10 held under real load); a deliberately-tripped cost ceiling produced a real `tenant_schedule_state` pause with the blocked task preserved in `paused_batches`, and `POST /me/scheduler/resume` cleared both, confirmed by direct query, not the API's own claim about itself.

**Footgun for whoever reads `scheduler_instrumentation_daily` next**: the first verification pass showed `scheduled_runs_executed: 10` and it would be easy to read that as steady-state throughput ("10 runs in however-long, so roughly N runs/hour"). It wasn't a repeating cycle — none of that tenant's 17 registered tasks actually have a 15-minute cadence (they're genuinely weekly/monthly/daily by nature, e.g. "weekly-plan," monthly SEO, daily expense categorization). The 10 was each of ~10 tasks firing once, immediately, on registration — BullMQ's normal first-fire-on-create behavior for a freshly upserted Job Scheduler — not evidence of a fast recurring cadence. Don't extrapolate a firing rate from that number without first checking what cadence the counted tasks actually carry.

## Known state: a manual DB check against an RLS-protected table with no tenant scope returns zero rows, silently — a false "data loss" signature (2026-08-20)

While verifying R4's digest work, a read-only ad hoc check queried `signup_extraction_batches`, `company_charters`, `cost_reservations`, `audit_log`, `scheduler_instrumentation_daily`, `approval_queue_items`, and `tenant_schedule_state` directly with a plain `pool.query(...)` — no `set_config('app.tenant_id', ...)`, no transaction scope. Every one of those tables came back `count(*) = 0`. `tenants` and `users`, queried the same unscoped way in the same pass, came back with their real row counts (84 each). The contrast — two tables full, seven tables empty — read exactly like a selective data-loss incident: a targeted `TRUNCATE`, a Neon branch reset that spared the identity tables, something actively wrong. It was reported to the user as exactly that.

It wasn't. Every one of those seven tables has `FORCE ROW LEVEL SECURITY` with a `tenant_isolation` policy that filters on `current_setting('app.tenant_id', ...)` (`migrations/0002_durable_storage.sql` and friends) — the same mechanism `withTenantScope` (`packages/db/src/tenantContext.ts`) sets before every real application query touches these tables. An unscoped query has no tenant context set, so the policy correctly matches nothing — not an error, not a warning, just zero rows, indistinguishable at the SQL level from the table genuinely being empty. `tenants`/`users` returned real data only because those two tables were deliberately never put behind RLS in the first place (`0001_init.sql`'s own comment) — which is exactly what made the false signature look deliberate rather than like a query mistake.

Re-running the same check correctly — looping every real tenant id from the (unscoped-safe) `tenants` table and scoping each read through `set_config('app.tenant_id', $1, true)` inside a transaction, the exact `withTenantScope` mechanism — found all the data fully intact: 5 extraction batches, 2 charters, 15 cost reservations, 30 audit log rows, 2 scheduler-instrumentation rows, 15 approval-queue items, 1 schedule-state row, matching what R3's verification (the entry above) had already found and reported for tenant "Acme." Nothing was ever lost.

**Tables outside RLS entirely** (safe to query unscoped, will return real global data): `tenants`, `users`. **Every other application table** (`tenant_members`, `signup_extraction_batches`, `company_charters`, `cost_reservations`, `audit_log`, `scheduler_instrumentation_daily`, `approval_queue_items`, `tenant_schedule_state`, `autonomy_counters`, and any future RLS-policied table) requires either `withTenantScope`/`withUserScope`/`withUserAndTenantScope` (one known tenant/user id) or `withInternalMetricsScope` (the one existing cross-tenant carve-out, currently scoped only to the signup-metrics tables) — never a bare `pool.query()`.

**The pattern worth naming**: an unscoped read against an RLS table doesn't fail loud, it fails silent and plausible — zero rows is a completely valid response for a table that's genuinely empty, so nothing about the query itself signals the mistake. The only thing that exposed it here was a second, independent signal (`pg_stat_user_tables.n_live_tup`, Postgres's own live-tuple estimate, which isn't subject to RLS) showing real nonzero row counts on tables a scoped `count(*)` had just reported as empty. Before concluding a table is empty from an ad hoc/manual query — especially one written outside the codebase's own store classes, which all correctly scope through `withTenantScope` already — check `pg_stat_user_tables` for that table's `n_live_tup`, or better, just scope the query correctly from the start.
